---
title: X68000 Z に Wi-Fi で TCP/IP を通す
---

X68000 Z の Human68k から、Wi-Fi 越しに TCP/IP を通せるようになった。RS-232C の SLIP では 2.7KB/s だったのが 8.7KB/s になり、Z は LAN 上の 1 台として Mac から直接つながる。

使ったのは、USB に挿して Z のリモートドライブにする Pico W のファーム [x68kzremotedrv](https://github.com/yunkya2/x68kzremotedrv) だ。これに、SCSI の 1 台分を通信路にして SLIP を運ぶ仕組み (netpipe と呼んでいる) を足した。Z の中では、計測技研の ESP/X をもとにした xip.x が TCP/IP を受け持つ。

作業は [x68kcli](https://github.com/j3tm0t0/x68k/tree/main/x68kcli) (Human68k 3.02 に zsh や vim を入れた HDD イメージ) の一部として進めた。

Z の中では、xip.x が作ったパケットを slip.sys が SLIP にし、slipd.x が SCSI ID 6 越しに Pico とやり取りする。Pico から先は、Wi-Fi に直接出すブリッジか、Pi を経由する UDP モードを選ぶ。

## 出発点: シリアルの SLIP

最初は Z の RS-232C と Raspberry Pi を 3 線でつなぎ、PPP (IIJ-PPP の Human68k 移植) で TCP/IP を通した。つながりはしたが約 1KB/s で、相手がいないと ppp.x が固まる。

Human68k には公開された SLIP ドライバがないので、自分で書いた。

- **slip.sys**: xip.x からは Ethernet カード (`/dev/ep0`) に見えるデバイスドライバ。送るときは Ethernet の見出しを外して SLIP にする。
- **slipd.x**: 常駐スレッド。IOCS でシリアルを読み書きし、受けた SLIP をほどいて xip.x に渡す。

初めは SCC の割り込みを slip.sys が自前で横取りしていたが、xip.x のヒープやスタックが壊れてバスエラーが出た。ROM と RSDRV.SYS の割り込み処理に任せる形にしてからは安定している。38400bps で 2.7KB/s 出て、これが今回の出発点になった。

## netpipe: SCSI の 1 台を通信路にする

x68kzremotedrv は Pico W を USB メモリのふりをさせ、Z からは SCSI のハードディスクに見せる。その中の SCSI ID 6 は、もともと B: ドライブ (Pi の共有フォルダ) のやり取りに使われている「通信用のディスク」だ。ここに空いている LBA を借りて、SLIP のバイト列を運ぶ。

1. Z の slipd.x が、送りたいバイト列を見出し 16 バイトと一緒に LBA 0x100000 に書き込む。
2. Pico は書き込みを受けたら、中身を外に送り、それまでに届いていた受信データで応答を作る。
3. slipd.x が応答を読み、送った番号と応答の番号が合えば、受信データを xip.x に渡す。
4. やり取りが続く間はすぐに次の交換をし、静かなときは 20〜50ms おきに問い合わせる。

1 回の SCSI の読み書きは 0.2〜2.5ms で、速さの壁にはならない。

ひとつだけ厄介なのが、Z 本体 (中は Linux で動くエミュレータ) が SCSI の読み込みをキャッシュすることだ。同じ LBA を 2 度読むと、Pico には届かず、古い中身が返ってくる。そこで応答は、約 480MB の帯 (LBA 0x110000〜0x1ffff7) を 8 セクタずつずらしながら、毎回違う場所から読む。B: のドライバ (scsiremote.sys) も同じ理由で同じことをしていて、そちらは 0x200000 以降を使う。

Pico から先は 2 つの運び方を用意した。

- **UDP モード**: Pico が SLIP を UDP で Pi に渡す。Pi の `slipudp.py` が疑似端末につなぎ、slattach で sl0 にして NAT で外へ出す。シリアルの SLIP と同じ構成を、ケーブルなしで作れる。
- **ブリッジモード**: Pico 自身が Wi-Fi に転送する (後述)。

## 律速は xip.x だった

netpipe でつないだ直後は約 4KB/s で、シリアルの 1.5 倍ほどにしかならなかった。計ってみると、xip.x はパケットの大きさに関係なく、1 個ごとに 100〜150ms かかっていた。しかも TCP の MSS が 512 に固定されているので、1 個で運べるのは 512 バイトまでだ。

ウィンドウを広げる (`-w`)、高速化係数 (`-n`)、Human68k のタイムスライス (`PROCESS`) はどれも効かなかった。`-w 16384` 以上にすると xip.x のヒープが足りなくなって固まる。

そこで xip.x を逆アセンブルして、MSS の既定値が置かれたデータの 1 ワード (`$0200`) を探し、`$05B4` (1460) に書き換えた。それだけで 8.5KB/s になり、1 個あたりの時間は変わらないまま、運べる量が増えた分だけ速くなった。

xip.x (K.Shirakata 氏による改良版 β5) はバイナリでしか配布されていない。改変したバイナリは配らず、イメージを作るときに `scripts/patchxip.py` が元の xip.x の SHA-256 を確かめてから書き換える。

## ブリッジモード: Pi も NAT もなしで LAN に出る

UDP モードだと、Z は Pi の NAT の内側にいて、外から Z のサーバにつなぐにはポート転送が要る。そこで、Pi を通さずに Pico が Wi-Fi に直接出す運び方を足した。

- Pico は、Z の IP (ここでは 192.168.1.68) 宛ての ARP 要求に、自分の MAC アドレスで答える (代理 ARP)。
- Wi-Fi から届いたフレームのうち、Z の IP 宛ての IPv4 だけを抜き取って SLIP にし、Z に渡す。それ以外は Pico 自身の lwIP に流す。
- Z から来たパケットは、lwIP の `etharp_output` で宛先 (LAN の外ならルーター) の MAC を引いて Wi-Fi に出す。

Z の IP は `slipd.x -z 192.168.1.68` のように渡し、要求の見出しに載せて Pico に知らせる。これで Z は LAN 上の 1 台になり、Mac から `192.168.1.68:2323` の rcmd に直接つながる。ルーターの DHCP では、ダミーの MAC アドレスで 192.168.1.68 を予約して、ほかの機器に払い出されないようにした。

1 つの MAC アドレスに 2 つの IP が載ることになるが、NURO のルーターは問題なく転送した。Pi の wlan0 に 2 つ目の IP を足して同じ状況を作り、外まで往復することを先に確かめている。

## ハマったところ

いちばん時間を食ったのは、Z 本体の読み込みキャッシュが絡む 2 つだった。どちらも「Pico の電源を入れ直すと直る」ので、最初は Pico の不具合に見えた。

| 症状 | 原因 | 直し方 |
| --- | --- | --- |
| 22 分ほど動かすと、通信がそれきり止まる | 応答を読む帯が 256MB しかなく、65,536 回で一巡するとキャッシュの古い応答しか返らなくなる | 帯を広げた |
| リセット後、昔のパケットが流れ込む。ping の返事が何倍も来る | キャッシュは X68000 をリセットしても消えない。番号を 1 から数え直すと、前の回の応答を「正しい」と受け取る | 番号と読み始めの位置を、起動のたびに時刻から決める |
| CONFIG.SYS で B: のドライバを組み込むところで止まる | netpipe の帯が scsiremote.sys の使う LBA (0x200000〜) と重なった | 帯を 0x200000 より下に移した |
| ブリッジで SYN-ACK が外に出ない | xip.x はフレームを 60 バイトに詰める。小さいパケットは IP の全長より長く届き、Pico が捨てていた | IP の全長で切って送る |
| rcmd が上がらないように見える | CTTY AUX の間に押したキーがキーバッファに溜まり、その ESC で rcmd.x がすぐ終わる | 起動時にキーバッファを捨てる |
| コンソールから打つと ping が返事を取りこぼす | 前面の ping.x が DOS コールで待つ間、裏の slipd.x に CPU が回らない | rcmd 経由 (zsh の中) で打つ |

切り分けで効いたのは、slipd.x に直近 64 パケットの先頭を残しておき、小さな道具 (ztap.x) で Z の上から表示したことだ。「送ったのは 2 つなのに返事が 7 つ来る」「Pi 宛ての古い TCP を Z が中継している」と分かったことで、キャッシュがリセットをまたいで残っていると気づいた。

Z を遠隔で操作するために、もう 1 枚の Pico W を USB キーボードにして Z に挿し、UDP でキーを送れるようにした。Ctrl+F11+Del (ソフトリセット) は 0.6 秒押し続けないと効かない。

## 結果

Wi-Fi 越しのブリッジがいちばん速く、シリアルの SLIP の約 3 倍出た。Pi から Z の NUL に 200KB を送って計った (PPP とシリアルの SLIP は 100KB)。

| 方式 | 経路 | xip.x の MSS | 速度 |
| --- | --- | --- | --- |
| PPP | RS-232C 38400bps → Pi | 512 | 約 1KB/s |
| SLIP | RS-232C 38400bps → Pi | 512 | 2.7KB/s |
| netpipe (UDP) | Pico W → Pi | 512 | 約 4KB/s |
| netpipe (UDP) | Pico W → Pi | 1460 | 8.4KB/s |
| netpipe (ブリッジ) | Pico W → LAN | 1460 | 8.6〜8.9KB/s |

ブリッジでは、Z から 8.8.8.8 への ping が約 200ms で往復し、Mac から Z の rcmd に直接つながる。200KB を休みなく送り続ける試験では、失敗は 0 回だった。

## 残っていること

- 帯を一巡したあと (約 12 万回の交換) も止まらずに動くかは、確かめている最中だ。
- 電源を入れた直後に「ディスクから起動できません」と出ることがある。Pico の Wi-Fi と SMB の接続が、Z がディスクを調べるまでに間に合わないためらしい。
- 律速は今も xip.x で、1 パケット 100〜150ms の中身はまだ調べていない。
- netpipe を足したファームはまだ公開していない。

[Previously]({{ site.baseurl }}{% post_url en/2026-11-07-x68000z-diary-17 %}): With the goal "I want it to feel so much like UNIX that you'd think you were using UNIX", I ran up to 11 AI workers at once and built mount.x, which presents the drives as a single tree, and zosh, a UNIX-like shell. Then I hit the weekly usage limit.

This entry picks up from there. After the limit reset, I cut the workers down to one or two. I also changed the approach. Instead of fixing whatever came to mind, an AI went through about 200 commands asking: "If someone used to UNIX used this for a day, where would they notice it isn't UNIX?" We fixed what it found and ran the check again, three times in all. Over two days we merged about 25 PRs, and at the end we ran it on a real Z.

## Checking with 200 commands

One worker did the check, playing "a day in the life of a UNIX user": look at files, chain pipes, search, edit, run jobs, make archives, mistype things. It booted the full image from SCSI in XEiJ (an X68000 emulator), typed the commands one key at a time, and read the screen (text VRAM). Other workers did the fixing; the checker only wrote down what it found.

I had it rank the results by how much they broke the illusion. The top item in the first pass was "the classic pipe doesn't work": typing `sort f.txt | uniq -c | sort -rn` got Sharp's SORT.X printing its usage in Japanese.

| What you notice | Pass 1 (11/07) | Pass 2 (11/08) | Pass 3 (11/09) |
| --- | --- | --- | --- |
| `sort` `find` `xargs` | Sharp's versions run, no `xargs` | GNU versions run | Blank lines from `xargs -n1` fixed too |
| Error messages | `cat: nosuch: ありません` (Japanese) | `No such file or directory` | man in English too |
| `sleep 100 &` | The shell blocks for 100 seconds | Returns at once; `jobs`, `kill %1` | — |
| `ls /` | Fails | Lists the boot files | Hidden with the hidden attribute |
| `ls -l` | `-rw--a` (Human68k attributes) | `-rw-r--r-- 1 moto moto` | External `ls` uses the same format |
| `pwd` | `A:/home/moto` | `A:/home/moto` | `/home/moto` |
| `echo $PATH` | Empty (only lowercase `path`) | `/usr/bin:/bin:...` | — |
| `less` | Broken | GNU less runs | Hangs on short files → fixed |
| `file f.txt` | Missing | A bus error stops everything | Fixed |

By the second pass most of the obvious problems were gone. Often, though, fixing one thing exposed the next layer. Once `ls /` worked, the listing was full of `human.sys` and `autoexec.bat`, which didn't look like UNIX. Once `file` was in, it brought down zos.x with a bus error.

Along the way we also fell into a trap once. In an image the lead AI built, `sort` was still Sharp's, and it panicked that the fix hadn't worked. It turned out the folder of GNU commands (the stage) was still the one built on 10/21, and GNU `sort` simply wasn't in it. The code was fine; the inputs were stale.

## Small stories from the fixes

Most of the fixes were mundane, but a few had interesting causes.

**`less` hangs.** Open a short file and the status line never appears, `q` doesn't get you out, and the CPU sits at 95%. less was opening files in text mode, and the C library (newlib) stripped the CR at the end of each line. That left fewer bytes to read than the file's length, so less kept rereading, thinking there was more to come. Opening in binary mode, as on MS-DOS, fixed it.

**`make`'s name gets garbled.** Typing `make` where there's no Makefile printed something like `h s.sh 1 2 longer args: *** No targets...`, with leftovers from an earlier command showing up as make's name. Human68k's argument-passing convention (HUPAIR) puts the command name (argv[0]) after the arguments. zosh wasn't putting it there, so make read the earlier string still in memory as its own name.

**`touch "with space"` creates `with`.** zosh wasn't splitting the name. The Human68k FAT drive was cutting names at the space. That can't be fixed, so instead of quietly creating `with`, zosh now refuses with `Invalid argument (this drive cuts names at a space)`. It also checks beforehand so it never overwrites an existing, different file named `with`.

**`~` looks like an overline.** In the X68000 font, the glyph for `~` (0x7E) is an overline (‾). zos.x panes and ssh.x already drew their own tilde, but outside the panes it was still an overline. A resident program that swaps the glyph already existed; it just wasn't in the boot image.

**A crashing child freezes the pane.** When a child program died with a bus error, its pane never came back. It didn't happen on the test rig, only with the full image. A worker narrowed it down by comparing five builds in XEiJ: the cause was the Ctrl+C handling we'd added to zosh last time. Swapping the Ctrl+C handler with a DOS call left something behind even after restoring it. We still don't know what. But writing directly to the process-management area and Human68k's work area made the problem go away.

## Why are external commands slow?

What feels least like UNIX when you're typing is actually speed. On XEiJ (10MHz) an external command takes 0.2–0.4 seconds, and a five-stage pipe such as `ls -l /usr/bin | wc -l` takes about 3 seconds. So I had a timer temporarily added to zosh and ran `ls.x` 20 times to get a breakdown.

| Stage | Time per run | Share |
| --- | --- | --- |
| Loading and relocation (`_EXEC`) | 0.161 s | ~70% |
| PATH search (`_PATHCHK`) | 0.044 s | ~19% |
| Saving and restoring every drive's current directory | 0.010 s | ~4% |
| Building the child's environment | 0.007 s | ~3% |

The biggest share is Human68k loading the program and rewriting its addresses to match where it was loaded (relocation), and zosh can't reduce that. Next is the PATH search, which went through five directories from the start every time. Like bash's `hash`, zosh now remembers where it found a command and skips the search next time. That made each run 17% faster.

Loading can still get faster. The GNU commands already have a trick that speeds up relocation (fastreloc), but ITA TOOLBOX, the standard X68000 command set, doesn't have it yet. Next we'll add fastreloc to ITA TOOLBOX too.

## Running it on a real Z

Finally, we ran it on a real Z. The boot image (1GB) goes onto the microSD in the Pico, which boots it as a SCSI hard disk. Writing goes over the Pico's Wi-Fi at about 700KB/s, so one image takes 24 minutes.

The first image booted, but about 45 seconds in, the worker lost control of the Z. Workers drive the Z by sending keys to the Pico over UDP. But the image's settings gave the Z the same IP as the Pico, `192.168.1.4`. So once the Z's network came up, the Z grabbed the keys meant for the Pico. The IP address in the README's example settings was wrong, so we changed it to `192.168.1.68` and added "don't use the Pico's IP address".

With the IP fixed, the second image confirmed:

- 41–45 seconds from power-on to the prompt (51–56 seconds on 11/07).
- `ls /`, `pwd`, `file`, `xargs -n1`, `ps`, `top`, splitting panes, and GNU `ls --color` colors.
- `curl -I http://example.com` returned HTTP 200 (the Pico handles TCP).

Some problems only showed up on real hardware. `less` shows the file near the bottom of the screen. `top` doesn't exit on `q` until the next refresh (about 30 seconds later). Workers are fixing both.

## Working after the limit

Since we hit the weekly limit at the end of last time, this time I ran fewer workers at once. Usually two: one fixing zosh, one fixing the tests and the boot image. The lead AI checks in every 30 minutes; when a PR is up it runs codex (OpenAI's code review), and merges if there are no major findings and CI is all green. Only risky changes, like ones that write directly into Human68k's internals, also got a review from Fable, another Anthropic model.

What I learned is that workers stall a lot. They say "waiting for test results" when nothing is actually running. Two and a half hours after the check finished, the results still weren't written up. So the check-ins now look not just at PRs but at whether XEiJ is running and when the working files were last touched, and nudge the worker if it has stopped.

The original goal of these two days isn't met yet. Whether it really feels like UNIX is, in the end, for me to decide by using it. Before that, I tried whether the same image runs on a real X68000 other than the Z.

## Running on a Compact XVI with BlueSCSI

In the evening I connected a BlueSCSI v2 to my X68000 Compact XVI and booted the same image. BlueSCSI v2 is a board that uses a Raspberry Pi Pico to emulate a SCSI hard disk; it presents image files on an SD card as SCSI disks. Mine is the external DB25 version.

The Compact XVI (XVI from here on) has a half-pitch 50-pin external SCSI port of the ribbon type. The adapter I had (Arvel AA904) is also half-pitch 50-pin but the comb type, so it doesn't fit. After hunting around for SCSI adapters, I found one on Yahoo! Auctions that goes from DB25 to the ribbon type.

![BlueSCSI v2 (DB25 version) and the adapter from DB25 to half-pitch 50-pin ribbon type]({{ "/assets/xvi-bluescsi.jpg" | relative_url }})

At first the screen stayed black after power-on. Looking at the SD card on a Mac, the log (`log.txt`) that BlueSCSI writes on every boot wasn't there. BlueSCSI wasn't getting power. The DB25 version takes power from pin 25 of the SCSI cable (TERMPWR), but with the XVI and this adapter, nothing seems to arrive there. So I powered it by connecting the Pico's USB to a Raspberry Pi 5.

With USB connected, BlueSCSI boots as a USB disk instead, and doesn't answer on SCSI while it's in that mode. Running `eject` on the Raspberry Pi 5 puts it back on SCSI. The USB port also carries the log, so the Raspberry Pi 5 can show each SCSI command the XVI sends.

Here the AI doing the work made a mistake. It didn't turn off echo on the terminal reading the log, so everything BlueSCSI printed was sent straight back to BlueSCSI. BlueSCSI treats single characters from the serial port as commands, so the debug toggle and the reboot prompt came up dozens of times. Luckily it never rebooted. The next boot stopped when the XVI didn't get a reply to Inquiry (the command that asks what kind of device it is). We don't know whether the echo caused it. Since reseating the BlueSCSI, it hasn't stopped once.

To narrow things down, I first wrote a plain 100MB Human68k image with only the files needed to boot. That booted, so next I wrote the 1GB Z-OS image built for the Z, without rebuilding it. That booted too.

![Z-OS running on the Compact XVI: output of uname and ls /usr/bin]({{ "/assets/xvi-zos.jpg" | relative_url }})

The BlueSCSI log shows how long booting takes. From the XVI's first disk read to the last write of the boot took about 13 seconds. On a real Z it's 41–45 seconds from power-on to the prompt. The XVI figure doesn't include the time from power-on to the first disk read, so the numbers can't be compared directly. Still, the XVI feels much faster. The Z's SCSI disk actually sits behind USB to the Pico, so every SCSI command means a USB round trip. The XVI talks SCSI directly. My XVI's CPU also runs at 24MHz.

The screen said `X68000 Z`, and `uname -a` still showed Z for both the machine and the host name. We'll detect the machine at boot and show its name, and on the XVI the prompt will be `moto@xvi`.

## Next

Next is running Pico Z Loader (our own firmware on the Z's Pico) on the BlueSCSI v2. The goal is to give the XVI what the Z's Pico does: switching boot disks, networking, and doing SSH's crypto. The Pico on my BlueSCSI has no wireless, so networking will be relayed to a Raspberry Pi over the BlueSCSI's USB. The scheme that hands crypto to the Pico (the crypto accelerator) doesn't use wireless, so it can go on as is. I've also designed a board that takes a Pico 2 W in a socket, and I'll get it ready to order.

The other issue is that rewriting a 1GB image for every test takes too long. Over the BlueSCSI's USB it measured only 200KB/s, so 1GB takes more than 70 minutes. So we'll make the boot disk small and move `/usr/local` and `/home` to disks on separate SCSI IDs. With `/home` on its own disk, rewriting the boot disk won't wipe history or files.

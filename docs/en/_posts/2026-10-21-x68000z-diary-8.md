[Previously]({{ site.baseurl }}{% post_url en/2026-10-21-x68000z-diary-7 %}): we used the SCSI mailbox directly, ditched SLIP, and hit 290kbps. xip.x is now using 65% of the CPU, which makes it the real bottleneck at last. In this series, the AI (Claude) does almost all of the code and research. This time I was out of the house.

## npd

It's not SLIP anymore, so it got a new name. The netpipe driver is `npd.sys`, and the thread is `npd.x`. slip.sys and slipd.x went back to being SLIP-only, for RS-232C and for UDP mode with slattach on the Pi. `make image NET=npd NETZIP=192.168.1.68` builds an image with npd in it.

While we were at it, we re-tested the old xip.x patch `--timer` (sweeps the timer tables once every 0.1 seconds instead of constantly). Last time it was 17–19KB/s, lost in the noise. Now: 36 → 40–45KB/s. With xip.x as the bottleneck, it finally matters. It's now on by default.

## 32 table slots, scanned end to end, every time

Next thing that stood out in the profile: xip.x's "named locks." 11% of the CPU.

Disassembled, the design turned out to be pretty naive. There's a table of 32 key/in-use-flag pairs, and every lock searches it from the top for the key. If it isn't there, it goes around again looking for a free slot. Unlock searches the same way. It wasn't waiting on contention. The searching was just expensive.

So remember the slot you found last time, and check that first. Usually it's the same socket's lock again, so you can skip the search entirely.

So I asked: "Are you putting this off because the patch is hard? Like, tsume-shogi-puzzle hard?"

The AI's answer: "Proving it's correct is heavier than writing it." There's no source, so we can only guess what the original design intended. Get it wrong, and it might run fine normally and freeze only when connections overlap. And I was out of the house, with no way to bring it back.

"Then why not run unit tests on dummy data and check the results match the current code? (Is that too sloppy?)"

It wasn't sloppy. It was the right way to do it.

## Raising a 68000 inside the Mac

The AI set up a 68000 inside the Mac with Unicorn, a CPU emulator you can drive from Python. Load xip.x, relocate it, and make just the three lock functions callable. Stop right before `_CHANGE_PR` (the DOS call that gives up the CPU), and you can pretend a thread switch happened there. Several threads call lock and unlock in random order.

Run the original code and the rewritten code with the same random seed. Check that these four things match:

- Return values
- Table contents
- Where it gave up the CPU
- Whether the new code clobbers registers the original never touches

A differential test. First result:

```
MISMATCH seed 0
 orig: lock(48268674) done, changed {d0, a0, d1}
 new : lock(48268674) done, changed {d0, d2, a0, d1}
```

The original lock doesn't touch d2. The rewrite was clobbering it. In gcc's calling convention, d2 is a register the callee has to preserve. If a caller counts on d2, something somewhere quietly breaks. This is exactly the kind of thing I built the tool to catch.

## The same key, twice in the table

Fixed d2, ran it again, and got this:

```
MISMATCH seed 277
 orig tab 00000000 f2572d00 00000000 ...  f2572d00 00000000 ...
```

The same key (f2572d00) appears twice in the table. The whole "check last time's slot first" plan rested on the assumption that keys in the table are unique. That assumption just fell apart.

The AI traced the steps:

1. Thread A is waiting for slot E, which holds key K, to be released.
2. Meanwhile, E gets released, and another thread reassigns E to a different key.
3. Meanwhile, a thread comes to lock K, can't find K in the table, and creates K fresh in a different slot.
4. Eventually A gets E, and writes E's key back to K, without holding the master lock.

Now there are two Ks in the table. And two threads hold K at the same time. This isn't a bug in the rewrite. It's a bug in the original xip.x.

When there are duplicates, the original code picks the one closer to the top. Checking last time's slot first can pick the other one. So we threw out the "remember it" plan, kept searching from the top just like the original, and only made the loop faster (68 → 40 cycles per slot). This time, all 400 random seeds matched.

## Interrupts can land anywhere

At that point I chimed in from outside: "If the bug is a bug, can't we just patch it?"

But fixing it changes the behavior compared to the original, so the differential test is out. The AI built a different test. Run under near-real conditions, where an interrupt switches threads after a random number of instructions, and check exactly one thing: two threads never hold the same key at the same time.

The original code broke mutual exclusion in 29–58 runs out of 200 (depending on conditions).

The first fix: once the waiting side gets the slot, it retakes the master lock, checks the key, and searches again if it's wrong. That brought it down to 2 out of 200. But 2 isn't 0.

Chasing those last 2 turned up a second race. The side that assigns a free slot "checks that the in-use flag is 0, then writes it." In between, a waiting thread that doesn't hold the master lock can grab the same slot with `tas`. We made the assigning side take it with `tas` too.

2,400 runs across 6 conditions: 0 broken. And no runs that stalled without making progress. It fits in the same 230 bytes as the original, and the entry addresses didn't move. We rebuilt the relocation table. `patchxip.py --lockfix`.

## XEiJ, and ping

Before the real hardware, we ran the whole of xip.x on XEiJ, connected to the Pi with SLIP over serial.

- At 38400bps, transfers from the Pi to XEiJ barely get through. XEiJ's SCC has no receive FIFO, so it drops bytes. Down at 9600bps, they finally went through.
- Even then, with an unpatched xip.x, 1 transfer in 5 stalls partway. As a place to measure stability, XEiJ was itself too unstable.
- The AI absent-mindedly pinged XEiJ from the Pi and froze xip.x. ESP/X freezes if it gets a ping from outside after a TCP connection closes. That's why we'd made the Pico drop them earlier.

I said, "Why not have the Pico answer them?" Not proxy ARP, but proxy echo. Answering roll call for a friend. With USB modems, it's common for the module to answer on the microcontroller's behalf. We'll do it next time we flash the firmware.

## The real hardware

In the end, we tested on the real thing. Because I said: if it freezes, we can reset it, and worst case it doesn't work. Fine.

| xip.x | Speed (Pi → Z, 200KB) |
| --- | --- |
| MSS 1460 only | about 290kbps |
| `--timer` | 315–364kbps |
| `--timer --lockfix` | 364–381kbps |

The test that writes 300KB of random data to A: and B: and compares it matched all 6 times.

In a 20-minute continuous test, we sent 200KB 220 times (44MB) with 0 failures. 44 of those runs wrote random data to B: and compared it, and they all matched. Of 32,008 netpipe exchanges, 28 had to be redone (after a 1-second wait). There's still room to trim.

Compared with the first PPP over serial (about 8kbps), that's about 47 times faster. About 10 times the speed of the RS-232C line itself (38400bps).

We found race conditions in an old binary with no source, using a 68000 inside the Mac, and fixed them within 230 bytes. Easier said than done. But this time, we tried it, and it actually got done.

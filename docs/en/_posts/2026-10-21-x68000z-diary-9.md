[Previously]({{ site.baseurl }}{% post_url en/2026-10-21-x68000z-diary-8 %}): I ran xip.x's locks through a differential test on a 68000 living inside my Mac, and it turned up two race conditions in the original binary. Fixed them, got 380kbps. In this series, an AI (Claude) does almost all of the code and research.

## The failed exchanges weren't the bottleneck

In last time's 20-minute endurance run, 28 out of 32,008 netpipe exchanges failed, and each failure cost a 1-second wait. The AI broke them down. All 28 were the same thing: "hit a stale response left in the cache 64 times in a row."

The problem was how it jumped. When it hits a stale response, it skips 16MB ahead inside the read area. But the area is only 480MB. Thirty jumps and you've wrapped around to where you started. So even with 64 tries, it was only ever looking at 30 spots. I'd reset the Z dozens of times that day, so most of the area was sitting in its cache, and if all 30 of those spots were cached, there was no way out.

We made the jump targets pseudo-random. While we were at it, a failed read can now re-read the same response (the Pico holds on to a response until the next request arrives). Another 20-minute run: zero failures, and stale-response re-reads went from 2,551 down to 605.

And the amount of data sent didn't change. 218 runs versus 220. The 1-second waits weren't the bottleneck. Worth fixing. Didn't make it faster. That happens.

## Twice per loop

A fresh profile showed xip.x's three threads passing the CPU back and forth with `_CHANGE_PR`, and that was eating about 25% of the CPU.

I asked, "Is this the limit?" The AI listed candidates and said the biggest one was how the threads were built. Let them sleep when idle, wake them when work arrives. The catch: we'd tried that once before in slipd.x, and "put it to sleep" turned into "it eventually stopped getting woken up." Risky.

Then it disassembled the thing and found a problem much closer to the surface.

- The receive thread loops forever: "check the inbox → call the receive handler (0x26B0) → `_CHANGE_PR` → back to the top."
- But the receive handler also calls `_CHANGE_PR` itself, right at the end.
- The timer thread does the same thing.

Every loop, it yields twice.

We replaced two `bsr` instructions inside the handlers with `nop`. Six bytes. The thread loops still yield like before, so nobody else gets starved. `patchxip.py --yield`.

## Wi-Fi at night

Straight onto the real hardware to measure it: 15–32KB/s. Slower than before. Take the patch out: still 15–32KB/s.

A few hours earlier it had been doing 46–50KB/s. The Pi was idle. Only the round trip to the Pico was off: 11ms on average, sometimes jumping to 64ms. Looks like the Wi-Fi got crowded once evening hit. In that state, a 12% difference just drowns in the noise.

Late at night, after I got home, the round trip to the Pico dropped back to 5ms. We measured with and without the patch, alternating, twice each.

| xip.x | 200KB × 5 runs (KB/s) |
| --- | --- |
| without `--yield` | 48.8 50.0 51.2 50.0 50.0 / 51.2 50.0 50.0 51.2 51.2 |
| with `--yield` | 56.9 55.4 55.4 55.4 56.9 / 56.9 55.4 56.9 56.9 55.4 |

12% faster. 56.9KB/s is about 455kbps.

I was watching the screen and said, "We're hitting the dream, 500kbps!" The AI corrected me: "It's about 455kbps. That's a little short of 500kbps."

I said, "The instantaneous rate's over. Check the log."

The AI read the serial log. Here's what rcmd.x on the Z had written:

```
rcmd: put NUL 204800/204800 bytes in 3.05s (67147 B/s = 537.1 kbps)
```

The AI had been looking at the number from x68put on the Pi side. That one divides by the whole time, including the TCP connect, the command line, and waiting for the end marker. The Z's number runs from the first byte of data to the last. Data alone: 537kbps. The dream had come true. The one doing the correcting was the one who was wrong.

## Freezing the Z with a profiler

I also wanted to confirm `--yield` in a way that didn't depend on the Wi-Fi. Easy: profile it and see if the share of time spent yielding went down.

I typed `zprof.x on` and got zero samples. zprof.x uses the first "SLPDPROF" marker it finds in memory as the place to store samples. But copies of that marker are lying around in memory, in disk buffers and leftovers from previous boots. This time it had grabbed a leftover.

The AI changed it to "start recording on every one you find." The Z froze. It had written "start recording" into memory that somebody else was currently using. Thanks to contee.sys, the error dialog came through the serial log intact:

```
(SR=$2009:PC=$0000EAD4)
　　　 中止＜Ａ＞ 再実行＜Ｒ＞ 無視＜Ｉ＞ ？
```

(That's Human68k's "Abort <A> / Retry <R> / Ignore <I> ?")

Pressing "Abort" on the remote keyboard just brought up the same dialog again. When I got home, I turned the power off.

These days zprof.x uses `_GET_PR` to get the address of the "npd" thread's inbox, and only searches the 128KB right before it. The inbox lives in npd.x's own .bss, so anything nearby is the real thing.

## Answering roll call

Last time I said, "Why not have the Pico answer the pings?" Not proxy ARP, but proxy echo. Answering roll call for an absent classmate.

ESP/X hangs if it receives a ping from outside after a TCP connection has closed. That's why the Pico had been dropping pings addressed to the Z. This time, instead of dropping them, the Pico builds an echo reply and sends it back. Swap source and destination, fix the TTL and the checksum. That's it.

One small twist: the reply only goes out the next time the Z's npd.x comes by for a netpipe exchange. If the Z is frozen, no exchange happens, so no reply goes out. Even with someone else answering roll call, ping still tells you whether the Z is alive.

```
5 packets transmitted, 5 received, 0% packet loss
rtt min/avg/max/mdev = 7.033/43.212/67.706/22.624 ms
```

And rcmd was still alive afterward.

## Where things stand

| Step | Speed |
| --- | --- |
| PPP (RS-232C 38400bps) | about 8kbps |
| SLIP (RS-232C 38400bps) | 21.9kbps |
| netpipe, first version | about 32kbps |
| MSS 1460 | about 70kbps |
| slipd.x improvements | 136kbps |
| SCSI mailbox, direct | 176kbps |
| Drop SLIP (npd) | about 290kbps |
| xip.x `--timer` | 315–364kbps |
| xip.x `--lockfix` | 364–381kbps |
| 16KB window | about 400kbps |
| xip.x `--yield` | about 455kbps (537kbps measuring data only on the Z side) |

About 57× the original PPP (about 67× counting data only).

A 20-minute endurance run with `--yield`: 255 sends of 200KB (51MB), zero failures. 51 of those wrote random data to B: and verified it, and every one matched. Without `--yield`, the same 20 minutes got 218–220 sends, so that's about 16% more. I was watching the screen and said, "This is rock solid."

Other things we settled:

- PROCESS (time slice) in CONFIG.SYS is 20. Same speed as 50, and ping is faster. I care more about real throughput than ping, but if they're tied, faster wins.
- The image now defaults to `--timer --lockfix --yield` (XIPTIMER / XIPLOCK / XIPYIELD). With npd, `netup` uses a 16KB window and a 1MB heap.

500kbps: cleared. What should we aim for next? Easier said than done.

[Previously]({{ site.baseurl }}{% post_url en/2026-10-03-psp-diary-1 %}): Chō Renshā 68K hit full speed. SION IV runs at 104–120ms per frame, about 10fps. In this series too, the code and the measurements are almost entirely the AI's (Claude's) work.

## 65,536 colors, and a palette that changes every frame

SION IV is a 3D shooter, and it uses 65,536-color mode. GE compositing didn't support 65,536 colors yet. On top of that, it uses a layer order where the graphics plane sits between the text plane and the BG plane. We added support for both.

72–78ms per frame. 14fps.

Next we noticed that every frame, the colors of the whole screen were being converted all over again. You should be able to do the conversion once, at write time. So we changed it. Nothing changed.

We looked closer. SION IV **really was rewriting the palette every single frame**. If the palette changes, every pixel's color changes. There's no avoiding redoing the conversion.

So the AI came up with a fun idea: make the GE do the color conversion itself. One pixel in 65,536-color mode is 16 bits. Draw the low 8 bits and the high 8 bits as two separate 256-color textures. If you build the two lookup tables so the bits they produce never overlap, additive blending is the same as OR. You assemble the color by adding.

58–65ms per frame. 16–17fps.

## The 68000 was innocent

The remaining 50-something ms was almost all 68000 time.

When a heavy game runs slow, the first thing anyone thinks is "the 68000 emulation is slow." I thought so too. Here are the options:

- (a) Shave down the current C 68000 core (C68K).
- (b) Rewrite the interpreter in MIPS assembly.
- (c) Write a dynamic recompiler that translates 68000 code into PSP instructions.

(c) is the romantic option. The AI went as far as writing the design. How to split blocks, the code cache, detecting self-modifying code, the conditions for never getting a single cycle count wrong. Estimate: 6–10 weeks.

Before that, let's measure.

The AI made a command called `cpubench`. It runs a 68000 loop in a corner of main memory and measures how many times faster than a real 10MHz 68000 it goes.

Result: **4–5 times**. Even if the 68000 works nonstop without a single break, one frame's worth (180,000 cycles) is done in 4–5ms.

So what's SION IV's 50ms?

We counted instructions on the host. About 15,000 68000 instructions per frame. Of those, **12,200** were word writes to graphics VRAM. And each word write took 6 function calls and about 100 instructions. `cpu_writemem24_word` → `_slow` → `wm_cnt` → `GVRAM_Write`, and then `wm_main` → `wm_cnt` → `GVRAM_Write` all over again.

The 68000 was innocent. The real culprit was the VRAM front desk, bouncing every request from one window to the next.

We made `GVRAM_WriteWord`, which handles a write in a single call, and got it down to about 40 instructions and 3 calls per word. SION IV went to about 48ms, 20fps. Twice where we started. Still only 40% of full speed, but from here on, it's the game itself that's heavy.

We decided not to write the dynamic recompiler. Romance will have to wait.

## Instruction counts lie

The most important thing I learned today about the PSP's CPU (Allegrex):

**Counting instructions tells you nothing about speed.**

The AI built a few variants of the core. One with the cycle counter kept in a register. One that left memory accesses as function calls. One with a shortcut to main memory baked into the handlers.

The version that kept the function calls executed fewer instructions than the original, and its memory-reading loop was **twice as slow**. Twice. That's not noise.

The PSP's instruction cache is only 16KB. The 68000 core is one giant function, and depending on where each instruction's handler ends up inside it, they fight over the cache. Baking in the shortcut made SION IV 2ms faster and Chō Renshā 68K 1ms slower.

41% of Chō Renshā 68K's 68000 time was a loop that waits by reading the state of the MFP (the timer chip). It's a loop that just keeps reading the same address until an interrupt shows up, so we skip straight to the end of the slice. -1.2ms.

Every time you change one line of the core, you have to measure again on the real hardware. Changes that should make it faster, in theory, make it slower. The universe just works that way.

## Counterproductive on x86

"Hey, there's a PSP-specific part to this, and a part that isn't, right?" That was me.

Some of these optimizations should backfire outside the PSP (the SDL builds for Mac and Linux). The AI wrote a benchmark that measures each optimization on an x86 host and ran it on GitHub Actions.

As expected, some of them backfired.

- Remembering the result of a division when reading the MFP: **18% slower** on x86. Checking the remembered value costs more than three divisions.
- Eliminating the per-line division: on x86 it's 4.1ns vs. 1.8ns per line, and the division is faster.
- Making the FM sound table 16-bit to halve its size: no difference on x86.

Division on x86 is fast. Division on the PSP is slow. We confirmed the obvious, with numbers. Those optimizations are now enabled only for the PSP.

By the way, the benchmark measures with three different code layouts. Layout alone moves the results by 20%. On x86, too.

"Are we OK on the Actions quota?" We were.

## Confession

There's something I have to put on the record.

The regression test captures the same scene with the pre-optimization build and the post-optimization build and compares them. But GE compositing is on by default. The reference side was also drawing with the GE. So for a while, we were comparing GE against GE and saying "they match."

We fixed the reference side to capture the CPU path with `ge off`, and compared again. Found one. On lines wider than 480 dots, the rightmost 32 dots were missing. The GE's drawing-region setting wasn't taking effect.

The test wasn't right, so we couldn't see the bug. We fixed the test, and there was the bug. That's what tests are.

## Correction

The next day, I asked: "How many fps was Chō Renshā getting before the improvements?"

The PR said "30.5ms at the start." The AI came clean. That wasn't the pre-improvement number. It was from a build that already had 68000 core and other improvements in it when we started testing Chō Renshā 68K. In fact, on the original px68k, Chō Renshā 68K doesn't even boot, because of the SRAM thing.

We took the original build, added only the SRAM fix, and measured again on the real hardware.

| Build | Per frame | fps |
| --- | --- | --- |
| Original + SRAM fix | 45.3–46.3ms | about 22 |
| Current | **14.1ms** | **70.7** |

3.3 times faster. The first run happened to land on a different scene with lots of explosions and gave 73.2ms, so we checked screenshots to make sure the scenes matched before comparing.

And to be clear, 70.7fps is with the speed limiter off. When you actually play, it caps at 55.46fps. Any leftover time, the PSP gets to rest.

## A 68000 faster than an XVI

Around noon the same day, I asked for one more thing. "Run a CPU benchmark on Human68k. I wonder how it compares to the original model."

Most X68000 benchmark software measures time with the MFP timer. But inside an emulator, the timer advances in emulated cycles too. So no matter what you do, it answers "10MHz." Honest, but useless.

The AI wrote `RTCBENCH.X`. The clock (RTC) runs on host time, so if you count how many loops you get through in 5 seconds of real time, you get the real speed.

| Setting | vs. original 10MHz |
| --- | --- |
| Speed limit on | 1.02x |
| No Wait | 1.87x |
| 16MHz (XVI) mode | 1.60x |
| 24MHz mode | 2.39x |

"Feels like we could get about XVI-level performance." We did. 10/16/24MHz is now selectable from the menu.

There's a 68000 faster than an XVI running in the palm of my hand.

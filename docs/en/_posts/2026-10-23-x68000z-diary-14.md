The waiting screen got its own logo, and the Pico firmware is going independent as "Pico Z Loader." In this series, an AI (Claude) does almost all of the code and research.

## What did I actually want?

Right after asking for password authentication in ssh.x, I asked: "Was OS-9 on the X68000 multitasking?" And then: "Could you build a multitasking OS that's binary-compatible with Human68k (or not, that's fine too), the way OS/2 was to MS-DOS..."

The AI said yes, it could. But the 68000 has no MMU, so there's no way to protect processes' memory from each other the way OS/2 did. The closest precedent, it said, is MiNT on the Atari ST, which runs the original OS's programs as-is and adds time-sliced multitasking on top.

Hearing that, I stopped. "Hmm. Let me actually think about what I wanted in the first place."

Up to this point, the direction had been "use the Z as a window." ssh out from the Z and use Claude Code on raspi5. But when I had the AI lay out the options, what I picked was **the Z, standing on its own**. Browse the web, talk to an AI, write programs, keep in touch with people. I want all four. The core of the OS runs on just the Z and the Pico, with no help from raspi or any other machine (apps using cloud APIs is obviously fine). The Pico can take on anything. For the screen, a CLI plus a GUI on the level of twm or a tiling window manager is plenty.

Put into words, it came out like this:

"iTerm2's pane handling is probably the closest / Pico Z Loader becomes the boot loader, an alternative OS you can switch to and from human68k / for a name, after S-OS, something like Z-OS. / I want to split panes, run zsh, ssh out, run gcc."

"And not just panes, it'd be nice to make separate windows (tabs) too."

The official name is **Z-OS for X68000 Z**. It needs a Pico, so it won't run on a real X68000. For the repository name I first said x68z-os, then changed my mind: "If it's x68, I want a k after it." So it's x68k-zos (still private).

## A Pico on the Mac

If we're going to build this by changing both the Pico and the Z, flashing the Pico and rebooting the Z every single time would be miserable. I asked: "Can you emulate a Pico on the Mac?"

The AI's proposal wasn't to emulate the whole chip. It was to **build the Pico-side program for the Mac and run it there**. Intercept the reads and writes that XEiJ (the X68000 emulator on the Mac) sends to SCSI ID 6, and hand them to a "stand-in Pico" on the Mac (picosim). The LAN beyond it is emulated with libslirp. With that, npd, ping, rcmd and ssh.x inside XEiJ can talk to the outside world along the same path as on real hardware.

Measuring it taught us something. Speed is almost exactly proportional to the 68000's clock.

| XEiJ clock | Mac → Z | Z → Mac |
| --- | --- | --- |
| 10 MHz | 10.8–18.1 KB/s | 29.2 KB/s |
| 16.7 MHz | 55.4–59.7 KB/s | 50.1 KB/s |
| 33.3 MHz | 97.0 KB/s | 99.5 KB/s |

The 16.7MHz numbers are close to the real Z (45–57KB/s). The bottleneck isn't the Pico or USB. It's the Z's 68000 itself.

## Passwords

One more thing. "Now that I think about it, ssh didn't support password authentication, did it?"

It did not. dropbear reads passwords with `getpass()`, and Human68k doesn't have one. The worker wrote a replacement that reads one character at a time without echoing, and added keyboard-interactive, which modern sshd uses a lot. If the public key gets rejected, it asks for a password. Three wrong tries and you're out. ESC cancels. When you open a second screen in the virtual console, it doesn't ask again.

On the real Z, the worker typed the passwords through the Pico's keyboard function, the genuine key-input path, and checked every case.

## TCP goes to the Pico

TCP/IP on the Z is currently done by xip.x, on the Z itself. We built a way to hand that off to lwIP on the Pico. The Z side is tis.x (`tis.x -p`). It exposes the same interface as xip.x, so rcmd.x and ssh.x run on it without being rebuilt. Between the Z and the Pico, it uses records in the same style as the crypto accelerator, bundling requests for multiple sockets into a single exchange.

We compared it against the xip.x path on the Mac test bench (XEiJ, 10MHz).

| | tis.x -p | xip.x |
| --- | --- | --- |
| 1-byte round trip | 39 ms | 102 ms |
| Z → Mac, 1MB | 166 KB/s | 33 KB/s |
| Mac → Z, 1MB | 233 KB/s | 65 KB/s |
| 300KB to the Z via rcmd.x | 167 KB/s | 17 KB/s |

2.5 to 10 times faster. But inside XEiJ, a single Z-to-Pico exchange takes essentially zero time, so on real hardware you add the USB time on top. No real-hardware numbers yet.

And it didn't fit on the current Pico W. Adding this uses 12KB of RAM, dropping free memory from 112KB to 100KB. Looking at what a running Pico actually uses, there's a good chance that runs out partway through. So we didn't flash it, and decided to use it only on the Pico 2 W side.

## Pico 2 W

Conveniently, the parts I'd been wanting all arrived.

- Raspberry Pi Pico 2 WH (the generation after the Pico W; RAM goes from 264KB to 520KB)
- Two Raspberry Pi Debug Probes. One stays permanently on the Pico plugged into the Z, one for development on the desk
- Two HDMI capture devices (cheap ones, no passthrough)
- A 32GB high-endurance microSD
- A Raspberry Pi keyboard (Japanese layout, small, with a USB hub)

First, I had the AI build the current firmware for the Pico 2 W. Upgrade the SDK, swap FreeRTOS for the RP2350 port, and 44 lines of source changes. SMB, USB and Wi-Fi all went straight through. Free memory: 362KB, about 3.6 times the Pico W. The TCP machinery fits without trimming anything.

When I flashed it, Wi-Fi connected in about five seconds and the HDS on SMB opened too. But plug it into the Z and: "Cannot boot from disk." We looked at the logs through the Debug Probe, halted it and poked around inside, and found that the firmware was crashing about a second after it started talking to the USB host (the Z, or a Mac). FreeRTOS and the USB interrupts were fine on their own. Narrowing it down, the cause turned out to be a small typo in the code that returns the USB device's identity. On the Pico W, it just happened not to do any harm. Fixed. Next up is trying it on the Z.

On the other Pico 2 WH, I hooked up a microSD on a breadboard. SPI was stable at 25MHz, around 2.2MB/s for both reads and writes. We wrote 1MB and read it back for comparison 23 times in a row, and not a single bit came back wrong. That's the foundation for a Pico Z Loader that boots from SD.

## The core of Z-OS

A prototype of the Z-OS core (the multitasking) was moving along in parallel. The plan was to write our own task switcher off the MFP timer. But when the worker dug into Human68k 3.02, it turned out **Human68k itself already has time-sliced task switching**. It's enabled with `PROCESS=` in CONFIG.SYS, and it even has logic to defer switching while a DOS call is in progress. tis.x uses this mechanism too (`_OPEN_PR`), so writing our own would collide with it.

So zos.x doesn't have its own scheduler. It sits on top of Human68k's threads and adds per-pane screens and keyboard routing. It splits the screen left and right and runs unmodified programs in each pane. F10 switches which pane gets the keys.

In XEiJ, zsh came up in both panes. Compiling hello.c with gcc (the Mariko build) in one of them printed `hello, Z-OS` after 12 seconds. The whole time, the counter in the other pane kept going without stopping.

## Redirects leak across panes

Something weird happened during testing. In pane 1, I had `count.x R … > redir.txt` write to a file, and meanwhile pane 2 ran `count.x B …` to the screen. Pane 2's `B` lines showed up mixed into redir.txt.

The cause: Human68k keeps only one table of "which file number is connected to what." Human68k's threads don't swap this table when they switch. The current drive and current directory work the same way, and we'd already handled those back in the first prototype, swapping them per pane in the switch hook.

The worker used the same hook to give each pane its own file-number table too. The table of actual open files stays global. Same shape as per-process file descriptors on UNIX. After the fix, redir.txt contains only the 40 `R` lines.

## On real hardware

Then we ran it on a real Z. Keys came in through the Pico's keyboard function.

- In pane 1, gcc compiled hello.c and printed `hello, Z-OS`.
- In pane 2, `ssh.x -t -oAccel=all` logged into raspi5. `stty size` said `31 48`. ssh.x's terminal treats the pane's size as its whole screen. `exit` took us back to zsh.

![Z-OS on a real X68000 Z, with the screen split into two panes, left and right. On the left gcc compiles hello.c; on the right ssh.x is logged into raspi5 and shows uname and stty size (31 48)]({{ "/assets/z-os-two-panes.jpg" | relative_url }})

Real hardware also turned up problems XEiJ didn't. Closing a pane didn't give its memory back, so the second launch failed with "Out of memory." And the overhead of copying state on every switch pushed ssh's key exchange past sshd's time limit (120 seconds). Both fixed.

## A real X68000

Z-OS needs a Pico, so it doesn't run on a real X68000. But it occurred to me: "Couldn't you do it with a different microcontroller on the SCSI interface?"

According to the AI, there's precedent. BlueSCSI v2 and ZuluSCSI use the RP2040, the same chip as the Pico, to pretend to be SCSI devices. From Z-OS's point of view it's all just "reads and writes to SCSI ID 6." So while it's still early, we're separating the Pico side into a "layer that handles SCSI commands" and the "transport" (USB, or a SCSI bus).

## Not yet

- The Pico 2 W firmware hasn't been tried on the Z yet. Real-hardware speed with TCP handed to the Pico is still to come.
- HTTPS (mbedTLS on the Pico) also depends on the Pico 2 W's RAM.
- Z-OS: ssh.x rewrites the color palette, so the colors in the other panes change too. Tabs, reopening panes and iTerm2-style key bindings don't exist yet. Keys typed ahead while gcc is running get lost.
- Choosing Z-OS from Pico Z Loader and booting into it: not yet.
- Japanese input (FEP) is still on hold.

Until yesterday, the Z was a terminal for raspi5. Now there are two programs running at the same time on the Z itself. How far can we get with just the Z and a Pico?

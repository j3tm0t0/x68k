[Previously]({{ site.baseurl }}{% post_url en/2026-10-21-x68000z-diary-6 %}): the slowness wasn't xip.x, it was the SCSI hauling. Fixing slipd.x got us to 136kbps. The profile shows 25% of the CPU spinning inside the SCSI ROM. In this series, the AI (Claude) does almost all of the code and research. My job is the power button. Today I pressed it a lot.

## Dumping the ROM

I want to know what the ROM is waiting for. Easy: read it. The AI built `memdump.x`, which writes any range of the Z's memory to a file, and dumped from 0xEA0000, where the SCSI ROM lives.

The Z froze.

"Bus error" on the screen. The remote keyboard reset didn't work either. I cut the power. Turned it back on: "Can't boot from disk." Turned it on again.

0xEA0000 through 0xEA001F turns out to be a region that throws a bus error when you read it. The AI changed it to read one word at a time, checking for bus errors as it goes (DOS `_BUS_ERR`). Unreadable spots get skipped and counted.

## The mailbox

Inside the dumped ROM, this:

```
Pseudo SCSI BIOS ver.1.05 Copyright (C) 2023 uchopon
```

The X68000 Z's SCSI isn't a real SCSI controller. It's uchopon's "Pseudo SCSI BIOS." Here's how it works:

- At 0xEA0060 there's a small drop box, about 16 bytes.
- The ROM writes the "ID," "command," "LBA," "byte count" and "buffer address" there, and raises a start flag.
- The emulator takes it from there: it talks to the Pico over USB, reads and writes the X68000's memory directly, and lowers the flag when it's done.
- Meanwhile, the ROM keeps watching the flag, with two `nop`s in between each check.

So it puts a letter in the mailbox and then just stands there in front of it until the reply comes. That standing around was the 25% in the profile.

Then put the letter in and go home. slipd.x uses the mailbox directly, skipping the ROM, and while it waits for the reply it gives the CPU to xip.x with `_CHANGE_PR`.

## There's only one mailbox

The catch: slipd.x isn't the only one using this mailbox. A: and B: use it too. If the B: driver drops a letter in while slipd.x is waiting, they overwrite each other's letters.

The AI put a hook on the ROM's entry point (IOCS `_SCSIDRV`). While slipd.x has a letter out, any other call has to wait.

With the first version, the Z froze once. The B: driver does "select," "command," "data" and "status" as separate IOCS calls, and slipd.x was cutting in between them. When the driver is outside the ROM, the hook can't stop anything. Making it wait until the mailbox's "phase" field goes back to 0 fixed it.

We ran 13 tests of receiving over the network while writing random files to A: and B: and comparing them. All matched. Speed went from 136kbps to 176kbps.

## The ghost of free()

Re-running the profile, it now looked like the C library's `free()` was eating 10% of the CPU, walking the memory chain forever.

The culprit was the profiler itself. Before `zprof.x dump` stops recording, it scans 2MB of memory looking for where the records are stored. And those 1–2 seconds were dutifully recorded too. Start it from zsh and zsh's startup (that's where the `free()` thing comes from) gets mixed in as well. The observer is disturbing the thing it observes. What is this, quantum mechanics?

`zprof.x` now discards its own samples. While we were at it, we switched rcmd.x's shell from zsh to COMMAND.X, so we don't start up zsh on every test. COMMAND.X takes `/c` instead of `-c`, and if you hand it an argument containing a space, it silently does nothing. Yes, of course we fell into that one too.

## Ditching SLIP

With the distortion gone from the profile, the next big one showed up: decoding SLIP inside slipd.x. Just the loop that scans the received bytes one at a time for the END delimiter and ESC and copies them was 19% of the CPU. The send side, too, pulls bytes out of slip.sys one function call per byte.

Wait a minute. In bridge mode, the Z is talking to the Pico. And we (well, the AI) wrote both ends. Why does it have to be SLIP at all?

It doesn't. So the inside of netpipe became a sequence of IP packets with lengths. Like GRE or IPIP, it's a tunnel that wraps IP packets as-is, with a length in front.

- Pico to Z: [length 2][spare 14][IP packet]. The 14 spare bytes are where slip.sys writes the Ethernet header when it hands the packet to xip.x. That way the Z can pass the received sectors to xip.x without copying a single byte.
- Z to Pico: [length 2][IP packet]. slip.sys stacks them in this form on its send ring, and slipd.x pulls them out in one go.
- This format is only used when the request marker is "X6NR." With an older slipd.x, or in UDP mode with slattach on the Pi, it stays SLIP.

Before I could re-flash the firmware, the Pico vanished from Wi-Fi. The Z said "An error has occurred." Retry, same thing. The AI pinged the Pico's IP address from the Pi, confirmed there was no answer, and said, "It's the Pico, not the Z." We still don't know why. I was about to re-flash it anyway, so I did.

First boot with the new slip.sys: another bus error. The AI was calling slip.sys's new command from user mode. slip.sys lives in a supervisor-only region. Fixed.

| | Speed (Pi → Z, 200KB) |
| --- | --- |
| End of last episode | 136kbps |
| Give up the CPU while waiting on SCSI | 176kbps |
| Ditch SLIP | 290kbps |

Still not a single byte of xip.x touched.

It's not SLIP anymore, so slip.sys and slipd.x will get renamed at some point. It's the netpipe driver, so: npd.

## contee, at last

`contee.sys` (copies whatever goes to the screen out to RS-232C as well), which I wrote about back in part 3 and never tested on the real hardware, finally got tested.

- At first, the driver loading messages came through, but the error dialogs didn't. The dialogs are drawn by `_B_PUTMES`, which prints a string at a given position. We hijacked that too.
- IOCS.X replaces the screen output IOCS calls with its own versions, so contee.sys has to go after it.
- With IOCS.X and contee.sys at the top of CONFIG.SYS, the log came out garbled. RSDRV.SYS was resetting the port to 9600bps when it loaded. contee.sys goes after RSDRV.SYS.

I made it read from an empty floppy drive on purpose, and this showed up in the serial log ("No disk in drive, please insert one / Abort<A> Retry<R> Ignore<I>?"):

```
　　　ディスクが入っていません、入れてください　　　
　　　 中止＜Ａ＞ 再実行＜Ｒ＞ 無視＜Ｉ＞ ？　　　　
```

Human OCR is officially retired.

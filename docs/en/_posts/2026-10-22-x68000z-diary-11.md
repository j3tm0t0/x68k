[Previously]({{ site.baseurl }}{% post_url en/2026-10-22-x68000z-diary-10 %}): I ssh'd from the X68000 Z into Linux and got `uname -a` back. 65 seconds per run, 59 of them crypto. Hooking up the VT100 the terminal agent built should give us an interactive shell. In this series, an AI (Claude) does almost all of the code and research.

## First, the shell worked

We wired the VT100 into ssh.x. Output goes from the SSH channel to the terminal emulator; input goes from the X68000 keyboard to the SSH channel. It only becomes a terminal when you pass `-t`.

I typed `ssh.x -t moto@192.168.1.108`, and after 65 seconds of key exchange, a Linux bash prompt appeared.

- Write something in `vi`, `ZZ` out, page through with `less`, full-screen scroll with `cat`.
- Up arrow for the previous command. Ctrl-C stops a `sleep`.
- `ls --color`: directories in blue, prompt in green.

The VT100 draws straight into text VRAM, so none of it shows up in the serial log. We checked by reconstructing the screen from VRAM. There's a Raspberry Pi's bash on the X68000 Z's screen.

![The Z's screen (reconstructed from text VRAM): ls --color -la /etc/ssh on the Pi, then exit]({{ "/assets/z-ssh-ls-color.png" | relative_url }})

And that was supposed to wrap up ssh.

## A sneaky idea

Looking at the screen, I said, "If we could borrow the Pico's CPU over SCSI, we could compute this way faster."

The Z's crypto is slow because it's a 10MHz 68000. But the Pico (RP2040) carrying that crypto's data over SCSI has two cores at 133MHz. And most of the time it's just hauling bytes. It's bored.

So put it to work. Proxy ARP, proxy echo, and now: proxy computation. Same idea as a USB modem's NIC handling TCP for the host. The Z asks the Pico "do this key multiplication for me" and just takes the result.

But there are degrees of cheating. Here's what we settled on:

| What goes to the Pico | Secrets the Pico sees | Speed |
| --- | --- | --- |
| Nothing (default) | none | 65 s |
| Host key verification only | **none** (just the public key and signature) | 43 s |
| + key exchange (X25519) | material for the session keys | 19 s |
| + authentication signature | your private key | 12 s |

The heaviest step, host key verification (26.7 seconds), only uses public information. So handing it to the Pico changes the security by exactly zero. That's in the "not cheating" zone. Past that, you're trusting the Pico. Then again, the Pico already carries every single packet, so the only difference is that with the keys it could read what's inside them, too. Off by default.

## Riding along the roll-call path

Requests and results get mixed into the existing netpipe exchanges. No new commands, no extra sectors. A record starts with `0xA5`. That makes the version field of the IP header read "10," so anything that doesn't understand it drops it as "broken IP" and moves on. We're borrowing IPv10 until it actually shows up.

On the Z side, npd.sys got five new commands (request, poll, cancel, reply, stats). It asks for a computation and waits, yielding the CPU with `_CHANGE_PR` the whole time. On the Pico side, we added Monocypher (a small crypto library with a good pedigree), and a dedicated task does the math when an exchange comes in. When idle, the task sleeps; when work shows up, it gets woken.

Correctness, as usual: differential tests against Python on the Mac as the reference, with fixed RFC vectors and random inputs. Everything passed on the host before it ever ran on the Z.

## Next door, 0.2 seconds

We ran the test program on the real hardware, and everything matched. On the Pico: X25519 in 91 milliseconds, ed25519 verify in 150, signing in 45. The round trip as seen from the Z: 0.2 seconds. It correctly rejects tampered signatures, too.

And then, ssh.

```
accel: ed25519 verify on the Pico in 149678 us (round trip 0.20 s)
Linux raspberrypi3 6.18.50+rpt-rpi-v8 ... aarch64 GNU/Linux
```

| ssh.x | One handshake |
| --- | --- |
| Plain (Z does all the math) | about 65 s |
| `-oAccel=verify` (verification on the Pico) | 43 s |
| `-oAccel=kex` (+ key exchange) | 19 s |
| `-oAccel=all` (+ signing) | **12 s** |

Of those 12 seconds, crypto isn't even one anymore. The rest is TCP round trips and reading a 326KB binary off B:. If the Pico doesn't answer, the Z falls back to doing the math itself. It gets slower, but it doesn't fail.

## Where things stand

An interactive Linux shell, in color, running from an X68000 Z. With help from the Pico next door, key exchange takes 12 seconds. Yes, it's cheating. But SCSI is the only realistic interface the Z has to the outside world anyway, so asking the thing on the other end to help with the math too? Not bad at all.

What should we make it do next? I have a feeling the day we ditch xip.x and hand the whole TCP stack to the Pico isn't far off. Easier said than done.

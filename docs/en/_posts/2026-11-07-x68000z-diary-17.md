The pipes in zosh, the Z-OS shell, can now run every stage at the same time. In this series, an AI (Claude) does almost all of the code and research.

This time it's about the OS. Z-OS is a home-made environment that runs on the X68000 Z. It consists of zos.x, which splits the screen and runs several shells, and zosh, our own shell. Over the last two days I gave the AI workers one goal.

> I want it to feel so much like UNIX that you'd think you were using UNIX. (使ってると UNIX 使ってるんじゃないかって錯覚するくらいの感じにしたい)

After that I ran up to 11 workers at once for about a day and a half, and we merged around 30 PRs. `ls`, `cd /`, `cat | grep`, `vi`, `man`, `ps`, `kill -9` and `curl` now work convincingly on top of Human68k.

## Drives as a single tree

The first thing I wasn't happy with was how files look. Like MS-DOS, Human68k has a separate tree per drive, `A:` and `B:`. I wanted everything under `/`, the way WSL and Cygwin do it.

The worker first tried Human68k's `ASSIGN` (which assigns a drive name to some other location) on XEiJ (an X68000 emulator). It only works in the direction "drive name to directory". There is nothing like MS-DOS's `JOIN`, which would show a drive under a directory of another drive.

So I had it write `mount.x`, a resident program that intercepts DOS calls (the OS calls for opening a file, listing a directory, running a program and so on). If the path argument is `/c/usr/bin`, it rewrites it to `C:\usr\bin` before passing it to the real handler. Opening just `/` shows a list of the drives (`a/ b/ c/ …`). It doesn't use the C library and is about 5KB.

After that we added a "tree mode" that makes the boot drive `/` itself. `/home` and `/usr/bin` are real directories on the boot drive, and the other drives appear as `/mnt/b` and so on. `/dev/null` points to Human68k's `NUL`. If a file starts with `#!/bin/sh`, it now runs with that interpreter.

One funny thing came up in review. The reviewer pointed out that typing `mount -r` (which removes the resident program) inside a shell started later would return into freed memory. The worker measured it, and Human68k had already fully returned from the intercept handler before running the child program, so it didn't happen. We didn't take the claim at face value. We measured and then decided.

## Making zosh a UNIX shell

zosh is the shell we're building to replace COMMAND.X (Human68k's standard shell). I had the worker list 21 things missing compared with POSIX sh, in order of how much they hurt, and fill them in from the top.

| Added | Examples |
|---|---|
| Paths | `/c/usr/bin`, `cd /`, `cd ..` out of a drive |
| Builtins | `ls` `cat` `cp -r` `mv` `rm` `mkdir` `head` `wc -l` `env` `seq` and more |
| Syntax | `{ }` `( )`, pipes into compound commands, here documents, `${v:-x}`, `trap`, `local`, `getopts`, `set -e` |
| Scripts | `#!/bin/sh -e`, `#!/usr/bin/env`, `sh -c` |
| Interactive | command name completion, `**`, `!!`, only `export`ed variables passed to children |
| Startup | `zosh.x -l` reads `/etc/profile`, and `logout` when it ends |

Finally, we made zosh the top-level shell without COMMAND.X (`SHELL=` in CONFIG.SYS). It shows a motd on startup and gives a `moto@z:~$` prompt. We did find a weak spot, though. If you press Ctrl+C while zosh is writing to the screen, Human68k stops zosh itself. When COMMAND.X was on top, you could fall back to it, but now there is nothing to fall back to. We're fixing it now so that zosh catches Ctrl+C itself, the way COMMAND.X does.

We also added process tools. Besides `ps` `top` `kill` `df` `du` and `free`, `kill -9` can now really stop a program running in a zos.x pane. If the program is running in user mode, it overwrites the saved return address (kept when threads are switched) with the address of the exit routine. If it still won't stop, the whole pane is dropped after 1.5 seconds, and another thread closes any files it had open. The network commands `host`, `curl` and `wget` also run on top of tis.x, which hands TCP/IP to the Pico (https isn't there yet).

## Bringing in the GNU commands

When I said "I want to cover the GNU commands pretty much completely," the worker built all 86 programs of GNU coreutils 9.12 for the X68000 as they are. It also added find, xargs, diff, gzip, less, file, patch and bc, and for editors we put both vim 3.0 (from 1994, which originally had an X68000 version) and vim 9.2. The XEiJ tests pass 122 of 123 items (the remaining one is `cat a >> a`, where input and output are the same file and can't be detected).

Speed was the problem. GNU `ls` took 0.55 seconds per run and `head` took 0.24 seconds. The long-standing ITA TOOLBOX versions take 0.12 and 0.05 seconds, so GNU is 4 to 7 times slower. I had once decided "GNU first," but after seeing these numbers I kept ITA in `/usr/bin` and put the same-named GNU commands in `/usr/gnu/bin`. Commands ITA doesn't have, such as `sort`, `find` and `diff`, use GNU.

The worker measured why it was slow. Loading costs about 1.45ms per 1KB, and on top of that Human68k spent about 33 microseconds on each spot in an executable where addresses must be fixed up (relocation). vim 9 has about 50,000 of those, which makes startup take 5 seconds. So we stopped passing the fix-up table to Human68k, put it after the executable instead, and let the startup code fix the addresses itself, faster. We also switched to a light stat that skips date conversion, which made each executable about 12KB smaller.

| Command | Initial | Now | For reference: ITA |
|---|---|---|---|
| head | 243ms | 173ms | 50ms |
| cat | 226ms | 160ms | 30ms |
| vim9 | 4.97 s | 3.54 s | — |

We also tried copying them to a RAM disk, but that was about 50% slower. RAMDISK.SYS copies byte by byte with the CPU, so it loses to SCSI DMA.

GNU sort took 12.4 seconds for 4000 lines. The worker built a tool that records the address XEiJ's CPU is executing every 1/5000 second, and used it to find the functions eating the time. After fixing things like writing out line by line even when the output is a file, and printf using a slow 64-bit division even to print integers, it came down to 7.0 seconds. The SORT.X that ships with Human68k takes 153.8 seconds for the same 4000 lines.

## Reviews by two AIs

At first I had OpenAI's Codex review the PRs and merge them if there were no problems. Partway through I said, "Reviews from both Fable and Codex would be good." Fable is one of Claude's models, and in this series it is used for heavy design work. From then on we ran both, and merged only what had no serious findings from either and passed all of CI.

The two found different things. On the zosh PRs, codex picks up boundary conditions and differences in behavior from sh in fine detail. Fable actually compiled the code and measured the stack usage of each function, and pointed out that "recursing 8 levels deep overflows the 24KB stack and silently corrupts zosh's internal data." Codex had missed that. Conversely, there were times when codex stopped something Fable had passed.

The three zosh PRs were finally merged after 8 rounds with codex and 3 with Fable. Every fix brought a new boundary-case finding and it never settled, so we decided to fix only the heavy ones (data loss, hangs, memory corruption) and move the small ones to a checklist in an issue. Even so, really dangerous things kept turning up, such as `cp ソ.txt dest/` overwriting a different file (a Shift-JIS character whose second byte is 0x5c, the same as `\`, was being mistaken for a path separator).

We also broke things after passing review. A PR that fixed a display glitch where the same line appeared twice right after splitting a pane was approved by both codex and Fable and merged. After that, all the ssh tests started failing. What ssh.x draws by itself inside a pane doesn't appear in zos.x's record of the screen, but the fix shifted only the changed parts according to that record. We reverted it right away, and the worker opened three temporary PRs with different conditions and narrowed down the cause with CI. A review can't know about tests in a different repository.

## CI and runners

When we ran the workers in parallel, the next bottleneck was CI. The tests use XEiJ, so I keep Linux VMs on a Mac mini I don't normally use and run them as GitHub Actions self-hosted runners. When I said "let's double it," the worker first measured whether more cores would make it faster. The XEiJ tests took about the same time with 6 cores or 2 cores, so we made it six VMs with 2 cores and 4GB each.

It still wasn't enough. The worst part was that every time one PR was merged, the remaining PRs conflicted. Every PR added its own test to the same single line in the workflow (the list of tests). GitHub doesn't run CI on conflicting PRs, so some PRs sat for hours with the worker saying "waiting for CI." In the end, we had each test file carry a line like `# group: shell`, and changed the workflow to collect those.

Tests also failed occasionally. They waited with a fixed sleep, so when the VM was busy they typed keys before the prompt appeared. After splitting a pane, the new prompt can take 11 to 14 seconds to appear, but the tests only waited 8 seconds. We changed them to look at the screen state and wait on that.

I received a lot of "CI failed" notifications. Because all the workers push with my token, every result comes to me.

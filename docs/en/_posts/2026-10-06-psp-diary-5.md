[Previously]({{ site.baseurl }}{% post_url en/2026-10-06-psp-diary-4 %}): We moved FM sound onto the PSP's second CPU (the Media Engine). Every time, the PSP's power died, and I turned it back on. This is the last part. Code and measurements are the AI's (Claude's), right to the end.

Let me write down the mission definition one more time. **Draw every frame, sound on, no slowdown.**

## A momentary hitch

The start jingle stretches out the moment the game begins. "Ta-ta-ta-tan" becomes "taaa-ta-ta-tan." Only the first note.

A few minutes later, another one. "After boot, the moment it goes from the logo screen to the menu screen is really heavy too. The music stumbles."

Both are momentary. During play it's stable. But a moment is very clearly audible.

## Writes that change nothing

You can't investigate a momentary glitch unless you can reproduce it. The AI added a debug command called `padat`. It presses the Circle button at fixed frames, counted from reset. That way the inputs from the title screen to the start of the game are exactly the same every time. You can measure the heavy moment the same way, as many times as you want.

We measured. The culprit was the text screen.

At scene transitions, the game clears the text screen. Thousands of times per frame, it writes zero to text VRAM. But that screen was already empty. Most of the writes were writing zero where there was already zero. **Writes that change nothing.**

And still, px68k dutifully did the full job for every single one. Bounced through the front desk (the same one we saw in part 2), advanced the generation of the GE's copy, and recalculated the display data for that byte's 8 dots from four tables.

The fix is almost embarrassingly simple to say out loud. Before writing, check whether it changes anything. If it doesn't, do nothing and go home. Go home before even the GE's watchdog. A write that changes nothing changes nothing for the GE either.

The heavy moment at the transition got clearly lighter.

## Slices that never enter the core

The same night, the AI also shaved down the 68000's waiting time.

A game's 68000 spends most of each frame in a loop waiting for an interrupt. As I wrote in part 2, that loop already skips straight to the end of the slice (200 cycles). But for each of the roughly 900 slices per frame, we were still entering the 68000 core once. The core's entry point, the compare and branch handlers, the idle-loop check. And every time, the core's code trashed the instruction cache.

The new `C68k_Exec_Idle` checks: if the previous slice ended in an idle loop, no interrupt has arrived, and the loop's instructions are still in memory, finish the slice in a few dozen instructions without entering the core. Most slices get handled this way.

Get even one condition wrong and the cycle counts drift, and the game's motion shifts by a frame. The AI's fuzz test (a test that throws large amounts of randomly generated input at it) ran 100,000 cases, changing interrupts, the values at the addresses being read, and even the branch instructions themselves between slices. It matched the original core.

## Frames that don't get drawn

We did one more thing about the start jingle.

When you play in Full Frame (draw every frame) and heavy scenes keep coming, the audio buffer runs dry. As I wrote before, when the sound runs short, the callback synthesizes on its own to fill the gap, and the music stretches by that much.

So on any frame where the remaining sound drops below 25ms, it still emulates, but doesn't draw to the screen. The few ms that drawing would take go to the sound instead. At most every other frame goes undrawn, and only while it's behind.

Does that count as "no slowdown"? To be honest: only in the heavy moments, screen updates get thinned out. But the emulation never skips a single frame. The game's progress and the sound stay at full speed. The human ear is harsher than the eye. I chose the ear.

The next morning I woke up and picked up the PSP.

"The sound stumble is gone!"

That's the only exclamation mark in the entire mission log.

## PGO that silently doesn't work

The last bug we found wasn't in the emulator. It was in the build.

The PGO profile (from part 3, the files that tell the compiler where to put the code) was, under certain conditions, **silently not being used**.

My checkout lives inside Dropbox, and locally I open it through a symbolic link. gcc builds the profile's file name from the `PWD` environment variable. make's `CURDIR` is the real path, with the link resolved. When the two disagree, the profile can't be found. No error. No warning. The EBOOT just ends up 7% bigger, and slower.

The nastiest bugs aren't the ones that crash. They're the ones that make things a little slower without saying a word. Set `PWD` to `CURDIR` in the Makefile, done.

## Where things stand

Here are the numbers. Frame times measured at 333MHz, drawing every frame, speed limiter off.

| Software | Starting point | Measured Oct 3–4 |
| --- | --- | --- |
| Chō Renshā 68K | Didn't boot before the improvements. About 46ms (22fps) with the SRAM fix | 14.1ms (about 70.7fps; capped at 55.46fps when playing) |
| SION IV (weapon select) | 104–120ms (about 10fps) | About 48ms (about 20fps) |

What's left:

- SION IV still isn't at full speed. The 68000 core already runs at 4–5 times real time, so even a perfect core wouldn't fit it in the budget. Next to measure: the remaining graphics VRAM writes and the GE path. The dynamic recompiler design doc is in the repository at `docs/c68k-speed.md`. The romance is still there.
- "Draw every frame" in the strict sense got deferred, for the heavy moments only. Drawing gets thinned out only when the sound is about to run short.
- The mystery of the ME build alone getting 1.5 times slower when `arec` and measurement are used together remains unsolved.
- The real cause of the ME power losses also hasn't been pinned down. It stopped happening, so there's no way to check.

## Lessons learned

1. **Don't build before you measure.** The 68000 was innocent.
2. **Don't trust instruction counts.** On a 16KB instruction cache, placement is everything.
3. **Look for work that changes nothing.** Code that writes zero over zero is everywhere.
4. **Don't pronounce death from a single ping.**
5. **Make the sound the clock.** The human ear is harsher than the eye.

Finally, the most important lesson. In these five days, I didn't write a single line of code. I turned the PSP on, turned it back on, listened to the sound and said "that's weird." That's all. But without "that's weird," not one of these bugs would have been found.

Mission complete. Charging the PSP.

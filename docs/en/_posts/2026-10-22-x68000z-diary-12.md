[Previously]({{ site.baseurl }}{% post_url en/2026-10-22-x68000z-diary-11 %}): An interactive Linux shell ran from the Z. Key exchange takes 12 seconds with help from the Pico next door. In this series, an AI (Claude) does almost all of the code and research.

## 1 FPS

Now that the interactive shell worked, I did the obvious thing. ssh from the Z to the Pi, from there into the Mac, and attach to tmux. Claude Code is running in there. Meaning the conversation with the AI writing this diary would show up on the X68000 Z's screen.

It showed up. And it was garbled. 「バックスラッシュ無し」 ("no backslash") came out as 「バックスラッシュ嗳し」, and 「通る」 ("goes through") as 「北る」. The kana were fine. Every single kanji was a different character.

The AI looked at the photo and had a guess right away. 通 is in row 36. 北 is in row 43. Off by exactly 7 rows. The X68000's CGROM doesn't have JIS rows 9–15; row 16 (the start of Level 1 kanji, at 0xF05E00) comes right after row 8, the last non-kanji row. The VT100 was counting rows without skipping the gap. Kana live in rows 4 and 5, before the gap, so they came through fine.

Fixed that and the garbling went away. But the other problem stayed. I said, "This is, what, 1 FPS?"

## What's slow

Testing on the Mac doesn't help here: the Mac's CPU is so fast you can't see how slow the 68000 is. The AI spun up two agents. One built a test rig that renders the VT100 screen to PNG using the real CGROM (the kanji offset bug had slipped through because the old tests left kanji glyphs blank). The other measured speed on XEiJ's 10MHz 68000.

The results weren't what I expected. Drawing to VRAM was only 10–40% of the total. The heavy part was parsing escape sequences and placing characters into the cell table: 5,000 clocks per character.

The agent shrank cells to 4 bytes with colors precomputed, placed runs of ASCII and UTF-8 in bulk, rewrote the inner drawing loop in 68000 assembly, and used the CRTC's simultaneous-access mode to write all four planes at once.

| Screen (XEiJ, 10MHz) | Before | After |
| --- | --- | --- |
| Claude Code | 6.6 KB/s | 14.5 KB/s |
| top | 2.8 KB/s | 10.3 KB/s |

Even so, the agent said: top takes 1.3 million clocks just writing to VRAM, and 2.7 million parsing. That's close to the limit for C.

## Push it onto the other side

I asked, "Wasn't there a UDP-based thing instead of ssh?"

mosh. mosh keeps the terminal screen on the server and only sends what changed. All of Claude Code's frantic redrawing gets thrown away on the server, and only the final screen arrives. But mosh is C++, and it needs protobuf and AES-OCB. Porting that to a 68000 is heavy. And it only works if mosh-server is installed on the other machine.

I thought for a bit and said, "We're allowed to launch something in userland on the ssh target, right? Like scp does."

Yes. scp launches `scp -t` on the other end over ssh, and mosh launches `mosh-server`. VS Code Remote pushes its own server into your home directory on first connect. I decided: "Write it in Rust and push the right build for the arch."

That became zterm.

- The helper on the remote side (Rust, 200–260KB gzipped): runs the shell in a pty and keeps its own copy of the screen. It converts everything into what the Z can draw (ASCII, JIS row/cell codes, emoji indices), then sends only the changed cells, batched up to about 20 times a second. Scrolling goes over as a single "scroll" command.
- The Z side: just draws the cells it receives using the VT100's drawing code. No Unicode handling, no escape-sequence parsing.
- Delivery: ssh.x checks `uname -sm` on the remote, picks from four builds (Linux aarch64 / x86_64, macOS arm64 / x86_64), and sends it over. From the second time on, it uses the copy already in the remote's `~/.cache/zterm`.

Bytes sent dropped to a tenth for top, and to 1/60–1/115 for a spinner that redraws the whole screen.

## 4096 bytes

The first time we pushed the helper from the Z, raspi5's sshd hung up on us. The log said:

```
Bad packet length 3490354796.
ssh_dispatch_run_fatal: Connection from user moto 192.168.1.68 port 2071: Connection corrupted
```

Until now, the Z had only ever sent small stuff, like keystrokes. Sending 257KB in one go was a first. The agent ran a bulk-send test on the Z and found one of xip.x's quirks. If you `write()` more than 4096 bytes to a non-blocking socket, all the data gets sent, but it returns -1 (EAGAIN). dropbear thinks "didn't send," sends the same data again, and the encrypted stream goes out of sync. In a test writing 32KB at a time, we meant to send 300KB and the other side received 3.3MB.

Chopping socket writes into 4096-byte pieces fixed it. If we'd built a file-upload feature from the Z later, we'd have hit exactly the same wall.

## 1.5KB/s

With that fixed, the push went through. In three minutes. The agent measured it: the Z's chacha20-poly1305 (the SSH cipher) could only process 1.5KB per second. The VT100 can draw 14KB/s, but decrypting incoming data chokes at 1.5KB/s. That was the real culprit behind 1 FPS.

Breaking it down: poly1305 was 80% of it. It leans hard on 64-bit multiplies, and on a 68000 every one of those turns into a library function call. Same disease as X25519. The agent rebuilt poly1305 around MULU 16×16, then switched it to looking up multiples of the per-packet key from a table, and turned chacha20 into assembly with all 80 quarter-rounds fully unrolled.

| chacha20-poly1305 | Before | After |
| --- | --- | --- |
| XEiJ | 4.0 KB/s | 22.1 KB/s |
| Real Z | 1.7 KB/s | 9.1 KB/s |
| Real Z, actual ssh receive | 1.42 KB/s | 4.54 KB/s |

Actual receive runs at half the crypto speed because the crypto (9KB/s) and TCP processing (also around 9KB/s) take turns on the same 68000, the agent wrote. From here, making only the crypto faster won't speed up the whole thing much. The day we ditch xip.x really is close.

## Everything at once

The faster VT100, zterm, the crypto, and the Pico accelerator all went into a single ssh.x.

| Z to raspi5 | VT100 (`-t`) | zterm (`-Z`) |
| --- | --- | --- |
| `top -d 0.5 -n 20` | 30.1 s | 23.8 s |
| `seq 1 20000` (20,000 lines) | 249.8 s | 13.9 s |

18× faster when you dump 20,000 lines. The VT100 decrypts and scrolls one line at a time, but with zterm the other side batches the screen, so only the final screen arrives. It also connected to macOS (an x86_64 Mac mini and an arm64 MacBook).

I logged in from the Z to raspi5 with `ssh.x -Z` (zterm), tried Claude Code with the Z's keyboard, and said, "It's working pretty well." So next: local echo. The Z draws what you type right away, without waiting for the Pi to reply (underlined until it's confirmed). The zterm helper holds the whole screen, so checking the guess is easy. If it's wrong, erase it and stop predicting for a while. For input that doesn't show on screen, like passwords, the first character never gets confirmed, so nothing gets drawn. In a test app mimicking Claude Code's input box, 55 out of 56 predicted characters were right.

Just to be clear: Claude Code itself is running on raspi5 (a Raspberry Pi 5). The Z's 68000 is only doing the ssh crypto, drawing the cells zterm sends, and sending keys. Even so, I'm talking to an AI on the X68000 Z's screen and keyboard, right in front of me.

So I asked that Claude Code: draw the X logo of the X68000 as big ASCII art.

The red thing in the top left is Claude Code's mascot. Until we added glyphs for the block elements, it was `???????`. I said, "That's really nice."

## Not yet

- Double-line box drawing (╔ ╗ ║ ═) doesn't render right. That's the broken outline around the logo in the photo.
- No Japanese input. ssh.x reads keys without going through the X68000's Japanese input method (FEP).
- Two bugs that only show up sometimes: one address error inside dropbear where the stack pointer went odd, and a MAC error on about one in four bulk sends. Neither reproduces.
- Crypto and TCP are fighting over the CPU. Hand TCP to the Pico and that frees up.

I talked to a 2020s AI on the screen and keyboard of a 10MHz 68000. Easier said than done. But this time, there's a photo.

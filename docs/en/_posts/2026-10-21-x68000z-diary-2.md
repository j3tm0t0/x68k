[Previously]({{ site.baseurl }}{% post_url en/2026-10-21-x68000z-diary-1 %}): the AI built a command-line environment, and I plugged and unplugged USB sticks. Over and over. I'm done with that.

The Z has an RS-232C port. I have a Raspberry Pi. Connect them. Problem solved.

## Three wires

I wired the Z's RS-232C straight to the Pi's UART with three wires: TX, RX, GND. That part was my job. The AI doesn't have hands.

Logging in to the Pi from MuTERM, a terminal program on the Z, went smoothly. But MuTERM isn't a VT100, so bash's bracketed-paste sequence (`ESC [ ? 2004 h`) shows up on screen as literal garbage. The AI added a line to the Pi's `.bashrc` that turns it off, but only when TERM=ansi.

So now I can drive the Pi from the Z. But I want the opposite. I want to send files from the Pi to the Z, and type commands on the Z from the Pi. In other words, the Z needs TCP/IP.

## PPP

TCP/IP on Human68k means ESP/X from Keisoku Giken. The AI tracked down xip.x, an improved version of its inetd.x (K.Shirakata's beta 5), plus a Human68k port of IIJ-PPP, and hooked them up to pppd on the Pi.

Ping 8.8.8.8 from the Z came back. Yes! But:

- It runs at about 8kbps.
- If pppd isn't running on the other end, ppp.x freezes at "Phase: Dead." BREAK doesn't help. That means it's power-button time, which means it's me time.

The AI wrote `pppwait.x`, which waits until it has received an LCP packet from pppd before starting ppp.x. That took care of the freezing. The speed, though, is what it is.

## No SLIP driver? Write one

SLIP is lighter than PPP, so it ought to go a bit faster. Problem: there's no public SLIP driver for Human68k.

Fine. If there isn't one, write one. By "write" I mean the AI writes it.

- **slip.sys**: a device driver that looks to xip.x like an Ethernet card (`/dev/ep0`).
- **slipd.x**: a resident thread. It reads and writes the serial port through IOCS, unwraps the SLIP framing and hands the packets to xip.x.

In the first version, slip.sys hijacked the SCC interrupt for itself. The result: xip.x's heap and stack got trashed, and I got the full tour. Bus errors. Address errors. A scrolling screen gone to pieces. The AI changed tack. It let the ROM and RSDRV.SYS keep handling the interrupts, and read and wrote through IOCS the same way ppp.x does. It hasn't crashed since.

On the X68000 Z, the UART only honors the speed you set through IOCS. So the AI also made `rsspeed.x`, which calls `_SET232C` directly. On a 38400bps line we got an effective 21.9kbps with 0% loss. Three times PPP.

## rcmd

With TCP/IP up, I leave `rcmd.x` waiting on the Z. It's a tiny server: it takes one line of command on TCP 2323, runs it in zsh and sends back the output. The Pi side is written with nothing but bash's `/dev/tcp`.

```sh
x68 'ls -l /usr/bin'          # run on the Z and show the result
x68put hello.c /home/hello.c  # send a file (over 4KB it goes as a tar.gz and gets unpacked on the Z)
```

And here Human68k gave me my initiation. While the foreground program is waiting inside a DOS call, Human68k doesn't run the background threads. So if rcmd does the obvious thing and just waits for a connection, xip.x, the thing that processes the connection's packets, stops too. So the connection never arrives. Waiting for it is exactly what keeps it from arriving. What is this, a Zen koan?

The AI changed the wait into a polling loop, and had rcmd give up the CPU on its own with `_CHANGE_PR`.

Now the loop runs without me: the AI writes code on the Mac, sends it from the Pi, runs make on the Z and tests it. One fewer job for me. Whether I should be happy about that, I haven't decided.

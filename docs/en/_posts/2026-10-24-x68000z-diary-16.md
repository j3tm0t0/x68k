## The culprit was the serial port

Pico Z Loader is firmware being rewritten from scratch for the Pico 2 W that plugs into the Z. In the desk tests, everything worked: holding the boot until SMB is ready, the B: drive (raspi3's shared folder mounted over SMB), networking, and the crypto accelerator.

But plug it into the Z, and the Z froze. It stops in the middle of `dir`. It stops right after boot. It stops after an `echo`. It stops somewhere different every time. The cursor on screen keeps blinking, so the X68000's interrupts are alive. And yet nothing you type gets a response.

The AI worker on it would come up with a theory, then check it on the Z.

| Theory | What we tried | Result |
|---|---|---|
| USB mouse | Remove the mouse function | Still freezes |
| The Pico replies too fast | Wait 3ms after every command | Still freezes |
| USB keyboard | Remove the keyboard function too | Still freezes |
| Read cache | Find and fix one cache bug | Still freezes |
| How the HDS (the Z's hard disk image) file is handled | Make it the same as the released firmware | Still freezes |

Five tries, no cause. So I had it change how it was narrowing things down. Between the released firmware, which doesn't freeze, and Pico Z Loader, which does, build versions that swap layers in and out (USB handoff, cache and so on) and see which layer the freezing starts at.

The result was a surprise. **The released firmware, completely unchanged, froze the same way.**

What they had in common was the way we were testing. The AI was driving the Z through the serial console (`CTTY AUX`, a setup where you type the Z's commands over RS-232C). Type `dir` over that enough times, and the Z is what stops. When the released firmware passed its tests before, that was luck.

Switch to driving it with rcmd, which sends commands over the network, and Pico Z Loader booted three times, took ten `dir`s each time, and never froze once. Copying on the B: drive worked, networking worked, ssh to the Mac worked.

The way I normally use it, driving from the keyboard with `CTTY CON`, this problem doesn't happen. Why the serial console stops, we still don't know. But the cache bug we found along the way was one that genuinely needed fixing. Even after a write, it could sometimes return stale contents left in the cache as a successful read. The released firmware had the same bug too, just rarer, so we fixed both.

## A bug found right after release

Before all this, I'd released the current firmware as [v2026.10.23](https://github.com/j3tm0t0/x68k/releases/tag/v2026.10.23). It includes a Pico 2 W build, boot waiting, the USB keyboard, using an SD card plugged into the Pico as the Z's C: drive, `tis.x -p` (which hands TCP processing to the Pico), and password authentication in ssh.x.

We measured `tis.x -p` on a real Z too.

| | tis.x -p | xip.x |
|---|---|---|
| 1-byte round trip | 53 ms | 149 ms |
| Z → Mac, 1MB | 109 KB/s | 25.7 KB/s |
| Mac → Z, 1MB | 145 KB/s | 16.5 KB/s |

After the release, one of the AI workers was running a new test and caught that firmware stopping with "Out of memory." It happens now and then if you keep reading and writing the disk right after boot. The cause: two pieces of the networking code were using the same connection at the same time.

I asked: "Hmm, that's not good. Not enough testing?"

Exactly that. The pre-release checks had only covered one configuration, a single Pico with an SD card plugged into the Z. So we built a test suite that runs before every release. On a Pico on the desk, it tries with and without an SD card, SMB traffic that's delayed or dropped, the same USB usage pattern as the Z, and ten minutes of continuous running, and checks for no out-of-memory, no USB disconnects and no data mismatches.

The fixed version was checked on a real Z. In two of three boots we stopped SMB, for 45 and 60 seconds, and confirmed that the waiting screen came up and then the boot went through. The fixed release, v2026.10.23.1, goes out once that suite passes in full.

## Running every stage of a pipe at once

zosh, Z-OS's own shell, used to connect `a | b` through a temporary file. b starts reading only after a has finished writing everything. Same as MS-DOS.

I had a newly added AI worker build a way to run every stage of a pipe at the same time. zos.x adds eight pipe devices to Human68k and runs each stage of the pipe on its own thread, wiring each stage's standard input and output to those devices. What it runs are existing, unmodified .x executables.

On a real Z, we pushed 220KB through and didn't lose a single line. Writing every 0.5 seconds, it arrived on the reading side at 0.51-second intervals. A pipe that never ends can be stopped with Ctrl+C.

Along the way, we also found the cause of an old bug. Run a program that just computes forever in one of Z-OS's split screens (panes), and every so often the switch to other threads stops happening, and key input and networking freeze for 20 to 100 seconds. When the timer interrupt that switches threads arrives in supervisor mode, Human68k defers the switch until the return from DOS processing. A pure-computation program never calls DOS, so the switch stays deferred. The thread time slice is 20ms, exactly twice the 10ms period of another timer, so apparently the switching interrupt can keep landing in the middle of that other timer's handler, every single time.

The worker inserted a small routine in front of that timer interrupt. If a switch is pending, and what was running at interrupt time is an ordinary program, switch right there. We ran it for 16 minutes on a real Z. The routine switched on the spot 818 times, and the longest freeze was 0.55 seconds.

We also reshot last time's vi and gcc video on this build. I'd said: "If you don't move the cursor or something in the left pane while it compiles, you can't tell it's multitasking." In the current video, for the roughly 30 seconds gcc is compiling, typing continues in vim on the left and the clock in the bottom right keeps going (2.5x speed until the gcc command is typed, real time after that).

## The case

Last time's case had room to store the Debug Probe cable. But the finished version doesn't need a Probe. Solder a Pico 2 W with no pin headers straight onto the board, put the microSD kit at the end opposite the Pico's USB, and cut the board down to only the size it needs. That shrank it to 78 × 35 × 13mm. About half the first design.

It sticks to the side of the Z with removable double-sided tape. There's a hole for pressing the BOOTSEL button with the lid closed, and the top is made thin so the LED shows through. The dimensions are still provisional. The design gets redone after measuring the actual board and the actual Z.

## Seven AI workers

The AI workers are up to seven. The task list had gotten scattered across conversations with each worker and their handoff notes, so I pulled it together in GitHub Projects. From now on, changes go like this: a worker cuts a branch, opens a PR, writes up the test results, then merges. I decided the first issue myself: "Build the ultimate OS for the X68000 Z." It stays open. Forever.

I also had notes about the AI's Japanese. It kept reusing phrases like 「印」「帯」「道」「効く」 ("mark," "band," "path," "takes effect"), where you can't tell what's actually meant. I said: "Should we make a skill or something? One that doesn't talk like an AI." Now, before writing, the AI reads a list of words to avoid, and after writing, it searches to make sure none of them survived. Text going into other people's repositories also gets read by a different AI (Codex).

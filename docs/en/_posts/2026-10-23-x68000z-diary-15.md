[Previously]({{ site.baseurl }}{% post_url en/2026-10-23-x68000z-diary-14 %}): I started building "Z-OS," an OS that runs on nothing but the Z and a Pico. By the end of the day, the Z's screen was split in two, with gcc on one side and ssh on the other. In this series, an AI (Claude) does almost all of the code and research.

Once I started letting the AI work on the real Z, there was a problem. The AI can't see the Z's screen, can't type on it, and can't press the power button when it freezes. If I have to sit next to it sending photos of "here's what it shows now," nothing gets done while I'm asleep or out.

So I gathered up tools until the AI could run the Z and the Pico, watch them and fix them by itself. Emulator, serial, keyboard, smart plug, Debug Probe, HDMI capture.

![The whole debugging setup: XEiJ and picosim on the Mac; from raspi3 to the X68000 Z, serial, HDMI capture, Debug Probe and x68key; a smart plug on the Z's power]({{ "/assets/z-debug-env.png" | relative_url }})

## The emulator

The thing we use most isn't the real hardware. It's XEiJ on the Mac. Paired with picosim (the stand-in Pico) from last time, the Z inside XEiJ boots the same way the real one does, uses B:, and gets on the network.

The AI bolted a Java hook onto XEiJ and reads the screen as text instead of as a picture. It reads text VRAM directly, and repeats "when the prompt shows up, type the next key." It also spots bus-error dialogs this way before I do.

The test suite is up to six. Boot waiting, B:, networking, the hand-TCP-to-the-Pico mechanism, Z-OS, and Pico Z Loader, which is being rewritten. That last one takes the new firmware's code, builds it as-is for the Mac, and hooks it up to XEiJ. Before flashing a Pico, we can confirm on the Mac that the Z boots from that firmware.

Set XEiJ to 16.7MHz, and the speed is close to the real thing too. But inside XEiJ the USB latency is essentially zero, so the final numbers still come from real hardware.

As the number of workers grew, they started fighting over this test bench. Run two XEiJs at once and the fixed ports and working directories collide. I asked: "Can't you run more than one XEiJ?" And then: "Could you use Docker or something / then we could use the cloud or GitHub Actions."

XEiJ is Java, so it runs inside a Linux container if you give it a virtual display instead of a real screen. The tests read the screen as text, so not seeing the picture doesn't matter. Run each test in its own container, and the ports and directories are separate, so they can run side by side. A worker is building it now.

The catch: XEiJ itself and the boot HDS (with Human68k and gcc on it) are other people's distributions, so they don't go into the image. They're passed in from outside at run time. Putting this on GitHub Actions has to wait until we decide where they live.

## Serial

The Z's RS-232C is wired to raspi3. Right after boot, the `CTTY AUX` at the end of AUTOEXEC.BAT points the Z's console at the serial port. The AI types from raspi3, and everything the Z says back goes into a log. Before the network comes up, this is the most reliable way in.

One pitfall. Send a string all at once and the Z freezes. So we made `x68type`, which sends one character at a time.

Once the network is up, rcmd.x (a small remote-command server on the Z) runs commands and sends files from raspi3.

Going the other way, even after the console is switched back to the Z's keyboard and screen (`CTTY CON`), there's `contee.sys`, which copies whatever goes to the screen out to serial. It's only loaded in the development boot (`PROFILE=dev`). Even while I'm typing on the Z, the AI can follow the screen in the log. Error messages end up there too.

## Keyboard

Serial can't test real key input. Switching panes in Z-OS, typing an ssh password: those come from the keyboard.

So we mixed a USB keyboard function into the Pico firmware. From the Z's point of view, the Pico is a disk and also a keyboard. Send `x68key` from raspi3 over Wi-Fi, and it becomes key input on the Z. `x68key combo ctrl f11 del` does a soft reset too. There are two Picos now, so you pick the target by name, like `-t z`.

## Smart plug

I said: "You can touch the real hardware. And if it freezes, go ahead and yank the power."

I put a Wi-Fi smart plug at the source of the Z's power strip. raspi3 is on a separate supply, so even when the Z goes down, the tools stay up.

Normally it doesn't get used, though. The default way to restart is a soft reset from the keyboard. The plug is only for when that doesn't bring it back. The exception is after reflashing the Pico. The Z doesn't rediscover USB devices on a soft reset, so we cycle the power.

## Debug Probe

Two Raspberry Pi Debug Probes are plugged into raspi3's USB. One connects to the Pico in the Z, the other to the development Pico on the desk.

- **Flashing**: burn firmware over SWD. No BOOTSEL button, no replugging USB. It flashes while still plugged into the Z.
- **Halt and inspect**: run openocd, and stop the Pico from gdb on the Mac to look inside. The Pico 2 W problem from last time, "crashes when a USB host connects," got fixed after we used this to find where it crashed.
- **Logs**: a logger writes the Pico's UART output to a file, nonstop. You read it by name, like `picolog sd`.

## HDMI capture

The Z's HDMI goes into raspi3 through a cheap USB HDMI capture device. Now the AI can see the Z's screen too.

- `zshot` for stills. The first few dozen frames are black, so it throws those away before taking the shot.
- `zrec` for video (1280×720, 30fps). Used to check boot screens and the flicker when Z-OS scrolls.

Here's a video the AI shot with `zrec`. Z-OS has the screen split three ways. In the left pane, vim adds a line to z.c and saves it, and in the top-right pane gcc starts compiling. Through the roughly 30 seconds of compiling, the left-pane vim keeps getting comment lines typed into it, and the clock in the bottom right ticks every second. Two programs really are running at the same time. The keys are typed from a script through `x68key`. Up to typing the gcc command it's at 2.5x speed, and from there to the end it's real time, and it says so on screen.

These capture devices have no passthrough, so while the Z is hooked up to one, my monitor gets nothing. When I want to use the Z, I swap the cable. "I can't see the screen anyway," I said, and let the AI have it for a while.

## There's only one Z

Once the tools were in place, a different problem showed up. That day, four or five AI workers were running in parallel. And there is exactly one Z.

At one point, two of them used the Z at the same time, and keys typed by one leaked into the other's test. So we made a "sign." Before using the Z, you check the sign. If it's empty, you write your name on it. If someone else's name is there, you wait. When you're done, you erase it. No overwriting.

So most testing happens in the emulator, and the real hardware is only for final confirmation. A worker waiting its turn keeps going on its next job in XEiJ.

## Wiring hell

All four of raspi3's USB ports are taken. Two Probes, the capture device, and power for the development Pico. Tangled up with those are the serial and HDMI cables and the wiring for the breadboard microSD.

![Wiring hell. Next to the X68000 Z: Debug Probes, a Pico 2 WH, a microSD kit on a breadboard with jumper wires in every color, and raspi3's cables all knotted together]({{ "/assets/z-wiring-hell.jpg" | relative_url }})

"This is turning into wiring hell." "I want to solder it all onto a perfboard and put it in a case."

The Pico 2 WH goes in a pin socket, and the microSD kit, the pull-up resistors and a header for the Probe all go on one board. For the case: "I want it to pop open, and store the probe cable inside." I asked the AI, and it wrote up a 3D-printable design in OpenSCAD. Hinge at the back, latch at the front, and a little cable compartment behind a divider. The dimensions get redone after I assemble the board and measure it. Until then, I plan to drill holes in a Muji polypropylene storage box and use that.

![The OpenSCAD case, opened. In front, the Pico 2 WH and the microSD kit; in back, the divider and the cable compartment; the lid swings open on a hinge]({{ "/assets/pzl-case-open.png" | relative_url }})

## Not yet

- To watch on both the monitor and the capture device, I need an HDMI splitter.
- To test mouse range selection in Z-OS, the Pico needs a USB mouse function too.
- The USB latency gap between the emulator and real hardware hasn't been closed.

Right now the AI boots the Z, takes screenshots, and power-cycles it when it freezes, all while I'm asleep. My job is plugging in parts, and soon, soldering.

[Previously]({{ site.baseurl }}{% post_url en/2026-11-10-x68000z-diary-18 %}): An AI went through about 200 commands three times, looking for places where someone used to UNIX would notice they weren't on UNIX, and we fixed them. At the end, the Z-OS image built for the Z booted unchanged on the BlueSCSI v2 in my X68000 Compact XVI (the XVI from here on).

This entry is mostly about the XVI. I modified the BlueSCSI v2 firmware so the XVI can do what the Pico in the Z does: switching boot disks and handling the crypto math. I also moved to the Pico 2 W version of BlueSCSI so disk images can be sent over Wi-Fi. At first it only managed 25 KB/s. The cause was the radio, and with an access point next to the XVI it went to 1.1 MB/s.

## Putting Pico Z Loader features on the BlueSCSI v2

On the Z, the Pico that emulates the SCSI disk runs my own firmware (Pico Z Loader), which switches boot disks, provides networking, and does the SSH crypto math. The BlueSCSI v2 in the XVI is also a Pico inside, so I added the same things to the BlueSCSI firmware. The BlueSCSI firmware is GPL-3, and my changes stay on a local branch; I haven't published them.

The XVI's disks are split by purpose. Image files on the SD card give the Z-OS boot disk (64 MB), `/usr/local` (256 MB) and `/home` their own SCSI IDs. As I wrote at the end of last time, rewriting the boot disk leaves `/home` alone. I first made `/home` 32 MB, but this isn't the UNIX quota from my first year at university, so I later made it 512 MB (sent over Wi-Fi and swapped in, as described below).

What I added:

- **Boot menu**: replace the boot sector of the ID0 disk with my own loader and pick what to boot from a list on screen. If nothing is chosen, it boots the default after 5 seconds. Arrow keys and Enter, or number keys.
- **ID6 for communication**: the BlueSCSI presents one SCSI device on ID6 for communication, and talks with the X68000 using vendor SCSI commands. The boot menu uses it to hide the IDs that weren't chosen. The SSH crypto (X25519 / Ed25519) is also handed to the Pico through ID6.
- **Choosing a game image**: the boot menu's "choose an image" entry asks ID6 for the list of images on the SD card, swaps the chosen one onto ID5, then boots. It takes the place of swapping floppies.

The boot menu had a bug that only showed up on real hardware. Sometimes after power-on the countdown didn't start. Keystrokes had piled up right after boot, and the loader took them as "a key was pressed." Reading and discarding queued keys before showing the menu, and stopping the countdown only for keys the menu uses, fixed it. At first the lead AI was convinced the cause was a different resident program; it found the real cause only after I told it "the countdown isn't running."

## Sending images over Wi-Fi and swapping them in

Rewriting the boot image for every test was still a chore. With the BlueSCSI's USB connected to a Raspberry Pi and written as a USB disk, the XVI loses all its disks while it's being written. It's also only 100-150 KB/s, so 64 MB takes 10 minutes.

So I moved the BlueSCSI to the Pico 2 W version (with wireless) and had the following built:

1. While the XVI keeps running on the old image, receive the new image over Wi-Fi into a separately named file on the SD card. SCSI keeps answering.
2. Once everything has arrived and the size and CRC32 match, mark it "waiting to swap."
3. At the next BlueSCSI start, or at the SCSI bus reset the XVI issues when it resets, rename the old image to the backup file name and the new image to the usual file name. If power is lost midway, the next start either finishes the job or rolls it back.

The BlueSCSI firmware already has wireless code, but it emulates a SCSI Ethernet adapter for Macs (DaynaPORT) and just passes frames to SCSI. There's no TCP/IP. I added lwIP (the TCP/IP stack in the Pico SDK) to the Pico 2 W build only, and run a TCP server just for receiving. The sending side is a Python script, `bsstage`.

On real hardware the swap worked on the first try. The swap at start took 15 ms, the swap at an XVI reset 13 ms, and the XVI booted straight into the new image. But the speed was only 25 KB/s. At over 40 minutes for 64 MB, that's slower than USB.

The AI working on the firmware suspected the firmware first. It turned off Wi-Fi power saving, widened the TCP receive window to 32 KB, and wrote to the SD card in aligned 32 KB chunks, but it didn't get faster. When I had it log the time spent in each stage of the receive path every 5 seconds, the firmware spent most of its time waiting for the next frame. Logging the wireless chip's state showed a signal strength of -77 dBm and a wireless link rate of 5.5 Mbps. The slowness wasn't the firmware; the signal was weak.

So I switched an NEC Aterm to access point (AP) mode and put it right next to the XVI. The Aterm switches to AP mode with a switch on the unit. The BlueSCSI's wireless chip (CYW43439) only does 2.4 GHz, and the encryption should be WPA2-PSK.

![The BlueSCSI v2 behind the XVI (Pico 2 W version, white case) and the NEC Aterm right next to it]({{ "/assets/xvi-ap.jpg" | relative_url }})

| | Before | AP placed next to it |
| --- | --- | --- |
| Signal strength | -77 dBm | -56 dBm |
| Link rate | 5.5 Mbps | 57.5 Mbps |
| Time to send 8 MB | about 5 minutes | 7.4 seconds |
| Speed | 25 KB/s | about 1.1 MB/s |

A 64 MB image arrives in 62 seconds. Running a job on the XVI that copies `ZOS.X` 20 times while sending, both finished. Resetting the XVI afterwards boots it on the new image. Going from building an image on the Mac to trying it on the XVI now takes about a minute, with no power cycling.

The firmware changes weren't wasted either. With a good signal, the receive window and write size set the speed, so having fixed those first is why just placing the AP got all the way to 1.1 MB/s. I didn't measure how much each of the AP and the firmware changes contributed separately.

## Swapping the Raspberry Pi, and a remote drive over serial

There's a Raspberry Pi next to the XVI. It runs a resident program (zmuxd) connected to the XVI's RS-232C that reads the screen and sends keys, and the BlueSCSI's USB and a web camera for screenshots are connected to it. It used to be a Raspberry Pi 5; I replaced it with a Raspberry Pi 2 (32-bit, 4 cores). zmuxd is written in Rust, so I built it for 32-bit ARM on the Mac and copied it over. Heavy work such as builds happens on the Mac; the Raspberry Pi 2 only connects the XVI and the devices.

I also put a remote drive (ZRMT) on top of zmux's serial link. With `zrmt.sys` loaded on the XVI, a directory on the Raspberry Pi shows up as drive F:. It only does about 3 KB/s, but a small test program can be built on the Mac, dropped on the Raspberry Pi, and run on the XVI from `F:`. That's how I run test programs when I swap them in over and over. Before, every change meant powering off and rewriting the image.

Eventually I want to remove this Raspberry Pi too. If networking, crypto and image transfers can all go over the BlueSCSI's Wi-Fi, the XVI and the BlueSCSI are enough. But while the firmware is under development, the Raspberry Pi is needed for USB logs and flashing. It goes once the firmware settles down.

## What's next

Separately, Z-OS got a setting called ZOS_PROT. The 68000 has no MMU, so it rewrites the X68000's "from here up only supervisor mode can write" boundary ($E86001) per thread, making a program in a pane get a bus error if it writes to the OS's or another pane's memory. It's off by default.

Next, these two:

1. **Make the files on the BlueSCSI's SD card a drive as they are.** Right now whole images get swapped. Only the boot disk would stay an image; the rest of the SD card's files would be shown as a Human68k remote drive, so files dropped over Wi-Fi are visible on the XVI right away. An AI wrote the design, Fable reviewed it, and implementation has started.
2. **The remaining two ZOS_PROT issues.** Fix what the review pointed out: on a real 68000, a jsr into protected memory can bus-error before the return address is pushed onto the stack, and a thread waiting inside the TCP/IP code couldn't be stopped.

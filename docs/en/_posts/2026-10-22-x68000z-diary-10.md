[Previously]({{ site.baseurl }}{% post_url en/2026-10-21-x68000z-diary-9 %}): xip.x's threads were yielding twice per loop. Fixed that, broke 500kbps. I ended with "what should we aim for next?" In this series, an AI (Claude) does almost all of the code and research.

## I said it out loud

"I wonder if we could make ssh for the x68k. With vt100 support."

That's all I said, at 1 a.m. The network was fast now, and I had nothing better to do.

The AI's assessment: doable. dropbear, a small SSH implementation, is written in C, and the X68000 cross-compiler (elf2x68k) ships with a BSD sockets library. Two problems. One: filling in everything Human68k doesn't have (fork, signals, /dev/urandom, terminals). Two: the crypto is heavy. SSH key exchange uses an elliptic curve (Curve25519), and that's a lot to ask of a 10MHz 68000.

I assigned the work. "Cut a worktree and have a subagent do it. Up to the point where you can run some command over ssh. Have another agent do terminal emulation in parallel."

The AI spun up two more AIs, and I went to bed.

## The RST culprit was TOS

I woke up and read the logs. The ssh agent had started with a socket smoke test: before running dropbear, make sure the library works against xip.x on its own. The results were weird.

- Connecting works.
- Data we send reaches the other side, and the ACKs come back.
- But when data arrives from the other side, xip.x sends back an RST and kills the connection.

The stock telnet.x did the same thing. So that's why, way back, I'd decided "telnet.x doesn't work."

The AI set up a plain Python listener on the Pi to compare. That one worked perfectly. It knocked out the differences one by one, and the last thing standing was the **TOS** field in the IP header. sshd marks its packets DSCP EF (TOS 0xb8). xip.x is a descendant of KA9Q NOS, and it throws away TCP data with a nonzero TOS. The handshake packets (TOS 0) got through, and then the first data packet got an RST.

Two ways to fix it:

- Set `IPQoS none` on the Pi's sshd. Only works against servers you control, but it's instant.
- Have the Z-side driver npd.x rewrite the TOS of incoming packets to 0, and fix up the checksum.

The ssh agent did the first one, stood up a test sshd on port 2222, and kept going. The AI that was talking to me put the second one into npd.x. Now it works against a stock sshd too.

## A five-minute multiplication

In under two hours, dropbear became ssh.x (233KB). It got through connecting, the banner exchange, and the start of key exchange. Then it stopped.

It hadn't stopped. It was computing. One Curve25519 scalarmult took **five minutes**. A handshake needs two of those, plus an ed25519 signature verification and a signature. 15–20 minutes total. sshd drops the connection after 2 minutes.

I said, "Doesn't matter if it's slow, let's verify with something that's guaranteed to connect." Worst case, relay through the Pi. Or set up a honeypot on the Pi pretending to be telnetd and come in over telnet. Isolate the simple problems first.

The ssh agent extended the test sshd's grace period to an hour and aimed for one complete run first.

## While I slept

Except the terminal agent finished VT100 first (that's for next time). With its hands free, it picked up the job of making the crypto faster.

dropbear's Curve25519 is the TweetNaCl version, which holds field elements mod 2^255-19 as sixteen 64-bit integers. One multiplication is 256 64-bit products. The 68000 has no 64-bit multiply, so every one of those is a library function call.

The terminal agent rewrote the field arithmetic so it only needs the 68000's `MULU.W` (16 bit × 16 bit → 32 bit).

| Version | One scalarmult (XEiJ, 10MHz) |
| --- | --- |
| Original (TweetNaCl) | 118 s |
| C, tuned for MULU | 22 s |
| Comba multiplication in 68000 assembly | 10 s |
| Inversion as an addition chain | 9.1 s |

The surprise: the biggest time savings didn't come from the multiplication itself. They came from carry propagation (car25519). Sixteen limbs' worth of 64-bit adds and right shifts, six times per multiply. Just switching that to 32-bit made more than half the time disappear.

Next up: ed25519. Verifying a signature took 37 seconds, signing took 19. Both of them compute "k times the base point B." The base point is fixed, so if you build a table of multiples of B ahead of time (25KB), you go from 256 additions to 64. Same trick as ref10. Signing got to 3.3 seconds, verification to 21, and with windowing, 13. Key generation used the same table and went from 9 seconds to 2.7.

For correctness, it ran differential tests against Python on the Mac (the cryptography library) as the reference, using fixed RFC test vectors and random inputs. Same idea as what we did with xip.x last time. The assembly parts were checked against the C reference on Unicorn's 68000. That differential testing caught one bug hiding in the carry folding.

By 4 a.m., the handshake was down to 27.9 seconds on XEiJ. The real Z is 2–3× slower, so call it around 70 seconds. Under 120.

## Morning

I woke up to find the Pico had dropped off the Wi-Fi and the Z was frozen. Power cycle. Bonus: the Claude session had ended too. The ssh agent's memory was gone, but its work was still on the branch. We spun up a new agent and kept going.

The rest came fast. Key exchange and verification went through, and it stopped at authentication.

```
B:\dbcf.x: Failed loading keyfile 'b:\id_x68k'
```

It couldn't read the key file. The file was there. 83 bytes. The AI ran a little test program on the Z, and it read 81 bytes.

elf2x68k's C library opens files in **text mode** by default. On read, it throws away 0x0D and 0x1A. The 83-byte binary key happened to contain one of each. Adding `O_BINARY` fixed it. Anyone from the MS-DOS era is nodding right now.

Next came "Couldn't set nonblocking." dropbear tries to make stdin and stdout non-blocking, and Human68k's standard I/O doesn't support that. We made it do nothing for anything that isn't a socket.

```
B:\dbcf.x: Caution, skipping hostkey check for 192.168.1.108
Linux raspberrypi3 6.18.50+rpt-rpi-v8 #1 SMP PREEMPT Debian 1:6.18.50-1+rpt1 (2026-09-11) aarch64 GNU/Linux
Connection to moto@192.168.1.108:22 closed.
```

I ssh'd from an X68000 Z into Linux, and `uname -a` came back. Port 22, stock sshd. The Pi's log says `Accepted publickey for moto from 192.168.1.68`. The test sshd isn't needed anymore.

## Where the 65 seconds go

| Stage | Seconds |
| --- | --- |
| Startup (loading keys, etc.) | 0.6 |
| TCP connect | 0.2 |
| Curve25519 key generation | 5.6 |
| Waiting on the server | 1.3 |
| Curve25519 shared secret | 19.6 |
| ed25519 verification of the host key | 26.7 |
| Round trip | 1.2 |
| ed25519 signature for authentication | 7.2 |
| Run, output, disconnect | 2.0 |
| Total | 65.0 |

59 seconds of crypto, 5 seconds of network and plumbing. We're making a CPU from over 40 years ago do 2000s-era elliptic-curve crypto, so that's about what you'd expect. 15 minutes became 65 seconds.

What it can't do yet:

- Interactive sessions. Right now ssh.x doesn't read the keyboard. It runs one command and comes home.
- It skips the host key check (`-y -y`).
- The randomness is weak. It just mixes in the timer, so don't use it for real keys.
- `-v` causes a bus error.

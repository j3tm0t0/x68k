[Previously]({{ site.baseurl }}{% post_url en/2026-10-22-x68000z-diary-12 %}): I ssh'd out from the Z, and Claude Code on raspi5 ran on the Z's screen. The main cause of the slowness wasn't drawing. It was parsing and crypto. In this series, an AI (Claude) does almost all of the code and research.

## The keyboard goes on the Pico too

Up to now, the Z had two Pico Ws plugged into it. One handled the disk, the network and the crypto accelerator. The other ran picokbd (send keys over UDP from raspi3, and it pretends to be a USB keyboard and types them into the Z). I was listing the things I wanted to do, and then I remembered: "Oh right. Combine the USB keyboard."

One firmware, hosting both a disk (MSC) and a keyboard (HID). The big worry was whether the Z would accept a USB device that is "a disk and also a keyboard." There's no way to know without plugging it in.

It accepted it. picokbd's commands (UDP 6869, `x68key`) work unchanged. So now there's one Pico in the Z, and the AI no longer needs a second Pico to type on the Z.

## The emoji are black and white

After last time, we bumped the emoji count up to 300. I was watching and asked: "Wait, are emoji black and white?" In the Mac tests they had color. But "the Z's screen is black and white."

The AI's theory: CRTC simultaneous access, which we'd added in last time's speedup (a trick that writes to all four planes at once). Emoji have a different color in every pixel, so the code turns simultaneous access off and writes one plane at a time. Except on the real Z, "off" wasn't actually off. So whichever plane you wrote to, the same pattern landed in all four, and you got a white silhouette. On XEiJ it turns off properly, which is why the tests never showed it.

I tried a build that doesn't use simultaneous access at all, and "it came out in color." The fix: always set CRTC R21 to 0 before drawing.

## Four screens

I'd been saying this for a while: "Be nice if I could switch between several, like Alt+F1/F2 on the Linux console." I know real multitasking is off the table. "I mean, I could just use tmux."

What the worker built was a way to open up to four shells inside one ssh connection. SSH can already carry multiple channels over a single connection. CTRL+F1 through F4 (or `Ctrl-]` followed by a number) switches between them, and if that number isn't open yet, it opens a new shell right there. Works in both VT100 (`-t`) and zterm (`-Z`) modes.

I was worried the CTRL+F keys wouldn't make it through from the Z's USB keyboard intact. They did. "Nice, it switches really smoothly."

While I was at it, I asked: "I'd like an English key layout, please." The Z reads the keyboard as Japanese layout, so on a US keyboard the symbols end up in the wrong places. We had the network-startup batch file load KeyWitch, the same one the x68kcli image uses, as its very first step.

## Cannot boot from disk

Right now, the Pico reads an HDS (a disk image) over Wi-Fi from an SMB share on raspi3, and presents it to the Z as the boot disk. If the Pico's SMB connection isn't ready when the power comes on, the Z stops at "Cannot boot from disk."

I asked: "If the SMB mount doesn't make it in time, what if we hand over a boot sector that just reboots, like the settings UI does?" Then I worried about it myself: "Would the SCSI ROM cache it, though?"

The AI said that worry was exactly the biggest trap. A layer inside the Z remembers sectors it has read, and it doesn't forget them on a soft reset (that's the same reason we kept pulling stale replies back in [Diary (9)]({{ site.baseurl }}{% post_url en/2026-10-21-x68000z-diary-9 %})). Show it a fake reboot sector, and the Z might keep reading the remembered fake even after SMB comes up.

Then the worker read the firmware code and found the cause further upstream. When SMB wasn't ready and the HDS couldn't be read, the Pico didn't return an error. **It returned zero-filled data to the Z as a successful read.** The signature at the top of the boot sector comes back as zero, so you get "Cannot boot." And those zeros stay lodged inside the Z.

## Make it wait

The worker went with a much more straightforward approach. Until the HDS can be opened, the Pico answers the Z with "NOT READY." That's a reply that exists within the SCSI rules, and when the Z sees it, it waits and asks again. We also stopped returning zeros on a failed read.

I stopped raspi3's SMB on purpose for 60 seconds and turned on the Z.

| | |
| --- | --- |
| Power-on to the Z coming to read the boot sector | about 28 s |
| Times the Pico answered "not ready" | 8 |
| Power-on to Human68k booting | about 87 s |

No "Cannot boot from disk."

## The waiting screen

Once it stopped dying, the pitch-black screen during the wait started to bother me. "Yeah, I want something on there." "Can it at least show some ASCII art?" "And maybe something BIOS-like, 'to enter setup mode, press...'?"

Here's what the worker built. The Pico keeps a copy of the first 16KB of the HDS. While waiting for SMB, it hands the Z that copy with only the boot program swapped out for a "waiting program" (two stages, around 1.2KB). The waiting program draws the status on screen and keeps asking the Pico "ready yet?", dodging the cache as it goes. Once the HDS opens, it compares the copy against the real first 16KB. If they match, it hops over to the real boot. If not, it says "The HDS has changed. Please power-cycle the Z." and stops. Press S, and you get the settings screen (Wi-Fi, SMB, HDS) that x68kzremotedrv already had.

My review of the first version: "I want it a bit cooler. Functionally, though? Perfect."

## The X logo

"I kind of want it to look like, you know, the X logo."

The worker came back with a mockup (a PNG) of an X mark made of four triangles, drawn in dots on the text screen. I looked at it for a while, and then it hit me. "SHARP's logo is a trademark, isn't it. That's a problem."

Yep. The X68000 logo belongs to SHARP. I'd rather not ship a lookalike in a public repository. The closer it gets to the real one, the riskier it gets. Also, "I don't love the colors."

Fine. Make my own logo, then. It needs a name too. My first idea was "picoboot," and I was told that's the same name as the Pico's flashing mechanism. So: **Pico Z Loader**. I had a few logo candidates laid out on a design canvas and picked the one with a Z inside a power-symbol ring.

## The progress line

![The Pico Z Loader waiting screen on a real X68000 Z: a Z logo inside a ring, Wi-Fi, SMB and HDS status, and a ◆ line at the bottom (later replaced with a real progress line)]({{ "/assets/z-pico-z-loader-wait.jpg" | relative_url }})

Once I saw it on real hardware, one more thing bugged me. The ◆ in `[Pico W] ━◆━ [X68000 Z]` at the bottom just moved every half second. It didn't represent anything. "I hate that it looks meaningful but isn't." So we turned the line into real stages. Four segments, Wi-Fi, SMB, HDS and boot. Finished stages are light blue, the current one is white, and while waiting for SMB, the segment grows in step with the time until the next reconnect attempt. As for the last label: "Let's not say 起動 (boot). Make it BOOT."

```
Wi-Fi ━━━ SMB ━━━ HDS ━━━ BOOT
```

Counting firmware patches, the waiting screen alone took 15 of them and an hour and ten minutes. Flash, stop SMB, power on. Repeat. At the end, I did an ordinary cold boot. No waiting screen. It just boots. "Nice. It's stable, and the boot looks cool."

## A different name

With that wrapped up, I thought about what to do with the Pico firmware going forward.

The foundation of the Pico firmware is yunkya2's x68kzremotedrv. Presenting a disk on the Z's USB, reading the HDS over SMB, the settings screen: we only got this far because that foundation was there. But as I kept piling on networking, a crypto accelerator, a keyboard and boot waiting, it turned into something quite different from the original. If I shipped it under the original's name, nobody could tell them apart, and bug reports about the parts I added might end up with yunkya2.

So once the version that reads from an SD card is done, I'll release it under a different name. The name is the same as the waiting screen: Pico Z Loader.

The code inherited from x68kzremotedrv keeps yunkya2's copyright notices, and the README will say what this foundation made possible. Any fixes that look useful upstream, I'd like to send back upstream. The version that reads the HDS from an SD card has to wait until I buy the parts.

## Not yet

- The waiting screen's subtitle still says "x68kzremotedrv." That comes off when it ships under the new name.
- Where the Z remembers the sectors it has read (the theory: the file cache of the Linux inside the Z) is unconfirmed. Grabbing the Pico's logs with a Debug Probe should tell us.
- As long as we wait on SMB, booting depends on the network. The real fix is booting from an SD card, so there's nothing to wait for.
- Japanese input (FEP) is still on hold.

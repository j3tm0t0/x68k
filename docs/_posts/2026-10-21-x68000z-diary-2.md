前回のあらすじ: AI が CLI 環境を作り、僕は USB メモリを抜き差しし続けた。もう嫌だ。

Z には RS-232C がある。手元には Raspberry Pi がある。つなげばいい。

## 3 本の線

Z の RS-232C と Pi の UART を、TX・RX・GND の 3 本で直結した。これは僕の仕事だ。AI には手がない。

Z 側の通信ソフト MuTERM から Pi にログインするところまでは、あっさりいった。ただ MuTERM は VT100 ではないので、bash の bracketed paste (`ESC [ ? 2004 h`) が画面にそのまま出る。AI が TERM=ansi のときだけ切る設定を Pi の `.bashrc` に足した。

これで Z から Pi を触れる。でも欲しいのは逆向きだ。Pi から Z にファイルを送りたいし、コマンドを打ちたい。つまり Z に TCP/IP が要る。

## PPP

Human68k の TCP/IP といえば計測技研の ESP/X だ。AI は、その inetd.x を改良した xip.x (K.Shirakata 氏の β5) と、IIJ-PPP の Human68k 移植を探してきて、Pi の pppd とつないだ。

Z から ping 8.8.8.8 が返ってきた。やった。ただし:

- 速さは約 8kbps。
- 相手の pppd がいないと、ppp.x が Phase: Dead で固まる。BREAK も効かない。つまり電源ボタンの出番で、つまり僕の出番だ。

AI は、pppd が送ってくる LCP を先に受け取ってから ppp.x を起動する `pppwait.x` を書いて、固まる方はしのいだ。速さはどうにもならない。

## SLIP ドライバがないなら書けばいい

PPP より軽い SLIP ならもう少し出るはずだ。ところが Human68k には、公開された SLIP ドライバがない。

ないなら書けばいい。書くのは AI だけど。

- **slip.sys**: xip.x からは Ethernet カード (`/dev/ep0`) に見えるデバイスドライバ。
- **slipd.x**: 常駐スレッド。IOCS でシリアルを読み書きし、SLIP をほどいて xip.x に渡す。

最初の版は、SCC の割り込みを slip.sys が自前で横取りしていた。結果、xip.x のヒープとスタックが壊れ、バスエラー、アドレスエラー、画面のスクロール崩れを一通り拝んだ。AI は方針を変え、ROM と RSDRV.SYS の割り込み処理に任せて ppp.x と同じく IOCS で読み書きする形にした。そこから先は落ちていない。

X68000 Z の UART は、IOCS で設定した速度しか効かない。そこで `_SET232C` を直接呼ぶ `rsspeed.x` も作った。38400bps の線で実効 21.9kbps、取りこぼし 0%。PPP の 3 倍だ。

## rcmd

TCP/IP が通ったら、Z の上で `rcmd.x` を待たせておく。TCP 2323 でコマンドを 1 行受けて zsh で実行し、出力を返すだけの小さなサーバだ。Pi の側は bash の `/dev/tcp` だけで書かれている。

```sh
x68 'ls -l /usr/bin'          # Z で実行して結果を表示
x68put hello.c /home/hello.c  # ファイルを送る (4KB を超えたら tar.gz にして送り、Z で展開)
```

ここで Human68k の洗礼を受けた。Human68k は、前面のプログラムが DOS コールで待っている間、裏のスレッドを動かしてくれない。rcmd が「接続が来るまで待つ」を素直にやると、接続のパケットを処理する xip.x が止まる。だから接続は永遠に来ない。待つことで、待っているものが来なくなる。禅問答か。

AI は待ちをポーリングにして、`_CHANGE_PR` で自分から CPU を譲るようにした。

これで、AI が Mac で書いて Pi から送り、Z で make して試す、が僕の手を借りずに回るようになった。僕の仕事が 1 つ減った。喜ぶべきかどうかは、まだ分からない。

前回のあらすじ: Mac の中の 68000 で xip.x のロックを差分テストにかけたら、元のバイナリの競合が 2 つ見つかった。直して 380kbps。このシリーズでは、コードも調査もほぼ全部 AI (Claude) にやらせている。

## 交換の失敗は、律速ではなかった

前回の 20 分の連続試験では、netpipe の交換 32,008 回のうち 28 回が失敗し、そのたびに 1 秒待っていた。AI が内訳を取ると、28 回とも「キャッシュに残った古い応答に 64 回続けて当たった」だった。

原因は飛び方だった。古い応答に当たると、読み出し領域の中を 16MB 先に飛ぶ。ところが領域は 480MB しかないので、30 回飛ぶと一周して同じ場所に戻る。64 回試しても、見ているのは 30 か所だけだった。今日は何十回もリセットしたので、Z のキャッシュには領域の大部分が残っていて、その 30 か所が全部キャッシュ済みだと抜け出せない。

飛び先を疑似乱数にした。ついでに、読み込みに失敗しても同じ応答を読み直せるようにした (Pico は次の要求が来るまで応答を持っている)。もう一度 20 分回すと、失敗は 0 回、古い応答の読み直しは 2,551 回から 605 回に減った。

そして、送れた量は変わらなかった。218 回 対 220 回。1 秒の待ちは律速ではなかった。直す価値はあったが、速くはならなかった。こういうこともある。

## 1 周に 2 回

プロファイルを取り直すと、xip.x の 3 本のスレッドが `_CHANGE_PR` で CPU を譲り合っている部分が、CPU の約 25% を占めていた。

僕は「もう限界?」と聞いた。AI は候補を並べ、一番大きいのはスレッドの作りだと言った。暇なときは眠らせて、仕事が来たら起こす。ただし、前に slipd.x で「眠らせたら、そのうち起こされなくなった」ことがあり、危ない。

逆アセンブルしてみると、もっと手前に問題があった。

- 受信スレッドは「受け箱を見る → 受信の処理 (0x26B0) を呼ぶ → `_CHANGE_PR` → 最初に戻る」を回り続けている。
- ところが受信の処理も、最後に自分で `_CHANGE_PR` を呼んでいた。
- タイマースレッドも同じ。

1 周ごとに、2 回譲っている。

処理の中の 2 か所の `bsr` を `nop` に置き換えた。6 バイト。スレッドの繰り返しの中では今までどおり譲るので、ほかのスレッドが待たされることはない。`patchxip.py --yield`。

## 夜の Wi-Fi

さっそく実機で測ると、15〜32KB/s。前より遅い。パッチを外しても 15〜32KB/s。

数時間前は 46〜50KB/s 出ていた。Pi は暇で、Pico への往復だけが平均 11ms、ときどき 64ms に跳ねていた。夜になって Wi-Fi が混んだらしい。この状態では、12% の差も揺れに埋もれる。

僕が帰ってきた深夜、Pico への往復が 5ms に戻ったところで、パッチのあり・なしを交互に 2 回ずつ測った。

| xip.x | 200KB × 5 回 (KB/s) |
| --- | --- |
| `--yield` なし | 48.8 50.0 51.2 50.0 50.0 / 51.2 50.0 50.0 51.2 51.2 |
| `--yield` あり | 56.9 55.4 55.4 55.4 56.9 / 56.9 55.4 56.9 56.9 55.4 |

12% 速い。56.9KB/s は約 455kbps。

画面を見ていた僕は「夢の 500kbps 出てんじゃん!」と言った。AI は「約 455kbps です。500kbps には少し届いていません」と訂正した。

僕は言った。「瞬間値だと出てるよ。ログ見てごらん」

AI がシリアルのログを読むと、Z の rcmd.x はこう書いていた。

```
rcmd: put NUL 204800/204800 bytes in 3.05s (67147 B/s = 537.1 kbps)
```

AI が見ていたのは、Pi 側の x68put の数字だった。TCP の接続、コマンド行、終わりの印を待つ時間まで含めて割っている。Z 側の数字は、データの最初のバイトから最後のバイトまで。データだけなら 537kbps。夢は叶っていた。訂正した方が間違っていた。

## プロファイラで Z を固める

`--yield` の効果は、Wi-Fi に左右されない方法でも確かめたかった。プロファイルで、譲る処理の割合が減ったかを見ればいい。

`zprof.x on` を打つと、記録が 0 件だった。zprof.x は、メモリの中で最初に見つけた「SLPDPROF」の印を記録の置き場所に使う。ところがメモリには、ディスクバッファや前の起動の残骸にも、同じ印のコピーが残っている。今回は残骸を拾っていた。

AI は「見つかったもの全部で記録を始める」ように直した。Z は固まった。残骸の場所を今使っている誰かのメモリに、「記録開始」を書き込んだのだ。シリアルのログには contee.sys 経由で、エラーのダイアログがそのまま流れてきた。

```
(SR=$2009:PC=$0000EAD4)
　　　 中止＜Ａ＞ 再実行＜Ｒ＞ 無視＜Ｉ＞ ？
```

遠隔キーボードで「中止」を押しても、同じダイアログがまた出る。外出から帰った僕が電源を落とした。

今の zprof.x は、`_GET_PR` でスレッド「npd」の受け箱の番地を得て、その直前 128KB の中だけを探す。受け箱は npd.x 自身の .bss にあるので、その近くにあるのは本物だけだ。

## 代返

前回、僕は「Pico が ping に返せばいいんじゃない?」と言った。代理 ARP ならぬ、代理 echo。代返だ。

ESP/X は、TCP を閉じたあとに外から ping を受けると止まる。だから Pico は Z 宛ての ping を捨てていた。今回、捨てる代わりに Pico が echo reply を作って返すようにした。送り元と宛先を入れ替え、TTL とチェックサムを直すだけだ。

ひと工夫して、返事を送るのは Z の npd.x が次に netpipe で交換しに来たときにした。Z が固まっていれば交換は来ないので、返事も来ない。代返でも、ping で Z が生きているかは分かる。

```
5 packets transmitted, 5 received, 0% packet loss
rtt min/avg/max/mdev = 7.033/43.212/67.706/22.624 ms
```

そのあとも rcmd は生きていた。

## いまのところ

| 段階 | 速度 |
| --- | --- |
| PPP (RS-232C 38400bps) | 約 8kbps |
| SLIP (RS-232C 38400bps) | 21.9kbps |
| netpipe 最初の版 | 約 32kbps |
| MSS 1460 | 約 70kbps |
| slipd.x の改善 | 136kbps |
| SCSI の郵便受けを直接 | 176kbps |
| SLIP をやめる (npd) | 約 290kbps |
| xip.x `--timer` | 315〜364kbps |
| xip.x `--lockfix` | 364〜381kbps |
| ウィンドウ 16KB | 約 400kbps |
| xip.x `--yield` | 約 455kbps (Z 側でデータだけを測ると 537kbps) |

最初の PPP から約 57 倍 (データだけなら約 67 倍)。

`--yield` 入りで 20 分の連続試験をすると、200KB を 255 回 (51MB) 送って失敗 0 回。そのうち 51 回は乱数を B: に書いて照合し、全部一致した。`--yield` なしでは同じ 20 分で 218〜220 回だったので、約 16% 多く送れている。画面を見ていた僕は「めちゃんこ安定してる」と言った。

ほかに決めたこと:

- CONFIG.SYS の PROCESS (タイムスライス) は 20。50 と速さは同じで、ping が速い。僕は ping より実効スループットを重視するが、同じなら速い方がいい。
- イメージを作るときの既定は、`--timer --lockfix --yield` (XIPTIMER / XIPLOCK / XIPYIELD)。npd のときの `netup` は、ウィンドウ 16KB、ヒープ 1MB。

500kbps は越えた。次は何を目指そう。言うのは簡単だ。

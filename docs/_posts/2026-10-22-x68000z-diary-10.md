前回のあらすじ: xip.x のスレッドが 1 周に 2 回譲っていたのを直して、500kbps を越えた。次は何を目指そう、と書いた。このシリーズでは、コードも調査もほぼ全部 AI (Claude) にやらせている。

## 言ってみた

「x68k 用の ssh は作れるだろうか。vt100 対応」

深夜 1 時に僕が言ったのはこれだけだ。ネットワークは速くなったし、ほかにやることもない。

AI の見立ては「作れる」だった。小さな SSH 実装の dropbear は C で書かれていて、X68000 のクロスコンパイラ (elf2x68k) には BSD ソケットのライブラリも付いている。問題は 2 つ。1 つは Human68k に無いもの (fork、シグナル、/dev/urandom、端末) の穴埋め。もう 1 つは暗号の重さだ。SSH の鍵交換は楕円曲線 (Curve25519) で、10MHz の 68000 には荷が重い。

僕は分担を指示した。「worktree を切って、サブエージェントにやらせておいて。ssh でなんらかのコマンドが叩けるまで。端末エミュレーションは別のエージェントで並行に」

AI が AI を 2 人立てて、僕は寝た。

## RST の犯人は TOS だった

朝起きて記録を読むと、ssh 担当はまずソケットの煙試験から始めていた。dropbear を動かす前に、ライブラリが xip.x 相手に素で使えるかを確かめる。結果は妙だった。

- 接続はできる。
- 送ったデータは相手に届き、ACK も返る。
- ところが相手からデータが届くと、xip.x が RST を返して接続を切る。

純正の telnet.x でも同じだった。ずっと前に「telnet.x が使えない」と思っていた理由は、これだったのか。

AI は Pi に素の Python のリスナを立てて比べた。これだと完全に動く。違いを 1 つずつ潰していって、最後に残ったのは IP ヘッダの **TOS** だった。sshd は送るパケットに DSCP EF (TOS 0xb8) を付ける。xip.x は KA9Q NOS の子孫で、TOS が 0 でない TCP のデータを捨てる。ハンドシェイクのパケット (TOS 0) は通るのに、最初のデータで RST していた。

直し方は 2 つあった。

- Pi の sshd に `IPQoS none` を指定する。相手を選ぶが、すぐできる。
- Z 側のドライバ npd.x で、受け取ったパケットの TOS を 0 に書き換える。チェックサムも直す。

ssh 担当は前者で試験用の sshd をポート 2222 に立てて先へ進み、僕の相手をしている方の AI が後者を npd.x に入れた。これで素の sshd にも通る。

## 5 分の掛け算

dropbear は 2 時間足らずで ssh.x (233KB) になった。接続、バナー交換、鍵交換の開始までは通る。そこで止まった。

止まったのではなく、計算していた。Curve25519 の scalarmult が、**1 回 5 分**。ハンドシェイクにはこれが 2 回と、ed25519 の署名検証と署名が要る。合計 15〜20 分。sshd は 2 分で接続を切る。

僕は「速度遅くてもいいから、確実に繋がる手段で検証しよう」と言った。最悪 Pi 経由の中継でもいい。telnetd のふりをする honeypot を Pi に立てて telnet からでもいい。単純な問題から切り分けよう。

ssh 担当は、試験用 sshd の猶予を 1 時間に延ばして、まず 1 回の完走を目指した。

## 寝ている間に

ところが、端末担当の方が先に VT100 を終えていた (こちらは次回に書く)。手が空いたので、暗号を速くする仕事を取った。

dropbear の Curve25519 は TweetNaCl 版で、2^255-19 の体の数を 64bit の整数 16 個で持つ。掛け算 1 回で 64bit の積を 256 回。68000 には 64bit の掛け算が無いので、全部ライブラリ関数の呼び出しになる。

端末担当は、68000 の `MULU.W` (16bit × 16bit → 32bit) で済むように体の演算を書き直した。

| 版 | scalarmult 1 回 (XEiJ、10MHz) |
| --- | --- |
| 元 (TweetNaCl) | 118 秒 |
| C で MULU 向けに | 22 秒 |
| 68000 アセンブラの comba 乗算 | 10 秒 |
| 逆元を加算鎖に | 9.1 秒 |

意外だったのは、一番効いたのが掛け算そのものではなく、桁上げの処理 (car25519) だったことだ。64bit の足し算と右シフトを 16 桁分、掛け算のたびに 6 回。これを 32bit に変えただけで、半分以上が消えた。

次は ed25519 だ。署名の検証が 37 秒、署名が 19 秒。どちらも「基点 B の k 倍」を求めている。基点は固定なので、B の倍数の表 (25KB) を先に作っておけば、加算を 256 回から 64 回に減らせる。ref10 と同じやり方だ。署名は 3.3 秒、検証は 21 秒、さらに窓を使って 13 秒。鍵生成も同じ表で 9 秒から 2.7 秒。

正しさは、Mac の Python (cryptography) を正として、RFC の固定ベクタと乱数の入力で差分テストした。前回 xip.x でやったのと同じ発想だ。アセンブラの部分は Unicorn の 68000 で C の参照と突き合わせた。その差分テストが、桁上げの畳み込みに潜んでいたバグを 1 つ見つけている。

朝 4 時、ハンドシェイクは XEiJ で 27.9 秒になっていた。実機の Z は 2〜3 倍遅いので 70 秒前後。120 秒に収まる。

## 朝

起きたら Pico が Wi-Fi から消えていて、Z が固まっていた。電源を入れ直す。ついでに、Claude のセッションも切れた。ssh 担当の記憶は飛んだが、作業はブランチに残っている。新しい担当を立てて続けた。

続きはすぐだった。鍵交換も検証も通り、認証で止まる。

```
B:\dbcf.x: Failed loading keyfile 'b:\id_x68k'
```

鍵ファイルが読めない。ファイルはある。83 バイト。AI が Z で小さな試験プログラムを動かすと、読めたのは 81 バイトだった。

elf2x68k の C ライブラリは、ファイルを既定で**テキストモード**で開く。読むときに 0x0D と 0x1A を捨てる。83 バイトの二進の鍵に、たまたまその 2 つが 1 つずつ入っていた。`O_BINARY` を付けて直った。MS-DOS 時代の人なら「あるある」と言うところだ。

直すと今度は「Couldn't set nonblocking」。dropbear は標準入出力を非ブロッキングにしようとするが、Human68k の標準入出力はそれを受け付けない。ソケット以外では何もしないようにした。

```
B:\dbcf.x: Caution, skipping hostkey check for 192.168.1.108
Linux raspberrypi3 6.18.50+rpt-rpi-v8 #1 SMP PREEMPT Debian 1:6.18.50-1+rpt1 (2026-09-11) aarch64 GNU/Linux
Connection to moto@192.168.1.108:22 closed.
```

X68000 Z から Linux に ssh して、`uname -a` が返ってきた。ポート 22 の、素の sshd だ。Pi のログには `Accepted publickey for moto from 192.168.1.68` と残っている。試験用の sshd は、もう要らない。

## 65 秒の内訳

| 段階 | 秒 |
| --- | --- |
| 起動 (鍵の読み込みなど) | 0.6 |
| TCP 接続 | 0.2 |
| Curve25519 鍵生成 | 5.6 |
| サーバの応答待ち | 1.3 |
| Curve25519 共有秘密 | 19.6 |
| ホスト鍵の ed25519 検証 | 26.7 |
| 往復 | 1.2 |
| 認証の ed25519 署名 | 7.2 |
| 実行、出力、切断 | 2.0 |
| 合計 | 65.0 |

59 秒が暗号で、ネットワークと配管は 5 秒。40 年以上前の CPU に、2000 年代の楕円曲線暗号をやらせているのだから、こんなものだろう。15 分が 65 秒になった。

まだできないこと:

- 対話。今の ssh.x はキーボードを読まない。コマンドを 1 つ実行して帰ってくるだけだ。
- ホスト鍵の確認を飛ばしている (`-y -y`)。
- 乱数が弱い。タイマーを混ぜているだけなので、本番の鍵には使わないこと。
- `-v` を付けるとバスエラーになる。

## 次回

端末担当が作っていた VT100 は、漢字も絵文字も出る。これを ssh.x につなげば、Z で Linux のシェルが動く。言うのは簡単だ。

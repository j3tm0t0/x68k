[前回のあらすじ]({{ site.baseurl }}{% post_url 2026-11-07-x68000z-diary-17 %}): 「使ってると UNIX 使ってるんじゃないかって錯覚するくらいの感じにしたい」という目標で、AI の担当を最大 11 人同時に動かし、ドライブを 1 本の木に見せる mount.x と、UNIX 風のシェル zosh を作った。そこで週の利用上限に当たった。

今回はその続きだ。上限が戻ってからは、担当を 1〜2 人に絞って進めた。やり方も変えた。思いつきで直すのをやめ、「UNIX に慣れた人が 1 日使ったら、どこで UNIX じゃないと気づくか」を 200 個ほどのコマンドで洗い出す。それを直して、また洗い出す。これを 3 回繰り返した。2 日で 25 本ほどの PR をマージし、最後に Z の実機でも動かした。

## 200 個のコマンドで洗い出す

洗い出しは、担当の 1 人に「UNIX に慣れた人の 1 日」を想定してやらせた。ファイルを見る、パイプでつなぐ、探す、編集する、ジョブを動かす、アーカイブする、打ち間違える。完全な起動イメージを XEiJ (X68000 のエミュレータ) の SCSI から起動し、コマンドを 1 つずつキーで打って、画面 (テキスト VRAM) を読む。直すのは別の担当で、洗い出す担当は見つけたことを書くだけにした。

結果は、「どれだけ UNIX に見えなくなるか」の順に並べさせた。1 回目の一番上は「定番のパイプが動かない」で、`sort f.txt | uniq -c | sort -rn` を打つと、Sharp の SORT.X が日本語の使い方を出して終わった。

| 気づくこと | 1 回目 (11/07) | 2 回目 (11/08) | 3 回目 (11/09) |
| --- | --- | --- | --- |
| `sort` `find` `xargs` | Sharp の版が動く、`xargs` が無い | GNU の版が動く | `xargs -n1` の空行も直った |
| エラーの文 | `cat: nosuch: ありません` | `No such file or directory` | man も英語 |
| `sleep 100 &` | シェルが 100 秒止まる | すぐ戻る、`jobs` `kill %1` | — |
| `ls /` | 失敗する | 起動用のファイルが並ぶ | 隠し属性で片付いた |
| `ls -l` | `-rw--a` (Human68k の属性) | `-rw-r--r-- 1 moto moto` | 外部の `ls` も同じ形 |
| `pwd` | `A:/home/moto` | `A:/home/moto` | `/home/moto` |
| `echo $PATH` | 空 (小文字の `path` だけ) | `/usr/bin:/bin:...` | — |
| `less` | 壊れている | GNU less が動く | 短いファイルで止まる → 直した |
| `file f.txt` | 無い | バスエラーで全体が止まる | 直った |

2 回目で、目立つ所はほとんど消えた。そのかわり、「直したら次の層が見える」こともよくあった。`ls /` が通るようになったら、今度は `human.sys` や `autoexec.bat` が一覧に並んで UNIX らしくなかった。`file` が入ったら、今度はそれがバスエラーで zos.x ごと止めた。

途中で 1 回、罠にも引っかかった。リーダー役の AI が作ったイメージで `sort` が Sharp のままになり、「直っていない」と慌てた。調べると、GNU のコマンドを集めたフォルダ (stage) が 10/21 に作ったままで、GNU の `sort` がそもそも入っていなかった。コードではなく材料が古かっただけだ。

## 直したものの中の、小さな話

直したものの多くは地味だが、原因を聞くと面白いものがいくつかあった。

**`less` が止まる。** 短いファイルを開くと、下の状態の行が出ず、`q` でも戻らず、CPU が 95% のままになる。less はファイルをテキストとして開いていて、C ライブラリ (newlib) が行末の CR を取り除いていた。ファイルの長さより読める量が少なくなるので、less は「まだ続きがある」と思って読み直し続けていた。MS-DOS 向けと同じく、バイナリで開くようにして直った。

**`make` の名前が壊れる。** Makefile の無い所で `make` を打つと、`h s.sh 1 2 longer args: *** No targets...` のように、前に打ったコマンドの残りが `make` の名前として出た。Human68k で引数を渡す約束 (HUPAIR) では、引数の後ろにコマンド名 (argv[0]) を置く。zosh はこれを置いていなかったので、make はメモリに残った前の文字列を自分の名前として読んでいた。

**`touch "with space"` が `with` を作る。** zosh は名前を切っていなかった。Human68k の FAT のドライブが、名前を空白で切っていた。これは直せないので、黙って `with` を作るのをやめ、`Invalid argument (this drive cuts names at a space)` と断るようにした。前からある別のファイル `with` を上書きしないよう、作る前にも確かめている。

**`~` が上線に見える。** X68000 のフォントでは、`~` (0x7E) の字の形が上線 (‾) だ。zos.x のペインと ssh.x は前から自前の波線で描いていたが、ペインの外は上線のままだった。字の形を差し替える常駐プログラムはあったのに、起動イメージに入っていなかった。

**子が落ちるとペインごと止まる。** 子のプログラムがバスエラーで落ちると、そのペインが戻らなくなった。試験台では起きず、完全なイメージでだけ起きる。担当が XEiJ で 5 つの版を比べて絞り込んだところ、前回入れた zosh の Ctrl+C の処理が原因だった。DOS コールで Ctrl+C の処理先を入れ替えると、戻した後でも何かが残っていた。何が残るのかは今も分からない。だが、プロセス管理の領域と Human68k の作業領域に直接書く形に変えると、起きなくなった。

## 外部コマンドはなぜ遅いか

打っていて一番「UNIX じゃない」と感じるのは、実は速さだ。XEiJ (10MHz) では、外部コマンド 1 つに 0.2〜0.4 秒、`ls -l /usr/bin | wc -l` のような 5 段のパイプで約 3 秒かかる。そこで、zosh に時間を測る仕掛けを一時的に入れさせ、`ls.x` を 20 回動かして内訳を取った。

| 段 | 1 回の時間 | 割合 |
| --- | --- | --- |
| 読み込みとリロケーション (`_EXEC`) | 0.161 秒 | 約 70% |
| PATH の検索 (`_PATHCHK`) | 0.044 秒 | 約 19% |
| 全ドライブのカレントディレクトリの控えと戻し | 0.010 秒 | 約 4% |
| 子に渡す環境変数を作る | 0.007 秒 | 約 3% |

一番大きいのは、Human68k がプログラムを読み込み、読み込んだ番地に合わせてアドレスを書き換える (リロケーション) 時間で、これは zosh からは減らせない。次が PATH の検索で、5 つのディレクトリを毎回頭から探していた。こちらは bash の `hash` と同じく、一度見つけたコマンドの場所を覚えて、次から検索を省くようにした。これで 1 回あたり 17% 速くなった。

読み込みの時間にも、まだ縮める余地がある。GNU のコマンドには、リロケーションを速くする仕掛け (fastreloc) を前に入れてあるが、X68000 の定番のコマンド集 ITA TOOLBOX には、まだ入っていない。次は ITA TOOLBOX にも fastreloc を入れる。

## Z の実機で動かす

最後に、Z の実機で動かした。起動イメージ (1GB) を Pico に挿した microSD に書き込み、SCSI のハードディスクとして起動する。書き込みは Pico の Wi-Fi 越しで、約 700KB/s で、イメージ 1 つに 24 分かかる。

最初のイメージは起動したが、起動して 45 秒ほどで、担当が Z を操作できなくなった。担当は Pico に UDP でキーを送って Z を操作している。ところが、イメージの設定で Z の IP を Pico と同じ `192.168.1.4` にしていた。そのため、Z のネットワークが動き出すと、Pico 宛てのキーを Z が受け取ってしまう。README に書いた設定例の IP アドレスが間違っていたので、`192.168.1.68` に直し、「Pico と同じ IP アドレスにしない」と書き足した。

IP アドレスを直した 2 つ目のイメージでは、次のことを確かめられた。

- 電源を入れてからプロンプトまで 41〜45 秒 (11/07 は 51〜56 秒)。
- `ls /`、`pwd`、`file`、`xargs -n1`、`ps`、`top`、ペインの分割、GNU の `ls --color` の色。
- `curl -I http://example.com` で HTTP の 200 が返った (TCP の処理は Pico が担う)。

実機でだけ見つかった問題もある。`less` でファイルの中身が画面の下のほうに出る。`top` は `q` を押しても、次の更新 (約 30 秒後) まで抜けない。どちらも担当が直している。

## 上限の後の進め方

前回の最後に週の利用上限に当たったので、今回は同時に動かす担当の数を減らした。担当は基本 2 人で、zosh を直す担当と、試験や起動イメージの周りを直す担当だ。リーダー役の AI は 30 分ごとに見回り、PR ができていれば codex (OpenAI のコードレビュー) にかけ、大きな指摘がなく CI が全部通ればマージする。Human68k の内部に直接書くような危ない変更だけ、Anthropic の別のモデル Fable にもレビューさせた。

やってみて分かったのは、担当がよく止まることだ。「試験の結果待ち」と言ったまま、実は何も動いていない。洗い出しが終わって 2 時間半たっても、結果を書いていない。見回りでは PR だけでなく、XEiJ が動いているかや作業中のファイルの更新時刻も見て、止まっていれば声をかけるようにした。

この 2 日の元の目標は、まだ達成したとは言えない。「錯覚するくらい」かどうかは、結局僕が触って決めることだからだ。その前に、X68000 Z 以外の X68000 の実機でも同じイメージが動くかを試した。

## Compact XVI の BlueSCSI で動かす

夜、X68000 Compact XVI に BlueSCSI v2 をつないで、同じイメージを起動してみた。BlueSCSI v2 は Raspberry Pi Pico を使って SCSI のハードディスクをまねる基板で、SD カードに置いたイメージファイルを SCSI のディスクとして見せる。うちのは外付けの DB25 版だ。

Compact XVI (以下 XVI) の外付け SCSI 端子は、ハーフピッチ 50 ピンのリボン形だ。手元の変換アダプタ (Arvel AA904) は同じハーフピッチ 50 ピンでも櫛形なので挿さらない。変換アダプタを探し回り、ヤフオクで DB25 とリボン形をつなぐものを見つけた。

![BlueSCSI v2 (DB25 版) と、DB25 からハーフピッチ 50 ピン リボン形への変換アダプタ]({{ "/assets/xvi-bluescsi.jpg" | relative_url }})

最初は、電源を入れても画面が真っ黒のままだった。SD カードを Mac で見ると、BlueSCSI が起動のたびに作るはずのログ (`log.txt`) が無い。BlueSCSI に電源が来ていなかった。DB25 版は SCSI のケーブルの 25 番ピン (TERMPWR) から電源を取るが、XVI とこのアダプタの組み合わせでは、そこに電源が来ないらしい。そこで Pico の USB を Raspberry Pi 5 につないで給電した。

USB をつなぐと、今度は BlueSCSI が USB ディスクとして起動し、その間は SCSI に応答しない。Raspberry Pi 5 で `eject` すると、SCSI のディスクに戻る。USB 経由でログも読めるので、XVI が送ってきた SCSI のコマンドを Raspberry Pi 5 で 1 つずつ確かめられる。

ここで、作業を任せていた AI が失敗した。ログを読む端末のエコーを切っていなかったので、BlueSCSI が出した文字がそのまま BlueSCSI に送り返された。BlueSCSI はシリアルから来た 1 文字をコマンドとして受け付けるので、デバッグ表示の切り替えや再起動の確認が何十回も出た。幸い、再起動はしなかった。この直後に起動したときは、XVI が Inquiry (ディスクの種類を問い合わせるコマンド) の返事を受け取れずに止まった。エコーのせいかどうかは分からない。BlueSCSI を挿し直してからは、一度も止まっていない。

切り分けのため、最初は起動に要るファイルだけを入れた 100MB の素の Human68k を書いた。これが起動したので、次に Z 用に作った 1GB の Z-OS のイメージを、作り直さずにそのまま書いた。これも起動した。

![Compact XVI で動く Z-OS。uname と ls /usr/bin の結果]({{ "/assets/xvi-zos.jpg" | relative_url }})

起動にかかる時間は、BlueSCSI のログで分かる。XVI が最初にディスクを読んでから、起動の最後の書き込みまでが 13 秒ほどだった。Z の実機は、電源を入れてからプロンプトまで 41〜45 秒かかる。XVI のほうは電源を入れてから最初にディスクを読むまでの時間を含まないので、この数字だけでは比べられない。ただ、触った感じでも XVI のほうがずっと速い。Z の SCSI のディスクは、実際には Pico と USB でつながっていて、SCSI のコマンド 1 回ごとに USB の往復が入る。XVI は SCSI で直接やり取りする。CPU も、うちの XVI は 24MHz で動いている。

画面には `X68000 Z` と出て、`uname -a` の機種名もホスト名も Z のままだった。起動時に機種を調べて名前を出すようにし、XVI ではプロンプトを `moto@xvi` にする。

## 次にやること

次は、BlueSCSI v2 の上で Pico Z Loader (Z の Pico で動かしている自前のファーム) を動かす。Z の Pico でやっている起動ディスクの切り替え、ネットワーク、SSH の暗号の計算を XVI でも使えるようにする。うちの BlueSCSI に載っているのは無線の無い Pico なので、ネットワークは BlueSCSI の USB を通して Raspberry Pi に中継する。暗号の計算を Pico に任せる仕組み (暗号アクセラレータ) は無線を使わないので、そのまま載せられる。Pico 2 W をソケットに挿して使える基板も設計してあるので、発注の準備を進める。

もう 1 つの課題は、テストのたびに 1GB のイメージを書き直すのに時間がかかることだ。BlueSCSI の USB 越しに書くと実測で 200KB/秒しか出ず、1GB に 70 分以上かかる。そこで、起動用のディスクを小さくし、`/usr/local` と `/home` を別の SCSI ID のディスクに分ける。`/home` を分けておけば、起動用のディスクを書き直しても履歴やファイルが消えない。

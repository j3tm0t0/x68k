X68000 Z の日記とは別に、実機の X68000 Compact XVI の日記を始める。Z の日記と同じく、コードと調査はほぼ全部 AI (Claude) にやらせている。

## 届いたもの

X68000 Compact XVI (CZ-674C) を手に入れた。主記憶は標準の 2MB。付いてきたのは本体、キーボード、Human68k 3.02 のシステムフロッピーと、使わないディスクが 2 枚。増設メモリ (I/O スロット用の 10MB) は別に頼んであって、まだ届いていない。

手元の道具は、DB-25 の RS-232C のクロスケーブルと USB シリアル。空きのフロッピーも頼んだが、届くのは夕方。SCSI のエミュレータはまだ無い。つまり、本体にソフトを入れる手段がシリアルしかない。

## 9 回のキー入力から

AI に、シリアルだけで道具を流し込む手順を作らせた。前日に、エミュレータの XEiJ で一連の手順が最後まで動くことを確かめてある。

1. X68000 のキーボードで `ctty aux` と Enter を打つ。9 回のキー入力で、コンソールが RS-232C に移る。ここから先のコマンドは Raspberry Pi から送る。
2. Pi が `COPY AUX RX.BAS` を打ち、20 行ほどの X-BASIC のプログラムを流し込む。
3. Pi が `BASIC RX` を打つ。このプログラムが、受信ツール rx.x (約 5KB) を 16 進数のテキストで 1 行ずつ受け取り、ファイルに書く。1 行ごとに合計を確かめ、合わなければ送り直させる。
4. あとは rx.x が、ファイルの送受信とコマンドの実行を受け持つ。

## 実機でつまずいたこと

XEiJ では通った手順が、実機では 3 か所で止まった。

**受け手のプログラムの途中が欠けた。** 最初の X-BASIC が「for に対応する next がありません」で止まった。届いた RX.BAS を表示させると、30 行目の途中から 40 行目の終わりまで、約 110 バイトが抜けていた。実機の RS-232C の受信バッファは 64 バイトしかない。フロッピーに書いている間に次の行が届いて、あふれていた。1 文字ごとに 20ms 待つように直して通った。

**16 進の行も欠けた。** 続く rx.x の受け取りでは、同じ行の送り直しが続いた。1 行 64 バイト分のデータは 16 進で約 140 文字になり、X-BASIC が読み切る前にバッファからあふれる。1 行を 16 バイト分 (約 40 文字) にして、バッファに収まるようにした。

**システムディスクを傷めた。** 状態が分からなくなったところで、僕が本体をリセットした。そのとき X-BASIC は RX.X を開いて書いている途中だった。次の起動から、A: に RX.X を作ろうとすると「ディスクの管理領域が破壊されています」と出るようになった。壊れたのは RX.X の管理情報だけで、起動はできる。名前を RY.X に変え、書く先を B: のディスクにして通した。

## ディスクを吸い出す

rx.x が動いたので、AI にフロッピーをセクタ単位で読む命令を足させた。付いてきた使わないディスク 2 枚を、まるごとイメージにして Mac に置いた。1 枚 1,232 セクタ、19,200bps で 12 分。

そのうちの 1 枚に、AI が用意した起動ディスクのイメージを書いた。Human68k、rx.x、SLIP 一式、Z-OS の zosh、ssh.x が入っている。書いたのは XVI 自身で、Pi から送ったデータを rx.x がフロッピーに直接書き、読み返して確かめた。

## 速さを上げる

RS-232C の速さを上げていった。150 セクタ (150KB) を読む時間で比べた。

| 速さ | 時間 | 速度 | 壊れたフレーム |
|---|---|---|---|
| 19,200bps | 87 秒 | 1.7 KB/s | 0 |
| 38,400bps | 53 秒 | 2.8 KB/s | 0 |
| 78,125bps | 29 秒 | 5.2 KB/s | 0 |

Human68k の設定で選べる速さは 38,400bps まで。X68000 の RS-232C は Z8530 (SCC) が 5MHz を分周して速さを作っていて、分周の値を 0 にすると 78,125bps になる。AI に rx.x を直させ、SCC の設定を直接書き換えるようにした。Pi 側の USB シリアルも、Linux の termios2 で標準に無い 78,125bps に合わせた。取りこぼしは出なかった。

## zmux

最後に、AI が作っている zmux を実機で動かした。シリアルの線 1 本に、次のものを同時に流す仕組みだ。

- チャネル 0: COMMAND.X のコンソール
- チャネル 1: キー入力の注入 (あとでマウスも)
- チャネル 2: リモートドライブ。Pi のディレクトリが XVI の C: に見える
- チャネル 3: ネットワーク。XVI の中で TCP/IP を動かさず、「このホストにつないで」「このデータを送って」という要求を流し、Pi が代わりにソケットを使う。ssh の鍵交換の計算や、Z-OS の zosh のセッションもここを通る

番号は XVI に近いものから順に並べた。画面とキーボード、ファイル、外のネットワークの順。

Pi 側はサーバーと、tmux のような画面に分かれている。画面にはタブとペインがあり、操作の最初に押すキー (プレフィックスキー) は、僕が普段の tmux で使っている Ctrl+X にした。

78,125bps で、コンソールは最初から動いた。TCP は、XVI の ssh.x から Pi の sshd につなぐと失敗した。ssh.x (420KB) をフロッピーから読む 10 秒あまりの間、zmux のフレームの送信が途切れ、XVI 側も Pi 側も 10 秒で接続を切っていた。この時間を 60 秒に延ばすと、パスワードを聞かれるところまで進んだ。鍵交換の計算は Pi に任せている。

リモートドライブは、ドライブは見えるのに `dir` が「ディレクトリが見つかりません」になった。XVI 側のドライバが、Pi から受け取ったファイルの情報を、書くべき場所より 20 バイト手前に書いていた。直すと、Pi に置いたファイルを XVI から読めた。

使いながら、細かいところも直させた。

- XVI を再起動すると、起動中の画面の出力も zmux のタブ 0 に出る。起動ディスクに、画面に出した文字をシリアルにも送るドライバを入れた。
- iTerm2 のウィンドウの題名に、XVI とつながっているかどうかを出す。
- Mac の Delete キーで文字が消えなかった。Delete が送る DEL (0x7F) を、タブ 0 では BS (0x08) に変えて送る。

## CPU の速さを測る

この XVI は、前面の切り替えで 10MHz と高速側を選び、高速側の 16MHz と 24MHz は背面のスイッチで選ぶ。XVI の高速側は本来 16MHz なので、24MHz は改造だと思う。本当に 24MHz で動いているかを、3 つの道具で測った。

- **cpupower.r**: 1992 年に TOMY 氏が作ったプログラム (X68000 LIBRARY にある)。XVI の 10MHz を 100% として、CPU や VRAM の速さを比べる。浮動小数点の演算パッケージ (FLOAT2.X) を先に組み込む必要があった。
- **RTCBENCH.X**: 以前、PSP 版の px68k (X68000 のエミュレータ) にクロックの切り替えを足したとき、AI に作らせた道具。時計 (RTC) で 5 秒ずつ測り、10MHz の 68000 の何倍かを出す。
- **cpuspd.x**: AI が作った道具。dbra の空ループが 2 秒に何回回るかを数える。

zmux を止め、キーボードの `A>` から測った。

| 設定 | RTCBENCH | cpupower | cpuspd |
|---|---|---|---|
| 10MHz | 9.43 MHz | 100% | 12.0 |
| 16MHz | 16.12 MHz | 168% | 20.4 |
| 24MHz | 23.46 MHz | 247% | 29.8 |

24MHz の改造は本物だった。RTCBENCH のメモリを読み書きするループも、レジスタだけのループとほぼ同じ倍率 (2.36 倍) になった。24MHz でもメモリの待ちで遅くなっていない。I/O の速さ (cpupower) は 24MHz でも 1.29 倍にとどまり、VRAM は 2.1〜2.3 倍だった。PSP 版の px68k で RTCBENCH を動かしたときの値 (16MHz で 1.60 倍、24MHz で 2.39 倍) とも、ほぼ同じだった。

zmux を動かしたまま測ると、24MHz の RTCBENCH は 17.43 MHz に下がった。zmux は、何も送っていないときも CPU を 26% 使っていた。XVI 側のスレッドが、仕事が無くても休まずにシリアルを見に行く作りだったため。cpupower は短い時間で測り終えるので、zmux があっても 247% のままだった。仕事が無いときはスレッドを眠らせるように、AI に直させている。

## まだ

- zmux が何もしていないときに使う CPU を減らす (直している途中)。
- 2MB では Z-OS が起動しない。AI に、作業用のメモリを必要になった時点で確保するように直させ、起動時に確保する分を 1.28MB から 0.28MB に減らした。エミュレータでの確認待ち。
- フロッピーは遅い。メモリが届いたら、起動時にディレクトリ構成ごとファイルをまとめたイメージを RAM ディスクに展開したい。イメージは Linux の initramfs と同じく、cpio 形式のアーカイブを LZ4 で圧縮する。各ドライブには `/mnt/a` などのパスでアクセスできるようにする。
- システムディスクは元のイメージから作り直す。
- マウスもキー入力と同じチャネルに載せる。

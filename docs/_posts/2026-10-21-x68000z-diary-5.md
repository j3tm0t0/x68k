前回のあらすじ: Wi-Fi 越しの TCP/IP が 68kbps で動いた。僕は AI (Claude) に「一晩回しといて」と頼んで寝た。それが間違いだった。このシリーズでは、コードも調査もほぼ全部 AI にやらせている。僕の担当は Pico の抜き差しと、電源ボタンだ。

## ログ: 朝、止まっている

朝起きたら、AI から報告が届いていた。Z が応答しなくなった、と。rcmd にも ping にもだんまり。

よし、落ち着こう。AI が夜のうちに並べておいてくれた事実はこうだ。

- テストを流し始めて約 22 分で止まっている。
- Pico の電源を入れ直すと直る。
- slipd.x の数え値を読むと、交換回数は **65,536** で止まっていて、リトライとエラーだけが増え続けている。

65,536。プログラマなら、この数字を見て偶然だとは思わない。

応答の読み出し領域 (返事を毎回 8 セクタずつずらして読む場所の範囲。端まで来ると先頭に戻る) は 0x80000 セクタで、1 回に 8 セクタずつ使う。0x80000 ÷ 8 = 65,536。つまり、読み出し領域をちょうど一周したところで止まっている。20ms おきに 65,536 回で 22 分。計算も合う。

犯人は Z の読み込みキャッシュだ。一周して同じ LBA に戻ってくると、Z の Linux は Pico に聞かず、覚えている 22 分前の応答を返す。番号が合わないので slipd.x は捨てて読み直すが、読み出し領域のどこを読んでもキャッシュ済みだ。詰んでいる。

Pico の電源を切ると直るのは、Z から見て USB ディスクが押し入れから消えるので、キャッシュも一緒に捨てられるからだ。Pico は無実だった。疑ってごめん。

## ログ: 読み出し領域を広げたら起動しない

AI の解決策は単純だった。読み出し領域を広げて、一周する前にキャッシュから追い出されるようにすればいい。ID6 を 4GB 近くにして、2GB 分を読み出し領域にする。僕は Pico を抜いて Mac に挿し、書き込んでもらって Z に戻した。

Z の答え: 「ディスクから起動できません」。

ああ、そう。

2GB に戻して、読み出し領域をその中に納めた。今度は起動はするが、CONFIG.SYS で B: のドライバを組み込むところで止まる。調べると、B: のドライバ (scsiremote.sys) は 0x200000 から 0x3fffff を応答の読み出しに使っていた。AI の読み出し領域がそこに重なっていて、ドライバ宛ての応答を netpipe が横取りしていた。ドライバからすれば、返事が永遠に来ない。そりゃ止まる。

ここで AI も僕も少し混乱した。僕は Pico を 4 回抜き差しした。重ならない場所に移したら、また「起動できません」が出たのだ。ところが同じファームのまま電源を入れ直したら、普通に起動した。

どうやら「起動できません」は LBA とは関係なく、電源を入れたときに Pico の Wi-Fi と SMB の接続が間に合うかどうかの競争らしい。4GB のときに起動しなかったのも、実はそれだったかもしれない。確かめてはいない。一度に変えていいのは 1 つだけ、という教訓を、また学んだ。

落ち着いた先は、書き込み 0x100000、読み出し領域 0x110000〜0x1ffff7 (約 480MB)。

## ログ: ブリッジで LAN に出る

UDP モードだと、Z は Pi の NAT の内側にいる。Z でサーバを立てようと思うと、ポート転送という面倒がついてくる。そもそも Pico は Wi-Fi につながっているのだから、Pi を通す意味があるのか?

ない。なので Pico にやらせる。

- Pico は Z の IP (192.168.1.68) 宛ての ARP に、自分の MAC で答える。代理 ARP だ。
- Wi-Fi から来たフレームのうち、Z 宛ての IPv4 だけを抜き取って Z に渡す。残りは Pico 自身の lwIP に回す。
- Z から来たパケットは、lwIP の `etharp_output` で宛先の MAC を引いて Wi-Fi に出す。

ARP は一発で通った。Mac から見ると、192.168.1.68 はたしかに Pico の MAC だ。ところが TCP がつながらない。Z は SYN を受け取って返事もしているのに、その SYN-ACK が電波に 1 つも出てこない。

原因は、笑ってしまうほど地味だった。xip.x は送るフレームを、Ethernet の最小長の 60 バイトまで詰め物で埋める。AI が書いた slip.sys は、その詰め物ごと SLIP で送っていた。そして Pico は「IP ヘッダの全長と受け取った長さが一致するものだけ通す」という、いかにも正しそうな検査をしていた。SYN-ACK は 44 バイトだから、全部捨てられる。UDP モードで問題にならなかったのは、Pi の Linux が余分を黙って切り捨ててくれていたからだ。

IP の全長で切って送るようにしたら、Mac から Z の rcmd につながった。Pi も NAT も通らずに。

ルーターの DHCP では、ダミーの MAC で 192.168.1.68 を予約しておいた。いつか誰かのスマホがこのアドレスをもらって、Z と喧嘩するのを防ぐためだ。

## ログ: リセットしても幽霊が出る

次は外に出る番だ。Z から ping 8.8.8.8。返事なし。ルーターまでは通るのに。

最初に疑ったのはルーターだ。同じ MAC に IP が 2 つ載っているのを嫌っているのではないか。Pi の wlan0 に 2 つ目の IP を足して同じ状況を作ってみたら、普通に外まで往復した。ルーターも無実。疑ってごめん、その 2。

こうなったら、中身を見るしかない。AI は slipd.x に、直近 64 パケットの先頭を残しておく仕掛けを足し、`ztap.x` で Z の上から表示した。出てきたのは、だいぶ奇妙な光景だった。

- Z が 8.8.8.8 に送った ping は 2 つ。
- 8.8.8.8 からの返事は、10 秒近く遅れて 7 つ届いている。
- しかも Z は、Pi 宛ての古い TCP のデータを、せっせと Pi に中継している。そんな接続はもう存在しないのに。

幽霊だ。過去のパケットが、今になって流れ込んでくる。

そして気づいた。試験のたびに、AI は遠隔キーボードの Ctrl+F11+Del で X68000 をリセットしていた。でもそれでリセットされるのはエミュレートされた X68000 だけで、外側の Linux が持っている読み込みキャッシュはそのまま残る。一方、リセット後の slipd.x は、応答の番号を 1 から数え直し、読み出し領域の同じ位置から読み始める。

つまり、前の回の応答が、番号まできっちり合った状態でキャッシュに待ち構えていたのだ。slipd.x はそれを「正しい応答」として受け取り、前の回に届いたパケットをそっくり再生する。xip.x は自分宛てではないそれを、親切にも中継する。ping の返事が 7 つ来たのも、前の回の分が混ざっていたからだ。

直し方は、番号の始まりと読み始める位置を、起動のたびに時刻から決める。これだけ。直した直後の ping:

```
64 bytes from dns.google: icmp_seq=0 time=200 ms
64 bytes from dns.google: icmp_seq=1 time=210 ms
```

X68000 Z が、Wi-Fi 越しに Google と話している。悔しいけど、ちょっと泣いた。

## ログ: いまのところ

数字を並べておく。Pi から Z の NUL に 200KB を送って計った (PPP とシリアルの SLIP は 100KB)。

| 方式 | 経路 | xip.x の MSS | 速度 |
| --- | --- | --- | --- |
| PPP | RS-232C 38400bps → Pi | 512 | 約 8kbps |
| SLIP | RS-232C 38400bps → Pi | 512 | 21.9kbps |
| netpipe (UDP) | Pico W → Pi | 512 | 約 32kbps |
| netpipe (UDP) | Pico W → Pi | 1460 | 67kbps |
| netpipe (ブリッジ) | Pico W → LAN | 1460 | 69〜71kbps |

シリアルの SLIP の約 3 倍。律速は今も xip.x で、1 パケット 100〜150ms が何に使われているのかはまだ分からない。

最後に、あの朝の再現試験をやった。200KB を休みなく送り続けて、読み出し領域を一周させる。480MB になったので、一周は 122,880 回目だ。

結果: 1 時間 7 分で 200KB × 150 回、失敗 0 回。交換は 141,626 回で、一周を越えても速さは 69〜71kbps のままだった。読み直しは 3 回から 6 回に増えただけ。古い応答に当たっても、ずらして読み直せば押し切れる。

22 分の壁は越えた。

残っていること:

- 電源を入れた直後の「ディスクから起動できません」。Pico の接続が間に合うまで Z に待ってもらう方法を考えたい。
- コンソールから ping.x を打つと、前面の ping.x が DOS コールで待つ間、裏の slipd.x に CPU が回らず、返事を取りこぼす。rcmd 経由なら通る。
- netpipe を足したファームは、パッチの形で [j3tm0t0/x68k](https://github.com/j3tm0t0/x68k) に置いた。

[前回のあらすじ]({{ site.baseurl }}{% post_url 2026-10-22-x68000z-diary-11 %}): Z から Linux の対話シェルが動いた。鍵交換は、隣の Pico に手伝わせて 12 秒。このシリーズでは、コードも調査もほぼ全部 AI (Claude) にやらせている。

## 1 FPS

対話シェルが動いたので、僕は当然のことをした。Z から Pi に ssh して、そこから Mac に入り、tmux に attach した。中では Claude Code が動いている。つまり、この日記を書いている AI との会話そのものが、X68000 Z の画面に映る。

映った。そして化けていた。「バックスラッシュ無し」が「バックスラッシュ嗳し」、「通る」が「北る」。かなは正しい。漢字だけが、ことごとく違う字になっている。

写真を見た AI は、すぐ当たりをつけた。「通」は 36 区、「北」は 43 区。ちょうど 7 区ずれている。X68000 の CGROM には JIS の 9〜15 区が無く、非漢字の 8 区のすぐ後ろに 16 区 (第 1 水準、0xF05E00) が続く。VT100 は区を詰めずに数えていた。かなは 4・5 区なので、ずれの手前にいて無事だった。

直すと化けは消えた。でも、もう 1 つの問題は残った。僕は言った。「1 FPS くらいかなぁ」

## 何が遅いのか

Mac の上の試験では、Mac の CPU が速すぎて 68000 の遅さが分からない。AI は 2 人の担当を立てた。1 人は、本物の CGROM で VT100 の画面を PNG に描いて確かめる試験の仕組みを作る (今回の漢字のずれは、それまでの試験が漢字の字形を空にしていたせいで漏れていた)。もう 1 人は、XEiJ の 10MHz の 68000 で速さを測る。

結果は予想と違った。VRAM に描く時間は全体の 1〜4 割しかない。重いのは、エスケープ列を解析して文字をセルの表に置く方で、1 文字に 5,000 クロックかかっていた。

担当は、セルを 4 バイトにして色の計算を前もって済ませ、ASCII と UTF-8 の連なりをまとめて置き、描画の内側を 68000 のアセンブラにし、CRTC の同時アクセスで 4 枚のプレーンに一度に書くようにした。

| 画面 (XEiJ、10MHz) | 前 | 後 |
| --- | --- | --- |
| Claude Code | 6.6 KB/s | 14.5 KB/s |
| top | 2.8 KB/s | 10.3 KB/s |

それでも担当は言った。top は VRAM への書き込みだけで 130 万クロック、解析で 270 万クロックかかる。ここが C の限界に近い、と。

## 相手に押し付ける

僕は聞いた。「ssh じゃなくて、UDP ベースのなかったっけ」

mosh だ。mosh は、端末の画面をサーバー側で持ち、変わったところだけを送る。Claude Code の激しい書き換えも、途中は全部サーバーで捨てられ、最後の画面だけが届く。ただ、mosh は C++ で、protobuf と AES-OCB が要る。68000 に移植するのは重い。しかも相手のマシンに mosh-server が入っていないと使えない。

僕はしばらく考えて、言った。「scp とかみたいに、ssh 先で userland で何か立ち上げてもいいのよね」

いい。scp は相手側で `scp -t` を、mosh は `mosh-server` を、ssh 越しに起動している。VS Code の Remote は、初回に自分のサーバーを相手のホームに送り込む。僕は決めた。「rust で arch にあわせて送り込む」

そうしてできたのが zterm だ。

- 相手側の補助プログラム (Rust、gzip で 200〜260KB): pty でシェルを動かし、画面を自分で持つ。Z が描ける形 (ASCII、JIS の区点、絵文字の番号) に直してから、変わったセルだけを、1 秒に最大 20 回ほどにまとめて送る。スクロールは「スクロールせよ」の 1 命令で送る。
- Z 側: 届いたセルを VT100 の描画処理で描くだけ。Unicode の処理も、エスケープ列の解析もしない。
- 送り込み: ssh.x がつないだ先の `uname -sm` を見て、Linux (aarch64 / x86_64) と macOS (arm64 / x86_64) の 4 種類から選んで送る。2 回目からは相手の `~/.cache/zterm` にあるものを使う。

送るバイト数は、top で 10 分の 1、全画面を描き直すスピナーなら 60〜115 分の 1 になった。

## 4096 バイト

Z で初めて送り込んだら、raspi5 の sshd に切られた。ログにはこうあった。

```
Bad packet length 3490354796.
ssh_dispatch_run_fatal: Connection from user moto 192.168.1.68 port 2071: Connection corrupted
```

今まで Z から送るのは、キー入力くらいの小さなデータだけだった。257KB をまとめて送るのは初めてだ。担当が Z で大量送信の試験をすると、xip.x の癖が見つかった。非ブロッキングのソケットに 4096 バイトを超えて `write()` すると、データは全部送られるのに -1 (EAGAIN) が返る。dropbear は「送れなかった」と思って同じデータを送り直し、暗号の流れがずれる。32KB ずつ書いた試験では、300KB 送ったつもりが、相手には 3.3MB 届いていた。

ソケットへの書き込みを 4096 バイトずつに区切って直った。今後 Z からファイルを送る機能を作っていたら、同じところで引っかかっていたはずだ。

## 1.5KB/s

直してみると、送り込みは通るが、3 分かかった。担当が測ると、Z の chacha20-poly1305 (SSH の暗号) は 1 秒に 1.5KB しか処理できなかった。VT100 が 14KB/s 描けても、届いたデータの復号が 1.5KB/s で詰まる。1 FPS の本当の主犯は、こちらだった。

内訳を取ると、poly1305 が 8 割。64bit の掛け算を多用していて、68000 では全部ライブラリ関数の呼び出しになっていた。X25519 のときと同じ病気だ。担当は poly1305 を MULU 16×16 で組み直し、さらにパケットごとの鍵の倍数を表にして引く形にし、chacha20 も 80 回の quarter-round を全部展開したアセンブラにした。

| chacha20-poly1305 | 前 | 後 |
| --- | --- | --- |
| XEiJ | 4.0 KB/s | 22.1 KB/s |
| Z 実機 | 1.7 KB/s | 9.1 KB/s |
| Z 実機、ssh で実際に受信 | 1.42 KB/s | 4.54 KB/s |

実際の受信が暗号の半分の速さなのは、暗号 (9KB/s) と TCP の処理 (同じく 9KB/s 前後) が、同じ 68000 を順番に使うからだ、と担当は書いていた。ここから先は暗号だけ速くしても、全体はあまり速くならない。xip.x を捨てる日は、やはり近い。

## 全部入り

VT100 の高速化、zterm、暗号、Pico のアクセラレータを 1 つの ssh.x にまとめた。

| Z から raspi5 へ | VT100 (`-t`) | zterm (`-Z`) |
| --- | --- | --- |
| `top -d 0.5 -n 20` | 30.1 秒 | 23.8 秒 |
| `seq 1 20000` (2 万行) | 249.8 秒 | 13.9 秒 |

2 万行を流すと 18 倍。VT100 は 1 行ずつ復号してスクロールするが、zterm は相手が画面をまとめるので、最後の画面しか届かない。macOS (x86_64 の Mac mini と、arm64 の MacBook) にもつながった。

僕は Z から `ssh.x -Z` (zterm) で raspi5 にログインし、Z のキーボードで Claude Code を試して、「まぁまぁ動いてるね」と言った。それなら次はローカルエコーだ。打った字を、Pi の返事を待たずに Z がその場に描く (確定するまでは下線付き)。zterm の補助プログラムが画面を全部持っているので、答え合わせは簡単だ。違ったら消して、しばらく予測をやめる。パスワードのように画面に出ない入力では、最初の 1 字が確定しないので、何も描かない。Claude Code の入力欄を真似た試験用のアプリでは、56 字中 55 字の予測が当たった。

念のため書いておくと、Claude Code そのものは raspi5 (Raspberry Pi 5) の上で動いている。Z の 68000 がやっているのは、ssh の暗号、zterm から届いたセルを描くこと、キーを送ることだけだ。それでも、目の前の X68000 Z の画面とキーボードで、AI と話している。

そして、その Claude Code に頼んだ。X68000 の X のロゴを、大きなアスキーアートで描いて。

## まだ

- 罫線の二重線 (╔ ╗ ║ ═) がうまく描けていない。上の写真の、ロゴの輪郭の崩れがそれ。
- 日本語は打てない。ssh.x は X68000 の日本語入力 (FEP) を通らずにキーを読んでいる。
- たまにだけ起きる不具合が 2 つある。dropbear の中でスタックポインタが奇数になったアドレスエラーが 1 回と、大量送信 4 回に 1 回の MAC のエラー。どちらも再現しない。
- 暗号と TCP が CPU を取り合っている。TCP を Pico に任せれば、ここが空く。

10MHz の 68000 の画面とキーボードで、2020 年代の AI と話せた。言うのは簡単だ。でも今回は、写真がある。

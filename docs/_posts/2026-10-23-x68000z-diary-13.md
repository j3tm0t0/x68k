[前回のあらすじ]({{ site.baseurl }}{% post_url 2026-10-22-x68000z-diary-12 %}): Z から ssh して、raspi5 の Claude Code が Z の画面で動いた。遅さの主犯は描画ではなく、解析と暗号だった。このシリーズでは、コードも調査もほぼ全部 AI (Claude) にやらせている。

## キーボードも Pico に

これまで Z には Pico W を 2 枚挿していた。1 枚はディスクとネットワークと暗号アクセラレータ、もう 1 枚は picokbd (raspi3 から UDP でキーを送ると、USB キーボードのふりをして Z に打つ)。僕がやりたいことを並べていたら、思い出した。「あ、USBキーボード混載。」

1 枚のファームに、ディスク (MSC) とキーボード (HID) を同居させる。一番の心配は、Z が「ディスクでもありキーボードでもある」USB 機器を受け付けるかどうかだった。これは挿してみないと分からない。

受け付けた。picokbd の命令 (UDP 6869、`x68key`) もそのまま使える。これで Z に挿す Pico は 1 枚になり、AI が Z のキーを打つのにも、別の Pico が要らなくなった。

## 絵文字が白黒

前回のあと、絵文字を 300 個に増やした。見ていた僕は聞いた。「あ、絵文字って白黒なのかい？」 Mac の試験では色が付いていた。でも「Z の画面が白黒だよ」。

AI の見立ては、前回の高速化で入れた CRTC の同時アクセス (4 枚のプレーンに 1 回で書く仕組み) だった。絵文字は 1 画素ごとに色が違うので、同時アクセスを切って 1 枚ずつ書く作りになっている。ところが Z の実機では、切ったつもりで切れていなかった。すると、どのプレーンに書いても 4 枚全部に同じ模様が入り、白い影絵になる。XEiJ ではちゃんと切れるので、試験では見えなかった。

同時アクセスを使わない版を試すと「カラーで出た」。描く前に CRTC の R21 を必ず 0 にして直った。

![X68000 Z の画面。raspi5 に ssh して、sushi や beer の色付きの絵文字と、300 個の絵文字の一覧が出ている]({{ "/assets/z-emoji-color.jpg" | relative_url }})

## 画面を 4 枚

僕は前から言っていた。「linux console みたいにAlt+F1/F2みたいに、複数切り替えられたらいいよねぇ」。マルチタスクは無理なのは分かっている。「tmux 使えばいいんだけどさ」。

担当が作ったのは、1 本の ssh 接続の中に最大 4 本のシェルを開く仕組みだ。SSH はもともと 1 本の接続にチャンネルを何本も通せる。CTRL+F1〜F4 (または `Ctrl-]` のあとに数字) で切り替え、まだ開いていない番号ならそこで新しいシェルを開く。VT100 (`-t`) と zterm (`-Z`) のどちらでも動く。

Z の USB キーボードから CTRL+F キーがそのまま届くかが心配だったが、届いた。「いいね、いい感じに切り替えできる」。

ついでに頼んだ。「英語キー配列にしてほしいです」。Z はキーボードを日本語配列として読むので、US 配列のキーボードでは記号がずれる。x68kcli のイメージで使っている KeyWitch を、ネットワークを上げるバッチの最初で常駐させるようにした。

## ディスクから起動できません

今の Z は、Pico が Wi-Fi 越しに raspi3 の SMB の共有から HDS (ディスクのイメージ) を読んで、起動ディスクとして見せている。電源を入れたとき、Pico の SMB が間に合わないと、Z は「ディスクから起動できません」で止まる。

僕は聞いた。「SMB マウント間に合わなかったら、設定UIみたいに、再起動だけするブートセクターを渡しちゃうのはどうなんだろうな？」 そして自分で心配した。「SCSI ROM がキャッシュしちゃうかな」

AI の答えは、その心配が一番の落とし穴だ、というものだった。Z の中の層は、一度読んだセクタを覚えていて、ソフトリセットでも忘れない ([日記 (9)]({{ site.baseurl }}{% post_url 2026-10-21-x68000z-diary-9 %}) で古い応答を引き続けたのも、これだった)。再起動用の偽物の起動セクタを見せれば、SMB がつながった後も、Z は覚えた偽物を読み続けるかもしれない。

担当がファームのコードを読むと、もっと手前に原因があった。SMB が間に合わずに HDS が読めないとき、Pico はエラーを返さず、**0 で埋めたデータを「読めた」として Z に返していた**。起動セクタの先頭の署名が 0 になるので「起動できません」になる。そしてその 0 が、Z の中に残る。

## 待たせる

担当が選んだのは、もっと素直な方法だった。HDS が開けるまで、Pico は Z に「準備中 (NOT READY)」と答える。SCSI の決まりの中にある返事で、Z はそれを見ると待って、聞き直す。読めなかったときに 0 を返すのもやめた。

raspi3 の SMB をわざと 60 秒止めて、Z の電源を入れた。

| | |
| --- | --- |
| 電源から、Z が起動セクタを読みに来るまで | 約 28 秒 |
| Pico が「準備中」と答えた回数 | 8 回 |
| 電源から、Human68k が起動するまで | 約 87 秒 |

「ディスクから起動できません」は出なかった。

## 待ち画面

止まらなくなったら、今度は、待っている間の真っ暗な画面が気になった。「うん、なんか出したいですね」「ASCII アートくらいは出せる？」「setup モードに入る場合は、みたいな、BIOS 的なのもいけそう？」

担当はこう作った。Pico は HDS の先頭 16KB を控えておく。SMB を待つ間は、その控えの起動プログラムだけを「待つプログラム」(2 段で 1.2KB ほど) に差し替えて Z に渡す。待つプログラムは画面に状態を描き、キャッシュを避けながら Pico に「準備できた?」と聞き続ける。HDS が開いたら、控えと本物の先頭を比べ、同じなら本物の起動に乗り換える。違っていたら「HDS が変わりました。Z の電源を入れ直してください」と出して止まる。S を押せば、x68kzremotedrv にもともとある設定画面 (Wi-Fi・SMB・HDS) に入れる。

最初の版を見た僕の感想は、「もうちょいかっこよくはしたい。機能的にはサイコー」。

## X のロゴ

「いわゆる、X のロゴっぽい感じにしたいんだよねぇ」

担当は三角 4 つを組んだ X のマークを、テキスト画面にドットで描いた見本 (PNG) を出してきた。僕はしばらく見て、気づいた。「SHARP のは商標があれってことだよね、きっと」

そういうことだった。X68000 のロゴは SHARP のものだ。公開しているリポジトリに似せた絵を入れて配るのは避けたい。本物に寄せるほど危うくなる。それに「色が嫌かな」。

それなら、自前のロゴにすればいい。名前も要る。僕が最初に思いついた「picoboot」は、Pico の書き込みの仕組みと同じ名前だと言われて、**Pico Z Loader** にした。デザインのキャンバスにロゴを何案か並べてもらい、電源マークの輪の中に Z を置いたものに決めた。

## 進み具合の線

![X68000 Z の実機に出た Pico Z Loader の待ち画面。輪の中に Z のロゴ、Wi-Fi・SMB・HDS の状態、下に ◆ の線 (この後、本物の進み具合の線に替えた)]({{ "/assets/z-pico-z-loader-wait.jpg" | relative_url }})

実機に出してみると、もう 1 つ気になった。下の `[Pico W] ━◆━ [X68000 Z]` の ◆ は、0.5 秒ごとに動くだけで、何も表していない。「意味ありそうでないのがやだな」。そこで線を本物の段階にした。Wi-Fi・SMB・HDS・起動の 4 区間で、済んだ段階は水色、今の段階は白く、SMB を待つ間は次の再接続までの時間に合わせて区間が伸びる。最後のラベルは「起動、はやめて、BOOT にしようか」。

```
Wi-Fi ━━━ SMB ━━━ HDS ━━━ BOOT
```

ファームのパッチで数えると、待ち画面だけで 15 本、1 時間 10 分。焼いて、SMB を止めて、電源を入れて、の繰り返しだった。最後に、普通にコールドブートした。待ち画面は出ず、そのまま起動する。「いいね、安定したし、起動かっこいいし」

## 別の名前で

一段落したところで、Pico のファームをこの先どう扱うかを考えた。

Pico のファームの土台は、yunkya2 さんの x68kzremotedrv だ。Z の USB にディスクを見せる仕組みも、SMB から HDS を読む部分も、設定画面も、この土台があったからここまで来られた。そこにネットワーク、暗号アクセラレータ、キーボード、起動待ちと足していくうちに、元とはだいぶ違うものになった。これを本家の名前のまま配ると、本家と見分けがつかず、僕が足した部分の不具合の問い合わせまで yunkya2 さんに行ってしまうかもしれない。

そこで、SD カードから読む版ができたら、別の名前で公開することにした。名前は、待ち画面と同じ Pico Z Loader。

x68kzremotedrv から受け継いだコードには yunkya2 さんの著作権表示を残し、README には、この土台のおかげでできたことを書く。本家の役に立ちそうな直しは、本家にも返していきたい。SD カードから HDS を読む版は、部品を買ってから。

## まだ

- 待ち画面の副題には、まだ「x68kzremotedrv」と出ている。別の名前で出すときに外す。
- Z が読んだセクタをどこで覚えているのか (Z の中の Linux のファイルのキャッシュ、という見立て) は、確かめていない。Debug Probe で Pico のログを取れば分かるはず。
- SMB を待つ限り、起動はネットワーク次第だ。根本的には、SD カードから起動すれば待たなくて済む。
- 日本語入力 (FEP) は相変わらず保留。

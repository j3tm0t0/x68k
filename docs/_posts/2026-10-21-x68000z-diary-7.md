前回のあらすじ: 遅さの犯人は xip.x ではなく、SCSI の運搬だった。slipd.x を直して 136kbps。プロファイルを見ると、CPU の 25% が SCSI の ROM の中で空回りしている。このシリーズでは、コードも調査もほぼ全部 AI (Claude) にやらせている。僕の担当は電源ボタンだ。今日はそれを何度も押した。

## ROM を吸い出す

ROM が何を待っているのか知りたい。なら、中を読めばいい。AI は Z のメモリを好きな範囲だけファイルに書き出す `memdump.x` を作り、SCSI の ROM がある 0xEA0000 から吸い出した。

Z は固まった。

画面には「バスエラー」。遠隔キーボードのリセットも効かない。僕は電源を切った。入れ直したら「ディスクから起動できません」。もう一度入れ直す。

0xEA0000 から 0xEA001F は、読むとバスエラーになる場所だった。AI は 1 ワードずつ、バスエラーを検査しながら読むように直した (DOS の `_BUS_ERR`)。読めない所は飛ばして数える。

## 郵便受け

吸い出した ROM の中に、こう書いてあった。

```
Pseudo SCSI BIOS ver.1.05 Copyright (C) 2023 uchopon
```

X68000 Z の SCSI は、本物の SCSI コントローラではなかった。uchopon 氏の「疑似 SCSI BIOS」だ。仕組みはこうなっている。

- 0xEA0060 に、16 バイトほどの小さな受け口がある。
- ROM はそこに「ID」「命令」「LBA」「バイト数」「バッファの番地」を書いて、開始の印を立てる。
- あとはエミュレータが Pico と USB でやり取りし、X68000 のメモリに直接読み書きして、終わったら印を下ろす。
- その間、ROM は `nop` を 2 つ挟みながら印を見続ける。

郵便受けに手紙を入れて、返事が来るまでポストの前に立ち尽くしているわけだ。プロファイルで 25% を食っていたのは、この立ち尽くしだった。

なら、手紙を入れたら家に帰ればいい。slipd.x が ROM を通さずに郵便受けを直接使い、返事を待つ間は `_CHANGE_PR` で CPU を xip.x に譲る。

## 郵便受けは 1 つしかない

問題は、この郵便受けを使っているのが slipd.x だけではないことだ。A: も B: も同じ郵便受けを使う。slipd.x が待っている間に B: のドライバが手紙を入れると、互いの手紙を書き換えてしまう。

AI は ROM の入口 (IOCS の `_SCSIDRV`) にフックを挟んだ。slipd.x の手紙が出ている間は、ほかの呼び出しを待たせる。

最初の版で、Z は 1 回固まった。B: のドライバは「選択」「命令」「データ」「状態」を別々の IOCS の呼び出しで行っていて、その合間に slipd.x が割り込んでいた。ROM の外にいる間はフックでは止まらない。郵便受けの「段階」の欄が 0 に戻るまで待つようにして、直った。

ネットワークで受けながら A: と B: に乱数のファイルを書いて照合する試験を 13 回やって、全部一致。速さは 136kbps から 176kbps になった。

## free() の幽霊

プロファイルを取り直すと、今度は C のライブラリの `free()` が CPU の 1 割を食っているように見えた。メモリの鎖を延々とたどっている。

犯人は、プロファイラ自身だった。`zprof.x dump` は記録を止める前に、記録の置き場所を探してメモリを 2MB 走査する。その 1〜2 秒も律儀に記録されていた。zsh から起動すると、zsh の起動処理 (`free()` のあれ) も混ざる。観測者が観測対象を乱している。量子力学か。

`zprof.x` は自分の分を捨てるようにした。ついでに、rcmd.x のシェルを zsh から COMMAND.X に替えた。試験のたびに zsh を起動しないで済む。COMMAND.X は `-c` ではなく `/c` を受け取り、しかも空白を含む引数を渡すと黙って何もしない。もちろん、これにもはまった。

## SLIP をやめる

ゆがみを除いたプロファイルで、次の大物が見えた。slipd.x の中の SLIP の解読だ。受け取ったバイト列から区切り (END) と ESC を 1 バイトずつ探して写すループだけで、CPU の 19%。送る側も、slip.sys から 1 バイトずつ関数を呼んで取り出している。

ちょっと待て。ブリッジでは、Z の相手は Pico だ。どちらの端も僕ら (というか AI) が書いている。SLIP である必要がどこにある?

ない。なので、netpipe の中を、長さ付きの IP パケットの並びにした。GRE や IPIP と同じく、IP パケットを長さ付きでそのまま包むトンネルだ。

- Pico から Z へ: [長さ 2][空き 14][IP パケット]。空き 14 バイトは、slip.sys が xip.x に渡すときに Ethernet の見出しを書く場所。こうしておけば、Z は受け取ったセクタを 1 バイトも写さずに xip.x に渡せる。
- Z から Pico へ: [長さ 2][IP パケット]。slip.sys が送信リングにこの形で積み、slipd.x はまとめて取り出す。
- 要求の印を "X6NR" にしたときだけこの形になる。古い slipd.x や、Pi の slattach が相手の UDP モードは SLIP のまま。

ファームを焼き直す前に、Pico が Wi-Fi から消えた。Z には「エラーが発生しました」。再実行しても同じ。AI は Pi から Pico の IP アドレスに ping を打ち、返事がないことを確かめてから「Z ではなく Pico です」と言った。原因はまだ分からない。ちょうど焼き直すところだったので、そのまま焼いた。

新しい slip.sys を入れて最初に起動したら、またバスエラー。AI が slip.sys の新しい命令を、ユーザーモードから呼んでいた。slip.sys はスーパーバイザ専用の領域にいる。直した。

| | 速度 (Pi → Z、200KB) |
| --- | --- |
| 前回の終わり | 136kbps |
| SCSI の待ちの間に CPU を譲る | 176kbps |
| SLIP をやめる | 290kbps |

xip.x にはまだ 1 バイトも触っていない。

もはや SLIP ではないので、そのうち slip.sys と slipd.x を改名する。netpipe のドライバだから、npd。

## contee、ついに

第 3 回で書いたきり実機で試していなかった `contee.sys` (画面に出す文字を RS-232C にも流す) を、ようやく試した。

- 最初は、組み込みメッセージは流れたが、エラーのダイアログが流れない。ダイアログは位置を指定して文字列を描く `_B_PUTMES` で出ていた。これも横取りした。
- IOCS.X は画面出力の IOCS を自分の版に置き換えるので、contee.sys はその後ろに置く。
- IOCS.X と contee.sys を CONFIG.SYS の先頭に置いたら、ログが化けた。RSDRV.SYS が組み込みのときに 9600bps に戻していた。contee.sys は RSDRV.SYS の後ろに置く。

わざと空のフロッピーを読ませると、シリアルのログにこう出た。

```
　　　ディスクが入っていません、入れてください　　　
　　　 中止＜Ａ＞ 再実行＜Ｒ＞ 無視＜Ｉ＞ ？　　　　
```

人間 OCR は、これで引退だ。

## 残っていること

- 電源を入れたときの「ディスクから起動できません」。Pico が起動時に Wi-Fi と SMB への接続を何度か繰り直すようにした。効いたかどうかは、何度か電源を入れてみないと分からない。
- Pico が Wi-Fi から消える件。次に起きたら、ログを Wi-Fi 越しに取れるようにして調べたい。
- xip.x の中では、ロックの空回りと表の掃除が目立つ。いよいよ xip.x か。言うのは簡単だ。

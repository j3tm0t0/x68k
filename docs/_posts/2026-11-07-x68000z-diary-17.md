[前回のあらすじ]({{ site.baseurl }}{% post_url 2026-10-24-x68000z-diary-16 %}): 新しい Pico のファームで Z が固まる件は、試験の操作に使っていたシリアルのコンソールが原因だった。Z-OS のシェル zosh のパイプは、各段を同時に動かせるようになった。このシリーズでは、コードも調査もほぼ全部 AI (Claude) にやらせている。

今回は OS の話だ。Z-OS は、X68000 Z の上で動く自前の環境で、画面を分けて複数のシェルを動かす zos.x と、自前のシェル zosh からできている。ここ 2 日で、僕は担当の AI たちにひとつ目標を出した。

> 使ってると UNIX 使ってるんじゃないかって錯覚するくらいの感じにしたい

それから約 1 日半、多いときで 11 人の担当を同時に動かし、30 本ほどの PR をマージした。`ls`、`cd /`、`cat | grep`、`vi`、`man`、`ps`、`kill -9`、`curl` が、Human68k の上でそれらしく動くようになった。

## ドライブを 1 本の木に

最初に納得いかなかったのはファイルの見え方だった。Human68k は MS-DOS と同じく `A:` `B:` とドライブごとに木が分かれている。WSL や Cygwin のように、全部を `/` の下に置きたい。

担当はまず Human68k の `ASSIGN` (ドライブ名を別の場所に割り当てる機能) を XEiJ (X68000 のエミュレータ) で試した。結果、できるのは「ドライブ名 → ディレクトリ」の向きだけで、ドライブを別のドライブのディレクトリの下に見せる MS-DOS の `JOIN` に当たるものは無いと分かった。

そこで、DOS コール (ファイルを開く、一覧を取る、実行する、などの OS の呼び出し) を横取りする常駐プログラム `mount.x` を作らせた。経路の引数が `/c/usr/bin` なら `C:\usr\bin` に書き換えてから、本来の処理に渡す。`/` だけを開くと、ドライブの一覧 (`a/ b/ c/ …`) が見える。C ライブラリを使わず、大きさは 5KB ほどだ。

その後、起動ドライブをそのまま `/` にする「木のモード」を足した。`/home` `/usr/bin` は起動ドライブの本物のディレクトリで、ほかのドライブは `/mnt/b` のように見える。`/dev/null` は Human68k の `NUL` に向く。ファイルの先頭が `#!/bin/sh` なら、そのインタプリタで動かすようにもした。

ひとつ面白かったのは、レビューで「後から起動したシェルの中で `mount -r` (常駐を外す) を打つと、解放したメモリに処理が戻る」と指摘された件だ。担当が実測してみると、Human68k は子のプログラムを動かす前に横取りの処理から戻り切っていて、指摘のようなことは起きなかった。指摘を鵜呑みにせず、実際に測って決めた。

## zosh を UNIX のシェルに

zosh は、COMMAND.X (Human68k の標準のシェル) のかわりに作っている自前のシェルだ。担当に、POSIX の sh と比べて足りないものを困る順に 21 個書き出させ、上から埋めさせた。

| 入れたもの | 例 |
|---|---|
| 経路 | `/c/usr/bin`、`cd /`、`cd ..` でドライブの外へ |
| 組み込み | `ls` `cat` `cp -r` `mv` `rm` `mkdir` `head` `wc -l` `env` `seq` など |
| 構文 | `{ }` `( )`、複合文へのパイプ、ヒアドキュメント、`${v:-x}`、`trap`、`local`、`getopts`、`set -e` |
| スクリプト | `#!/bin/sh -e`、`#!/usr/bin/env`、`sh -c` |
| 対話 | コマンド名の補完、`**`、`!!`、`export` した変数だけ子に渡す |
| 起動 | `zosh.x -l` で `/etc/profile` を読む、終わると `logout` |

最後に、COMMAND.X を使わずに zosh を一番上のシェルにした (CONFIG.SYS の `SHELL=`)。起動すると motd が出て、`moto@z:~$` というプロンプトになる。ただし弱点も見つかった。zosh が画面に出力している最中に Ctrl+C を押すと、Human68k が zosh ごと止めてしまう。COMMAND.X が上にいたときはそこに戻れたが、今は戻る先が無い。COMMAND.X と同じく Ctrl+C を自分で受ける直しを、今やっている。

プロセスまわりも足した。`ps` `top` `kill` `df` `du` `free` に加えて、zos.x のペインの中のプログラムを `kill -9` で本当に止められるようにした。ユーザーモードで動いているなら、スレッドを切り替えたときに保存してある戻り先の番地を、終了の処理の番地に書き換える。どうしても止まらなければ 1.5 秒後にペインごと落とし、開いていたファイルは別のスレッドが閉じる。ネットワークの `host` `curl` `wget` も、Pico に TCP/IP を任せる tis.x の上で動くようになった (https はまだ)。

## GNU のコマンドを入れる

「GNU 系のコマンドは一通り網羅したい」と僕が言うと、担当は GNU coreutils 9.12 の 86 本を、そのまま X68000 向けに組んだ。find、xargs、diff、gzip、less、file、patch、bc も入れ、エディタは vim 3.0 (1994 年、もともと X68000 版がある) と vim 9.2 の両方を置いた。XEiJ の試験は 123 項目のうち 122 が通る (残り 1 つは `cat a >> a` で、入力と出力が同じファイルだと判定できない件)。

困ったのは速さだ。GNU の `ls` は 1 回 0.55 秒、`head` は 0.24 秒かかった。昔からある ITA TOOLBOX の版はそれぞれ 0.12 秒、0.05 秒で、GNU は 4〜7 倍遅い。一度は「GNU を優先」と決めたが、この数字を見て ITA を `/usr/bin` に残し、同じ名前の GNU は `/usr/gnu/bin` に置くことにした。ITA に無い `sort` `find` `diff` などは GNU を使う。

担当は遅い理由を測った。読み込みは 1KB あたり約 1.45ms で、加えて Human68k は実行ファイルの番地を直す箇所 (再配置) 1 つにつき約 33 マイクロ秒かけていた。vim 9 はそれが約 5 万箇所あり、起動に 5 秒かかる。そこで、直す箇所の表を Human68k に渡さずに実行ファイルの後ろに置き、起動のコードが自分で速く直すようにした。さらに、日時の変換を経由しない軽い stat に替えて、実行ファイルを 1 本あたり約 12KB 小さくした。

| コマンド | 最初 | 今 | 参考: ITA |
|---|---|---|---|
| head | 243ms | 173ms | 50ms |
| cat | 226ms | 160ms | 30ms |
| vim9 | 4.97 秒 | 3.54 秒 | — |

RAM ディスクに写す案も試したが、かえって約 50% 遅かった。RAMDISK.SYS は CPU で 1 バイトずつ写すので、SCSI の DMA に負ける。

GNU の sort は、4000 行で 12.4 秒かかっていた。担当は XEiJ の CPU が実行している番地を 1/5000 秒ごとに記録する道具を作り、時間を食っている関数を突き止めた。ファイルへの出力でも 1 行ごとに書き出していたこと、printf が整数の表示にも遅い 64 ビットの割り算を使っていたことなどを直して、7.0 秒になった。Human68k 付属の SORT.X は、同じ 4000 行に 153.8 秒かかる。

## レビューを 2 つの AI に

最初は、OpenAI の Codex に PR をレビューさせて、問題が無ければマージさせていた。途中で僕は「Fable と Codex のレビューがよいな」と言った。Fable は Claude のモデルの 1 つで、このシリーズでは重い設計に使っている。以後は両方にかけ、両方で重い指摘が無く、CI が全部通ったものだけをマージすることにした。

2 つは見つけるものが違った。zosh の PR では、codex は境界の条件や sh との振る舞いの違いを細かく拾う。Fable は実際にコンパイルして関数ごとのスタックの使用量を測り、「関数を 8 段再帰させると 24KB のスタックがあふれ、zosh の内部のデータを黙って壊す」と指摘した。codex はこれを見落としていた。逆に、Fable が通したものを codex が止めたこともある。

zosh の 3 本の PR は、codex に 8 回、Fable に 3 回かけて、ようやくマージした。直すたびに新しい境界の指摘が出てきて収まらないので、重いもの (データを失う、止まる、メモリを壊す) だけを直し、細かいものは issue のチェックリストに回すことにした。それでも、`cp ソ.txt dest/` で別のファイルを上書きしてしまう件 (Shift-JIS の 2 バイト目が `\` と同じ 0x5c になる文字を、経路の区切りと誤認していた) のように、本当に危ないものが何度も出てきた。

レビューを通したのに壊したこともある。ペインを割った直後に同じ行が 2 回出る表示の乱れを直す PR を、codex も Fable も OK としてマージした。ところがその後、ssh の試験がみな落ちるようになった。ペインの中の ssh.x が自分で描いた絵は zos.x の画面の記録に載らないのに、直した処理はその記録で変わったところだけをずらしていた。すぐに取り消し、担当は条件を変えた一時的な PR を 3 本立てて、CI で原因を絞り込んだ。レビューでは、別のリポジトリの試験のことまでは分からない。

## CI とランナー

担当を並行で動かすと、次に詰まるのは CI だった。試験は XEiJ を使うので、普段使っていない Mac mini の上に Linux の VM を置いて、GitHub Actions の self-hosted ランナーにしている。「2 倍にしよう」と言うと、担当はまず「コアを増やすと速くなるか」を測った。XEiJ の試験は 6 コアでも 2 コアでもほぼ同じ時間だったので、2 コア・4GB の VM を 6 台にした。

それでも足りなかった。ひどかったのは、PR を 1 本マージするたびに残りの PR が競合することだ。どの PR も自分の試験を workflow の同じ 1 行 (試験の一覧) に足していたからだ。競合した PR には GitHub が CI を走らせないので、担当が「CI 待ちです」と言ったまま何時間も止まっていた PR もあった。最後は、各試験のファイルに `# group: shell` のような 1 行を書き、workflow はそれを集める形に変えた。

試験がたまに落ちる件もあった。決め打ちの sleep で待っていたので、VM が混むとプロンプトが出る前にキーを打っていた。ペインを割って新しいプロンプトが出るまでに 11〜14 秒かかることがあるのに、試験は 8 秒しか待っていなかった。画面の状態を見て待つ形に直した。

僕のところには「CI 失敗」の通知がたくさん届いた。担当がみな僕のトークンで push するので、結果が全部僕に届く。

## 次にやること

- 一番上の zosh で Ctrl+C を受ける。`exit` したら zosh を起動し直す。
- ペインの表示の乱れの直しを、ssh.x を壊さない形で入れ直す。
- X68000 の文字では `~` が `‾` に見える。UNIX らしく見せるには描き方を変える必要がある。
- 全部 XEiJ でしか確かめていない。Z と XVI の実機で確かめる。
- そのうえで、Z でデモの動画を撮る。台本と自動入力はもうできていて、Pico には USB マウスのまねも足した。

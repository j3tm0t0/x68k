[前回のあらすじ]({{ site.baseurl }}{% post_url 2026-11-10-x68000z-diary-18 %}): UNIX に慣れた人が気づく所を 200 個ほどのコマンドで 3 回洗い出して直した。最後に、Z 用の Z-OS のイメージを X68000 Compact XVI (以下 XVI) の BlueSCSI v2 でそのまま起動した。

今回は XVI の話が中心だ。BlueSCSI v2 のファームを改造して、Z の Pico でやっていた起動ディスクの切り替えと暗号の計算を XVI でも使えるようにした。BlueSCSI を Pico 2 W 版に替えて、ディスクイメージを Wi-Fi で送れるようにもした。最初は 25KB/秒しか出なかったが、原因は電波で、アクセスポイントを XVI の横に置くと 1.1MB/秒になった。

## BlueSCSI v2 に Pico Z Loader の機能を載せる

Z では、SCSI のディスクをまねる Pico に自前のファーム (Pico Z Loader) を入れて、起動ディスクの切り替え、ネットワーク、SSH の暗号の計算をさせている。XVI の BlueSCSI v2 も中身は Pico なので、同じことを BlueSCSI のファームに足した。BlueSCSI のファームは GPL-3 なので、改造は手元のブランチに置いていて、公開していない。

XVI のディスクは用途ごとに分けた。SD カードにイメージファイルを置き、Z-OS の起動用 (64MB)、`/usr/local` (256MB)、`/home` を別の SCSI ID にした。前回の最後に書いたとおり、起動用のディスクを書き直しても `/home` は残る。`/home` は最初 32MB で作ったが、大学 1 年のときの UNIX の quota ではないので、後で 512MB にした (下の Wi-Fi で送って入れ替えた)。

足したものは次のとおり。

- **起動メニュー**: ID0 のディスクの起動セクタを自前のローダーに替え、画面の一覧から起動先を選ぶ。選ばなければ 5 秒で既定の項目を起動する。↑↓ と Enter、数字キーで選べる。
- **通信用の ID6**: BlueSCSI が ID6 に通信用の SCSI 装置を 1 つ用意し、X68000 とは独自の SCSI コマンドで要求をやり取りする。起動メニューはこれを使って、選ばなかった ID を X68000 から隠す。SSH の暗号の計算 (X25519 / Ed25519) もこの ID6 で Pico に任せる。
- **ゲームのイメージを選ぶ**: 起動メニューの「イメージを選ぶ」項目で、SD カードにあるイメージの一覧を ID6 に聞き、選んだものを ID5 に差し替えてから起動する。フロッピーを入れ替える代わりになる。

起動メニューには実機でだけ出た不具合があった。電源を入れると、秒読みが始まらずに止まることがある。起動直後にキーの入力が溜まっていて、ローダーが「キーを押した」と判定していた。メニューを出す前に溜まったキーを読み捨て、メニューで使うキーだけで秒読みを止めるようにして直った。最初、リーダー役の AI はこれを別の常駐プログラムのせいだと思い込んでいて、僕が「カウントダウンされてない」と伝えてから原因にたどり着いた。

## Wi-Fi でイメージを送って入れ替える

試験のたびに起動用のイメージを書き直すのは、やはり手間だった。BlueSCSI の USB を Raspberry Pi につないで USB ディスクとして書くと、書いている間は XVI からすべてのディスクが見えなくなる。速さも 100〜150KB/秒で、64MB に 10 分かかる。

そこで BlueSCSI を Pico 2 W 版 (無線付き) に替え、次の仕組みを作らせた。

1. XVI が古いイメージで動いたまま、新しいイメージを Wi-Fi で SD カードの別名のファイルに受け取る。SCSI の応答は止めない。
2. 全部届き、大きさと CRC32 が合ったら「入れ替え待ち」にする。
3. BlueSCSI の次の起動か、XVI のリセットで出る SCSI バスリセットのときに、古いイメージを控えのファイル名に、新しいイメージをいつも使うファイル名に変える。途中で電源が切れても、次の起動で続きをするか元に戻す。

BlueSCSI のファームにはもともと無線の処理があるが、これは Mac 用の SCSI イーサネット (DaynaPORT) のまねで、フレームをそのまま SCSI に渡すだけだ。TCP/IP は入っていない。Pico 2 W 用のビルドにだけ lwIP (Pico SDK に入っている TCP/IP) を足し、受け取り専用の TCP サーバーを動かした。送る側は Python のスクリプト `bsstage` だ。

実機で動かすと、入れ替えは一発で通った。起動時の入れ替えは 15ms、XVI のリセットでの入れ替えは 13ms で終わり、XVI は新しいイメージでそのまま起動した。ところが速さが 25KB/秒しか出ない。64MB に 40 分以上かかるのでは、USB より遅い。

ファームを作った AI の担当は、まずファームを疑った。Wi-Fi の省電力を切る、TCP の受信の窓を 32KB に広げる、SD カードには 32KB ずつ位置をそろえて書く、といった直しを入れたが、速くならない。受信処理の各段階にかかった時間を 5 秒ごとにログに出させると、ファームはほとんどの時間、次のフレームが来るのを待っていた。無線のチップの状態も出させると、受信の強さが -77dBm、無線のリンク速度が 5.5Mbps だった。遅いのはファームではなく、電波が弱いせいだった。

そこで、NEC の Aterm をアクセスポイント (AP) モードにして XVI の真横に置いた。Aterm は本体のスイッチで AP モードに切り替える。BlueSCSI の無線のチップ (CYW43439) は 2.4GHz しか使えず、暗号化は WPA2-PSK にする。

| | 前 | AP を横に置いた後 |
| --- | --- | --- |
| 受信の強さ | -77dBm | -56dBm |
| 通信速度 | 5.5Mbps | 57.5Mbps |
| 8MB を送る時間 | 約 5 分 | 7.4 秒 |
| 速さ | 25KB/秒 | 約 1.1MB/秒 |

64MB のイメージが 62 秒で届く。送っている間に XVI で `ZOS.X` を 20 回コピーする処理を回しても、両方とも最後まで終わった。その後 XVI をリセットすると、新しいイメージで起動する。これで、Mac でイメージを作ってから XVI で試すまでが 1 分ほどになり、電源も切らなくてよくなった。

ファームの直しも無駄ではなかった。電波が良いときは受信の窓や書き込みの大きさが速さを決めるので、先に直しておいた分、AP を置いただけで 1.1MB/秒まで出た。AP とファームの直しのそれぞれで何倍になったかは、分けて測っていない。

## Raspberry Pi の入れ替えと、シリアルのリモートドライブ

XVI の横には Raspberry Pi を 1 台置いている。XVI の RS-232C をつないで画面を読んだりキーを送ったりする常駐プログラム (zmuxd)、BlueSCSI の USB、画面を撮る Web カメラがここにつながっている。これまでは Raspberry Pi 5 だったが、Raspberry Pi 2 (32 ビット、4 コア) に替えた。zmuxd は Rust で書いているので、Mac で 32 ビット ARM 用に組んで持っていった。ビルドなどの重い処理は Mac でやり、Raspberry Pi 2 は XVI と機器をつなぐだけにする。

もう 1 つ、zmux のシリアル回線の上にリモートドライブ (ZRMT) を載せた。XVI で `zrmt.sys` を組み込むと、Raspberry Pi のディレクトリが F: ドライブに見える。速さは 3KB/秒ほどしか出ないが、小さな試験プログラムなら、Mac で組んで Raspberry Pi に置き、XVI で `F:` から動かせる。試験プログラムを何度も入れ替えるときは、このやり方で動かしている。前は 1 つ変えるたびに、電源を切ってイメージを書き直していた。

いずれは、この Raspberry Pi も外したい。ネットワークも暗号もイメージの転送も BlueSCSI の Wi-Fi でできれば、XVI と BlueSCSI だけで済む。ただ、ファームを開発している間は、USB のログや書き込みに Raspberry Pi が要る。外すのはファームが落ち着いてからだ。

## 次にやること

ほかに、Z-OS に ZOS_PROT という設定を入れた。68000 には MMU が無いので、X68000 の「ここから上はスーパーバイザでしか書けない」という境界 ($E86001) をスレッドごとに書き換えて、ペインで動くプログラムが OS や他のペインのメモリに書くとバスエラーになるようにした。既定では無効だ。

次はこの 2 つ。

1. **BlueSCSI の SD カードのファイルをそのままドライブにする。**今はイメージごと入れ替えているが、起動用のディスクだけをイメージに残し、あとは SD カードのファイルを Human68k のリモートドライブとして見せる。Wi-Fi で置いたファイルが、XVI からすぐに見えるようになる。設計を担当に書かせて Fable にレビューさせ、実装を始めた。
2. **ZOS_PROT の残り 2 件。** レビューで指摘されたものを直す。実機の 68000 では、保護した範囲への jsr でバスエラーが起きたとき、戻り番地がスタックに積まれていないことがある件と、TCP/IP の処理の中で待っているスレッドを止められない件だ。

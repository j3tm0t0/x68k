[前回のあらすじ]({{ site.baseurl }}{% post_url 2026-10-23-x68000z-diary-13 %}): SMB が間に合わなくても、Z は起動を待てるようになった。待ち画面には自前のロゴを付け、Pico のファームは「Pico Z Loader」として独立させることにした。このシリーズでは、コードも調査もほぼ全部 AI (Claude) にやらせている。

## 部品

前から欲しかった部品が揃った。

- Raspberry Pi Pico 2 WH (Pico W の次の世代。RAM が 264KB から 520KB に増える)
- Raspberry Pi Debug Probe 2 個。1 個は Z に挿した Pico の常設用、1 個は机の上の開発用
- HDMI キャプチャ 2 個 (パススルーの無い安いもの)
- 高耐久の microSD 32GB
- Raspberry Pi のキーボード (日本語配列、小さい、USB ハブ付き)

## そもそも何が欲しいんだったか

ssh.x のパスワード認証を頼んだあと、僕は聞いた。「X68000のOS-9ってマルチタスクだったの？」 それから、「MS-DOSに対するOS/2みたいに、human68kとバイナリ互換のある (まぁなくてもいいんだけど) マルチタスクOSは作れるかな…」

AI は、作れると答えた。ただし 68000 には MMU が無いので、OS/2 のように互いのメモリを守ることはできない。近い前例は Atari ST の MiNT で、元の OS のプログラムをそのまま動かしながら、時間で切り替えるマルチタスクを足したものだ、と。

それを聞いて、僕は手を止めた。「うーん、そもそも何が欲しいんだったかをちゃんと考えるか。」

ここまでの方向は「Z を窓口にする」だった。Z から ssh して、raspi5 の上の Claude Code を使う。でも、AI に選択肢を並べてもらって選んだのは **Z 単体で完結** だった。Web を見る、AI と話す、プログラムを書く、連絡を取る。4 つ全部やりたい。OS の基本は Z と Pico だけで、raspi などの別のマシンには頼らない (アプリがクラウドの API を使うのは当然やる)。Pico には何でも任せる。画面は CLI もありつつ、twm やタイル型くらいの GUI で十分。

形にすると、こうなった。

「iterm2のペイン操作が一番近いかな / Pico Z Loader が boot loader になり、human68kと切り替えて使える alternative OS / 名前は、S-OS にあやかって Z-OS とか。 / ペイン割って zsh が動いて、ssh したり gcc 動かしたりしたい。」

「ペインだけじゃなくて、別ウィンドウ(タブ)も作れるといいね。」

正式な名前は **Z-OS for X68000 Z**。Pico が要るので、X68000 の実機では動かないからだ。リポジトリ名は、最初 x68z-os と答えたあとで「x68ときたら、k つけたいな」と言い直して x68k-zos にした (まだ非公開)。

## Mac の上の Pico

Pico と Z の両方を書き換えながら作るなら、毎回 Pico を焼いて Z を再起動するのはつらい。僕は聞いた。「Pico のエミュレーションって mac で出来るのかな」

AI の提案は、Pico のチップを丸ごとまねるのではなく、**Pico 側のプログラムを Mac 向けにビルドして動かす** ことだった。XEiJ (Mac の上の X68000 エミュレータ) が SCSI ID 6 に送る読み書きを横取りして、Mac の上の「Pico の代わり」(picosim) に渡す。その先の LAN は libslirp でまねる。これで、XEiJ の中の npd・ping・rcmd・ssh.x が、実機と同じ道を通って外とやり取りできる。

測ってみて分かったことがある。速さは、ほぼ 68000 のクロックに比例する。

| XEiJ のクロック | Mac → Z | Z → Mac |
| --- | --- | --- |
| 10 MHz | 10.8〜18.1 KB/s | 29.2 KB/s |
| 16.7 MHz | 55.4〜59.7 KB/s | 50.1 KB/s |
| 33.3 MHz | 97.0 KB/s | 99.5 KB/s |

16.7MHz の数字は、実機の Z (45〜57KB/s) に近い。律速は Pico でも USB でもなく、Z の 68000 そのものだ。

## パスワード

もう 1 つの話。「そういや、ssh はパスワード認証に対応してなかったよね」

対応していなかった。dropbear はパスワードを `getpass()` で読むが、Human68k にはこれが無い。担当は、画面に出さずに 1 字ずつ読む代わりを書き、最近の sshd がよく使う keyboard-interactive にも対応させた。公開鍵が断られたらパスワードを聞く。3 回間違えたら終わり、ESC で中止。仮想コンソールで 2 つ目の画面を開くときは、もう聞かない。

実機の Z では、担当が Pico のキーボード機能から本物のキー入力の経路でパスワードを打って、全部の場合を確かめた。

## TCP を Pico に

Z の TCP/IP は、今は xip.x が Z の上でやっている。これを Pico の lwIP に任せる仕組みを作った。Z 側は tis.x (`tis.x -p`)。xip.x と同じ窓口を持つので、rcmd.x も ssh.x も作り直さずに載る。Pico との間は、暗号アクセラレータと同じ流儀の記録で、1 回のやり取りに複数のソケットの用件をまとめる。

Mac の上の試験台で、xip.x の道と比べた (XEiJ、10MHz)。

| | tis.x -p | xip.x |
| --- | --- | --- |
| 1 バイトの往復 | 39 ms | 102 ms |
| Z → Mac、1MB | 166 KB/s | 33 KB/s |
| Mac → Z、1MB | 233 KB/s | 65 KB/s |
| rcmd.x で 300KB を Z へ | 167 KB/s | 17 KB/s |

2.5〜10 倍。ただし XEiJ の中では、Z と Pico の 1 回のやり取りの時間がほぼ 0 なので、実機ではここに USB の時間が足される。実機の数字はまだ無い。

そして、今の Pico W には入らなかった。この仕組みを足すと RAM を 12KB 使い、空きが 112KB から 100KB に減る。動いている Pico の実際の使用量を見ると、それでは途中で尽きる恐れが高い。書き込むのはやめて、Pico 2 W の側でだけ使うことにした。ちょうど、その部品が手元にある。

## Pico 2 W

その間に、AI は今のファームを Pico 2 W 向けにビルドさせていた。開発キットを上げて、FreeRTOS を RP2350 版に替え、ソースの直しは 44 行。SMB も USB も Wi-Fi も、そのまま通った。空きのメモリは 362KB で、Pico W の約 3.6 倍。TCP の仕組みも削らずに入る。

焼いてみると、Wi-Fi には 5 秒ほどでつながり、SMB の HDS も開いた。ところが Z に挿すと「ディスクから起動できません」。Debug Probe でログを見て、止めて中を調べると、USB の相手 (Z や Mac) とやり取りを始めて 1 秒ほどでファームが落ちていた。FreeRTOS も USB の割り込みも単体では正常で、USB ディスクの処理をタスクの中で回す組み合わせのどこかに絞れている。まだ直っていない。

もう 1 枚の Pico 2 WH には、ブレッドボードで microSD をつないだ。SPI は 25MHz で安定し、読み書きとも約 2.2MB/s。1MB を書いて読み戻す照合を 23 回続けて、一度も化けなかった。SD から起動する Pico Z Loader の土台になる。

## Z-OS の核

Z-OS の核 (マルチタスク) の試作も、並行して進んでいた。計画では、MFP のタイマーで作業を切り替える仕組みを自前で書くはずだった。でも担当が Human68k 3.02 の中を調べると、**Human68k 自身が、時間で作業を切り替える仕組みを持っていた**。CONFIG.SYS の `PROCESS=` で有効になるもので、DOS の呼び出しの最中は切り替えを後回しにする作りも入っている。tis.x もこの仕組み (`_OPEN_PR`) を使っているので、自前で書けばぶつかる。

そこで zos.x はスケジューラを書かず、Human68k のスレッドの上に、ペインの画面とキーの振り分けを足す形にした。画面を左右に割り、ペインごとに手を加えていないプログラムを動かす。F10 でキーを受けるペインを切り替える。

XEiJ で、両方のペインに zsh が出た。片方で gcc (真里子版) で hello.c をコンパイルすると、12 秒で `hello, Z-OS` が出た。その間、もう片方の数え上げは止まらずに進んだ。

## リダイレクトがペインをまたぐ

試験の中で、おかしなことが起きた。ペイン 1 で `count.x R … > redir.txt` とファイルに書かせ、その間にペイン 2 で `count.x B …` を画面に出す。すると、redir.txt にペイン 2 の `B` の行が混ざった。

原因は、Human68k が「どのファイル番号が何につながっているか」の表を 1 つしか持っていないことだった。Human68k のスレッドは、切り替えのときにこの表を入れ替えない。カレントドライブとカレントディレクトリも同じ作りで、こちらは最初の試作のときに、切り替えのフックでペインごとに入れ替えるようにしてあった。

担当は、同じフックでファイル番号の表もペインごとに持たせた。ファイルの実体の表は全体で 1 つのまま、UNIX のプロセスごとのファイル番号と同じ形だ。直した後は、redir.txt には `R` の 40 行だけが入る。

## 実機で

それから Z の実機で動かした。キーは Pico のキーボード機能から。

- ペイン 1 で gcc が hello.c をコンパイルし、`hello, Z-OS` が出た。
- ペイン 2 で `ssh.x -t -oAccel=all` で raspi5 にログインした。`stty size` は `31 48`。ssh.x の端末が、ペインの大きさを自分の画面として扱っている。`exit` で zsh に戻った。

実機では、XEiJ で出なかった問題も出た。ペインを閉じてもメモリが返らず、2 回目の起動が「Out of memory」になった。切り替えのたびに状態を写す手間で、ssh の鍵交換が sshd の制限時間 (120 秒) を超えた。どちらも直した。

## 実機の X68000

Z-OS は Pico が要るので、X68000 の実機では動かない。でも僕は思った。「SCSI インターフェイスの部分に別のマイコン使えばいけなくはないか」

AI によると前例がある。BlueSCSI v2 や ZuluSCSI は、Pico と同じ RP2040 で SCSI の機器のふりをする。Z-OS から見れば「SCSI ID 6 の読み書き」で同じだ。だから今のうちに、Pico 側の「SCSI の命令を処理する層」と「運び方 (USB か SCSI のバスか)」を分けておく。

## まだ

- Pico 2 W のファームは、USB の相手がつながると落ちる。TCP を Pico に任せたときの、実機の速さはこれから。
- HTTPS (Pico の mbedTLS) も、Pico 2 W の RAM が前提。
- Z-OS: ssh.x が色の表を書き換えるので、ほかのペインの色も変わる。タブ、ペインの開き直し、iTerm2 風のキー操作はまだ無い。gcc の実行中に先打ちしたキーは消える。
- Pico Z Loader から Z-OS を選んで起動するところも、まだ。
- 日本語入力 (FEP) は相変わらず保留。

昨日まで、Z は raspi5 につなぐ端末だった。今は、Z の上で 2 つのプログラムが同時に動いている。Z と Pico だけで、どこまで行けるか。
